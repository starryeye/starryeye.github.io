초록

이 명세는 OAuth 2.0 protected resource(보호된 리소스)에 접근하기 위해 HTTP 요청에서 bearer token(베어러 토큰)을 사용하는 방법을 설명합니다. bearer token을 소유한 당사자("bearer")라면 누구나 암호학적 키의 소유를 입증하지 않고도 해당 token을 사용하여 관련 리소스에 접근할 수 있습니다. 오용을 방지하려면 저장 및 전송 과정에서 bearer token이 노출되지 않도록 보호해야 합니다.

1. 서론

OAuth는 client(클라이언트)가 resource owner(리소스 소유자)의 자격 증명을 직접 사용하는 대신 access token(액세스 토큰)을 얻어 protected resource에 접근할 수 있게 합니다. "The OAuth 2.0 Authorization Framework" [RFC6749]는 access token을 "client에 발급된 접근 인가를 나타내는 문자열"로 정의합니다.

authorization server(인가 서버)는 resource owner의 승인을 받아 client에 token을 발급합니다. client는 access token을 사용하여 resource server(리소스 서버)가 호스팅하는 protected resource에 접근합니다. 이 명세는 OAuth access token이 bearer token인 경우 protected resource 요청을 수행하는 방법을 설명합니다.

이 명세는 Transport Layer Security (TLS) [RFC5246]를 사용하는 HTTP/1.1 [RFC2616]을 통해 bearer token으로 protected resource에 접근하는 방법을 정의합니다. 이 명세에서는 TLS의 구현과 사용이 필수입니다. 다른 명세는 다른 protocol과 함께 사용할 수 있도록 이 명세를 확장할 수 있습니다. 이 명세는 access token을 사용하도록 설계되었으며, 이러한 token은 OAuth protected resource에 접근하기 위한 OAuth 2.0 인가 [RFC6749] 흐름에서 얻습니다. 그러나 이 명세가 실제로 정의하는 것은 출처에 관계없이 bearer token을 사용하여 해당 bearer token으로 보호되는 모든 resource에 접근할 수 있는 일반적인 HTTP 인가 방법입니다. Bearer 인증 방식은 주로 WWW-Authenticate 및 Authorization HTTP header를 사용하는 서버 인증을 위한 것이지만, proxy 인증에 사용하는 것을 배제하지는 않습니다.

1.1. 표기 규칙

이 문서의 핵심어 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", "OPTIONAL"는 "Key words for use in RFCs to Indicate Requirement Levels" [RFC2119]에 설명된 대로 해석합니다.

이 문서는 [RFC5234]의 Augmented Backus-Naur Form (ABNF) 표기법을 사용합니다. 또한 HTTP/1.1 [RFC2617]의 auth-param 및 auth-scheme 규칙과 "Uniform Resource Identifier (URI): Generic Syntax" [RFC3986]의 URI-reference 규칙을 포함합니다.

달리 명시하지 않는 한, 모든 protocol parameter의 이름과 값은 대소문자를 구분합니다.

1.2. 용어

Bearer Token token을 소지한 당사자("bearer")라면 누구나 그 token을 소지한 다른 당사자가 사용할 수 있는 모든 방식으로 사용할 수 있다는 특성을 지닌 security token입니다. bearer token을 사용할 때 bearer가 암호학적 키 자료의 소유를 증명할 필요는 없습니다(proof-of-possession(소유 증명)).

다른 모든 용어는 "The OAuth 2.0 Authorization Framework" [RFC6749]의 정의를 따릅니다.

1.3. 개요

OAuth는 client가 resource owner를 대신하여 protected resource에 접근하는 방법을 제공합니다. 일반적으로 client가 protected resource에 접근하려면 먼저 resource owner로부터 authorization grant(권한 부여)를 얻은 다음, 이를 access token으로 교환해야 합니다. access token은 authorization grant가 부여한 scope(접근 범위), 기간 및 기타 속성을 나타냅니다. client는 resource server에 access token을 제시하여 protected resource에 접근합니다. 경우에 따라 client는 resource owner로부터 먼저 authorization grant를 얻지 않고도 자신의 자격 증명을 authorization server에 직접 제시하여 access token을 얻을 수 있습니다.

access token은 서로 다른 인가 수단(예: 사용자 이름과 비밀번호, assertion)을 resource server가 이해하는 단일 token으로 대체하는 추상화를 제공합니다. 이 추상화를 통해 짧은 기간 동안 유효한 access token을 발급할 수 있으며, resource server가 다양한 인증 방식을 이해할 필요도 없어집니다. 

     +--------+                               +---------------+
     |        |--(A)- Authorization Request ->|   Resource    |
     |        |                               |     Owner     |
     |        |<-(B)-- Authorization Grant ---|               |
     |        |                               +---------------+
     |        |
     |        |                               +---------------+
     |        |--(C)-- Authorization Grant -->| Authorization |
     | Client |                               |     Server    |
     |        |<-(D)----- Access Token -------|               |
     |        |                               +---------------+
     |        |
     |        |                               +---------------+
     |        |--(E)----- Access Token ------>|    Resource   |
     |        |                               |     Server    |
     |        |<-(F)--- Protected Resource ---|               |
     +--------+                               +---------------+

그림 1에 나타낸 추상적인 OAuth 2.0 흐름은 client, resource owner, authorization server 및 resource server 간의 상호 작용을 설명합니다([RFC6749]에 기술되어 있습니다). 이 문서는 다음 두 단계를 명세합니다.

(E) client는 resource server에 protected resource를 요청하고, access token을 제시하여 인증합니다.

(F) resource server는 access token을 검증하고, 유효하면 요청을 처리합니다.

이 문서는 단계 (D)에서 반환하는 access token에 대해서도 의미상의 요구 사항을 부과합니다.

2. 인증된 요청

이 절은 resource server에 보내는 resource 요청에 bearer access token을 전송하는 세 가지 방법을 정의합니다. client는 각 요청에서 token을 전송하는 방법을 둘 이상 사용해서는 안 됩니다(MUST NOT).

2.1. Authorization 요청 header field

HTTP/1.1 [RFC2617]에서 정의한 "Authorization" 요청 header field로 access token을 보낼 때 client는 "Bearer" 인증 방식을 사용하여 access token을 전송합니다.

예를 들면 다음과 같습니다. 

     GET /resource HTTP/1.1
     Host: server.example.com
     Authorization: Bearer mF_9.B5f-4.1JqM

이 방식의 "Authorization" header field 구문은 [RFC2617]의 2절에 정의된 Basic 방식의 사용법을 따릅니다. Basic과 마찬가지로 [RFC2617]의 1.2절에 정의된 일반 구문을 따르지는 않지만, HTTP 1.1을 위해 개발 중인 일반 인증 framework [HTTP-AUTH]와 호환됩니다. 다만 기존 배포 환경을 반영하기 위해 그 framework에서 제시하는 권장 관행을 따르지는 않는다는 점에 유의하십시오. Bearer 자격 증명의 구문은 다음과 같습니다. 

     b64token    = 1*( ALPHA / DIGIT /
                       "-" / "." / "_" / "~" / "+" / "/" ) *"="
     credentials = "Bearer" 1*SP b64token

client는 "Bearer" HTTP 인가 방식과 함께 "Authorization" 요청 header field를 사용하여 bearer token으로 인증된 요청을 수행하는 것이 좋습니다(SHOULD). resource server는 이 방법을 지원해야 합니다(MUST).

2.2. Form으로 인코딩된 body parameter

HTTP 요청 entity-body로 access token을 보낼 때 client는 "access_token" parameter를 사용하여 request-body에 access token을 추가합니다. 다음 조건이 모두 충족되지 않으면 client는 이 방법을 사용해서는 안 됩니다(MUST NOT).

o HTTP 요청 entity-header에 "application/x-www-form-urlencoded"로 설정된 "Content-Type" header field가 포함됩니다.

o entity-body가 HTML 4.01 [W3C.REC-html401-19991224]에 정의된 "application/x-www-form-urlencoded" content-type의 인코딩 요구 사항을 따릅니다.

o HTTP 요청 entity-body가 single-part입니다.

o entity-body에 인코딩할 내용은 전부 ASCII [USASCII] 문자로 구성되어야 합니다(MUST).

o HTTP 요청 method는 request-body의 의미가 정의된 method입니다. 특히 이는 "GET" method를 사용해서는 안 된다는 뜻입니다(MUST NOT).

entity-body에는 다른 요청별 parameter를 포함할 수 있습니다(MAY). 이 경우 "access_token" parameter는 "&" 문자(ASCII 코드 38)를 하나 이상 사용하여 요청별 parameter와 올바르게 구분해야 합니다(MUST).

예를 들어 client는 transport-layer security를 사용하여 다음 HTTP 요청을 수행합니다. 

     POST /resource HTTP/1.1
     Host: server.example.com
     Content-Type: application/x-www-form-urlencoded

     access_token=mF_9.B5f-4.1JqM

참여하는 browser가 "Authorization" 요청 header field에 접근할 수 없는 application 환경을 제외하고는 "application/x-www-form-urlencoded" 방법을 사용하지 않는 것이 좋습니다(SHOULD NOT). resource server는 이 방법을 지원할 수 있습니다(MAY).

2.3. URI query parameter

HTTP 요청 URI로 access token을 보낼 때 client는 "access_token" parameter를 사용하여 "Uniform Resource Identifier (URI): Generic Syntax" [RFC3986]에 정의된 요청 URI의 query 구성 요소에 access token을 추가합니다.

예를 들어 client는 transport-layer security를 사용하여 다음 HTTP 요청을 수행합니다. 

     GET /resource?access_token=mF_9.B5f-4.1JqM HTTP/1.1
     Host: server.example.com

HTTP 요청 URI의 query에는 다른 요청별 parameter가 포함될 수 있습니다. 이 경우 "access_token" parameter는 "&" 문자(ASCII 코드 38)를 하나 이상 사용하여 요청별 parameter와 올바르게 구분해야 합니다(MUST).

예를 들면 다음과 같습니다. 

    https://server.example.com/resource?access_token=mF_9.B5f-4.1JqM&p=q

URI Query Parameter 방법을 사용하는 client는 "no-store" option을 포함한 Cache-Control header도 보내는 것이 좋습니다(SHOULD). 이러한 요청에 대한 서버의 성공 응답(2XX 상태)에는 "private" option이 있는 Cache-Control header를 포함하는 것이 좋습니다(SHOULD).

access token을 포함한 URL이 로그에 기록될 가능성이 높다는 점을 비롯하여 URI 방법에는 보안상 취약점이 있으므로(5절 참조), "Authorization" 요청 header field 또는 HTTP 요청 entity-body로 access token을 전송하는 것이 불가능한 경우가 아니라면 이 방법을 사용하지 않는 것이 좋습니다(SHOULD NOT). resource server는 이 방법을 지원할 수 있습니다(MAY).

이 방법은 현재의 사용 현황을 문서화하기 위해 포함되었습니다. 보안상의 결함(5절 참조)이 있고, 예약된 query parameter 이름을 사용한다는 점이 "Architecture of the World Wide Web, Volume One" [W3C.REC-webarch-20041215]에 따른 URI namespace 모범 관행에도 어긋나므로 사용을 권장하지 않습니다.

3. WWW-Authenticate 응답 header field

protected resource 요청에 인증 자격 증명이 포함되어 있지 않거나, 해당 protected resource에 접근할 수 있게 하는 access token이 포함되어 있지 않으면 resource server는 HTTP "WWW-Authenticate" 응답 header field를 포함해야 합니다(MUST). 다른 조건에 대한 응답에도 이를 포함할 수 있습니다(MAY). "WWW-Authenticate" header field는 HTTP/1.1 [RFC2617]에서 정의한 framework를 사용합니다.

이 명세에서 정의하는 모든 challenge는 auth-scheme 값으로 "Bearer"를 사용해야 합니다(MUST). 이 scheme 뒤에는 하나 이상의 auth-param 값이 와야 합니다(MUST). 이 명세에서 사용하거나 정의하는 auth-param 속성은 다음과 같습니다. 다른 auth-param 속성도 사용할 수 있습니다(MAY).

HTTP/1.1 [RFC2617]에 설명된 방식으로 보호 범위를 나타내기 위해 "realm" 속성을 포함할 수 있습니다(MAY). "realm" 속성이 두 번 이상 나타나서는 안 됩니다(MUST NOT).

"scope" 속성은 [RFC6749]의 3.3절에 정의되어 있습니다. "scope" 속성은 요청한 resource에 접근하기 위해 access token에 필요한 scope를 나타내며, 대소문자를 구분하는 scope 값들을 공백으로 구분한 목록입니다. "scope" 값은 구현에 따라 정의되며, 중앙화된 registry는 없습니다. 허용되는 값은 authorization server가 정의합니다. "scope" 값의 순서는 중요하지 않습니다. 경우에 따라 "scope" 값은 protected resource를 이용하기에 충분한 접근 scope를 가진 새 access token을 요청할 때 사용됩니다. "scope" 속성의 사용은 선택 사항입니다(OPTIONAL). "scope" 속성이 두 번 이상 나타나서는 안 됩니다(MUST NOT). "scope" 값은 프로그램에서 사용하기 위한 것이며, 최종 사용자에게 표시하기 위한 것이 아닙니다.

다음은 두 가지 scope 값의 예입니다. 각각 OpenID Connect [OpenID.Messages]와 Open Authentication Technology Committee (OATC)의 Online Multimedia Authorization Protocol [OMAP] OAuth 2.0 사용 사례에서 가져왔습니다. 

     scope="openid profile email"
     scope="urn:example:channel=HBO&urn:example:rating=G,PG-13"

protected resource 요청에 access token이 포함되어 있고 인증에 실패한 경우, resource server는 접근 요청이 거부된 이유를 client에 알리기 위해 "error" 속성을 포함하는 것이 좋습니다(SHOULD). 이 매개변수의 값은 3.1절에 설명되어 있습니다. 또한 resource server는 최종 사용자에게 표시하기 위한 것이 아닌, 개발자를 위한 사람이 읽을 수 있는 설명을 제공하도록 "error_description" 속성을 포함할 수 있습니다(MAY). 오류를 설명하는 사람이 읽을 수 있는 웹 페이지를 식별하는 절대 URI와 함께 "error_uri" 속성을 포함할 수도 있습니다(MAY). "error", "error_description", "error_uri" 속성은 각각 두 번 이상 나타나서는 안 됩니다(MUST NOT).

"scope" 속성의 값([RFC6749] 부록 A.4에 명시됨)에는 scope 값을 나타내는 문자 집합 %x21 / %x23-5B / %x5D-7E와 scope 값 사이의 구분자인 %x20 이외의 문자가 포함되어서는 안 됩니다(MUST NOT). "error" 및 "error_description" 속성의 값([RFC6749] 부록 A.7 및 A.8에 명시됨)에는 문자 집합 %x20-21 / %x23-5B / %x5D-7E 이외의 문자가 포함되어서는 안 됩니다(MUST NOT). "error_uri" 속성의 값([RFC6749] 부록 A.9에 명시됨)은 URI-reference 구문을 따라야 하며(MUST), 따라서 문자 집합 %x21 / %x23-5B / %x5D-7E 이외의 문자가 포함되어서는 안 됩니다(MUST NOT).

예를 들어, 인증 정보가 없는 protected resource 요청에 대한 응답은 다음과 같습니다.

     HTTP/1.1 401 Unauthorized
     WWW-Authenticate: Bearer realm="example"

그리고 만료된 access token으로 인증을 시도한 protected resource 요청에 대한 응답은 다음과 같습니다.

     HTTP/1.1 401 Unauthorized
     WWW-Authenticate: Bearer realm="example",
                       error="invalid_token",
                       error_description="The access token expired"

3.1. 오류 코드

요청이 실패하면 resource server는 적절한 HTTP 상태 코드(일반적으로 400, 401, 403 또는 405)로 응답하고, 다음 오류 코드 중 하나를 응답에 포함합니다.

invalid_request 요청에 필수 매개변수가 누락되어 있거나, 지원하지 않는 매개변수 또는 매개변수 값이 포함되어 있거나, 같은 매개변수가 반복되거나, access token을 포함하는 데 둘 이상의 방법을 사용하거나, 그 밖의 형식 오류가 있습니다. resource server는 HTTP 400 (Bad Request) 상태 코드로 응답하는 것이 좋습니다(SHOULD).

invalid_token 제공된 access token이 만료되었거나, 폐기되었거나, 형식이 잘못되었거나, 그 밖의 이유로 유효하지 않습니다. resource는 HTTP 401 (Unauthorized) 상태 코드로 응답하는 것이 좋습니다(SHOULD). client는 새 access token을 요청하고 protected resource 요청을 재시도할 수 있습니다(MAY).

insufficient_scope 요청에는 access token이 제공하는 것보다 높은 권한이 필요합니다. resource server는 HTTP 403 (Forbidden) 상태 코드로 응답하는 것이 좋으며(SHOULD), protected resource에 접근하는 데 필요한 scope를 담은 "scope" 속성을 포함할 수 있습니다(MAY).

요청에 인증 정보가 전혀 없는 경우(예를 들어 client가 인증이 필요하다는 사실을 몰랐거나 지원하지 않는 인증 방법을 사용하려고 시도한 경우), resource server는 오류 코드나 그 밖의 오류 정보를 포함하지 않는 것이 좋습니다(SHOULD NOT).

예를 들면 다음과 같습니다.

     HTTP/1.1 401 Unauthorized
     WWW-Authenticate: Bearer realm="example"

4. access token 응답 예시

일반적으로 bearer token은 OAuth 2.0 [RFC6749] access token 응답의 일부로 client에 반환됩니다. 이러한 응답의 예시는 다음과 같습니다.

     HTTP/1.1 200 OK
     Content-Type: application/json;charset=UTF-8
     Cache-Control: no-store
     Pragma: no-cache

     {
       "access_token":"mF_9.B5f-4.1JqM",
       "token_type":"Bearer",
       "expires_in":3600,
       "refresh_token":"tGzv3JOkF0XG5Qx2TlKWIA"
     }

5. 보안 고려 사항

이 절에서는 bearer token 사용 시 token 처리와 관련된 보안 위협과 이러한 위협을 완화하는 방법을 설명합니다.

5.1. 보안 위협

다음 목록은 어떤 형태로든 token을 사용하는 프로토콜에 대한 몇 가지 일반적인 위협을 제시합니다. 이 위협 목록은 NIST Special Publication 800-63 [NIST800-63]을 기반으로 합니다. 이 문서는 OAuth 2.0 Authorization 명세 [RFC6749]를 기반으로 하므로, 해당 명세나 관련 문서에 설명된 위협은 논의에서 제외합니다.

Token manufacture/modification: 공격자가 가짜 token을 생성하거나 기존 token의 내용(인증 또는 속성 statement 등)을 수정하여, resource server가 client에 부적절한 접근 권한을 부여하도록 만들 수 있습니다. 예를 들어 공격자는 유효 기간을 연장하기 위해 token을 수정할 수 있으며, 악의적인 client는 자신이 볼 수 없어야 하는 정보에 접근하기 위해 assertion을 수정할 수 있습니다.

Token disclosure: token에는 민감한 정보를 담은 인증 및 속성 statement가 포함될 수 있습니다.

Token redirect: 공격자는 한 resource server에서 사용하도록 생성된 token을 사용하여, 해당 token이 자신을 위한 것이라고 잘못 판단하는 다른 resource server에 접근합니다.

Token replay: 공격자는 과거에 해당 resource server에서 이미 사용된 token을 다시 사용하려고 시도합니다.

5.2. 위협 완화

digital signature 또는 Message Authentication Code (MAC)를 사용하여 token의 내용을 보호하면 광범위한 위협을 완화할 수 있습니다. 또는 bearer token이 인가 정보를 직접 인코딩하는 대신 해당 정보에 대한 참조를 담을 수도 있습니다. 이러한 참조는 공격자가 추측하는 것이 현실적으로 불가능해야 합니다(MUST). 참조를 사용하는 경우, 참조로부터 인가 정보를 알아내기 위해 서버와 token 발급자 사이에 추가 상호작용이 필요할 수 있습니다. 이 명세에서는 그러한 상호작용의 구체적인 방식을 정의하지 않습니다.

이 문서는 token의 인코딩이나 내용을 명시하지 않으므로, token의 integrity(무결성) 보호를 보장하는 수단에 대한 상세한 권고 사항은 이 문서의 범위를 벗어납니다. token의 integrity 보호는 token이 수정되는 것을 막기에 충분해야 합니다(MUST).

token redirect에 대응하려면 authorization server가 의도한 수신자(audience(수신 대상))의 식별 정보를 token에 포함하는 것이 중요합니다. 수신자는 일반적으로 하나의 resource server(또는 resource server 목록)입니다. token 사용을 특정 scope로 제한하는 것도 권장됩니다(RECOMMENDED).

authorization server는 TLS를 구현해야 합니다(MUST). 구현하는 것이 바람직한 버전은 시간에 따라 달라지며, 구현 당시의 보급 현황과 알려진 보안 취약점에 따라 결정됩니다. 이 문서를 작성하는 시점에는 TLS 버전 1.2 [RFC5246]가 최신 버전이지만, 실제로 배포된 사례는 매우 제한적이며 구현 toolkit에서 바로 사용할 수 없을 수도 있습니다. TLS 버전 1.0 [RFC2246]은 가장 널리 배포된 버전으로, 가장 폭넓은 상호운용성을 제공합니다.

token 유출을 방지하려면 confidentiality(기밀성)와 integrity 보호를 제공하는 ciphersuite와 함께 TLS [RFC5246]를 사용하여 confidentiality 보호를 적용해야 합니다(MUST). 이는 client와 authorization server 간의 통신 상호작용뿐 아니라 client와 resource server 간의 상호작용에도 confidentiality와 integrity 보호를 사용해야 함을 의미합니다. 이 명세에서는 TLS의 구현과 사용이 필수이므로, TLS는 통신 채널을 통한 token 유출을 방지하는 데 우선적으로 선택하는 방법입니다. client가 token의 내용을 볼 수 없도록 해야 하는 경우에는 TLS 보호에 더하여 token 암호화를 적용해야 합니다(MUST). token 유출에 대한 추가 방어 수단으로, client는 protected resource에 요청을 보낼 때 Certificate Revocation List (CRL) [RFC5280] 확인을 포함하여 TLS certificate chain을 검증해야 합니다(MUST).

cookie는 일반적으로 평문으로 전송됩니다. 따라서 cookie에 포함된 모든 정보는 유출 위험에 노출됩니다. 그러므로 bearer token을 평문으로 전송될 수 있는 cookie에 저장해서는 안 됩니다(MUST NOT). cookie에 대한 보안 고려 사항은 "HTTP State Management Mechanism" [RFC6265]을 참조하십시오.

load balancer를 사용하는 배포 환경을 비롯한 일부 배포 환경에서는 resource server로 향하는 TLS 연결이 실제로 resource를 제공하는 서버에 도달하기 전에 종료됩니다. 이 경우 TLS 연결이 종료되는 front-end 서버와 resource를 제공하는 back-end 서버 사이에서 token이 보호되지 않을 수 있습니다. 이러한 배포 환경에서는 front-end 서버와 back-end 서버 사이에서 token의 confidentiality를 보장하기 위한 충분한 조치를 취해야 합니다(MUST). token 암호화는 가능한 조치 중 하나입니다.

token 탈취와 재사용에 대응하기 위해 다음과 같이 권고합니다. 첫째, token의 수명을 제한해야 합니다(MUST). 이를 달성하는 한 가지 방법은 token의 보호되는 부분에 유효 시간 필드를 넣는 것입니다. 수명이 짧은(1시간 이하인) token을 사용하면 유출 시의 영향을 줄일 수 있다는 점에 유의하십시오. 둘째, client와 authorization server 사이 및 client와 resource server 사이의 교환에 confidentiality 보호를 적용해야 합니다(MUST). 그러면 통신 경로의 도청자는 token 교환을 관찰할 수 없습니다. 따라서 이러한 경로상의 공격자는 token을 재사용할 수 없습니다. 또한 client는 resource server에 token을 제시할 때 "HTTP Over TLS" [RFC2818]의 3.1절에 따라 해당 resource server의 신원을 검증해야 합니다(MUST). client는 protected resource에 이러한 요청을 보낼 때 TLS certificate chain을 검증해야 한다는 점에 유의하십시오(MUST). 인증되지 않고 인가되지 않은 resource server에 token을 제시하거나 certificate chain을 검증하지 않으면, 공격자가 token을 탈취하여 protected resource에 무단으로 접근할 수 있게 됩니다.

5.3. 권고 사항 요약

bearer token 보호: client 구현은 bearer token이 의도하지 않은 당사자에게 유출되지 않도록 보장해야 합니다(MUST). 이들은 해당 token을 사용하여 protected resource에 접근할 수 있기 때문입니다. 이는 bearer token 사용 시 가장 중요한 보안 고려 사항이며, 뒤이어 나오는 모든 세부 권고 사항의 바탕이 됩니다.

TLS certificate chain 검증: client는 protected resource에 요청을 보낼 때 TLS certificate chain을 검증해야 합니다(MUST). 그렇게 하지 않으면 DNS hijacking 공격으로 token이 탈취되고 의도하지 않은 접근이 이루어질 수 있습니다.

항상 TLS (https) 사용: client는 bearer token을 사용하여 요청을 보낼 때 항상 TLS [RFC5246] (https) 또는 동등한 전송 보안을 사용해야 합니다(MUST). 그렇게 하지 않으면 token이 수많은 공격에 노출되어 공격자에게 의도하지 않은 접근 권한을 줄 수 있습니다.

bearer token을 cookie에 저장하지 않기: 구현은 평문으로 전송될 수 있는 cookie에 bearer token을 저장해서는 안 됩니다(MUST NOT). 평문 전송은 cookie의 기본 전송 방식입니다. bearer token을 cookie에 저장하는 구현은 cross-site request forgery에 대한 예방 조치를 취해야 합니다(MUST).

수명이 짧은 bearer token 발급: token 서버는 수명이 짧은(1시간 이하인) bearer token을 발급하는 것이 좋습니다(SHOULD). 특히 웹 브라우저나 정보 유출이 발생할 수 있는 그 밖의 환경에서 실행되는 client에 token을 발급할 때 그러합니다. 수명이 짧은 bearer token을 사용하면 유출 시의 영향을 줄일 수 있습니다.

사용 범위가 제한된 bearer token 발급: token 서버는 audience 제한이 포함된 bearer token을 발급하여, 의도한 relying party 또는 relying party 집합에서만 사용되도록 범위를 제한하는 것이 좋습니다(SHOULD).

페이지 URL로 bearer token을 전달하지 않습니다: bearer token을 페이지 URL로 전달하지 않는 것이 권장됩니다(SHOULD NOT). 예를 들어 query string parameter로 전달하지 않는 것이 권장됩니다. 대신 confidentiality 조치가 적용된 HTTP message header나 message body로 bearer token을 전달하는 것이 권장됩니다(SHOULD). Browser, web server 및 기타 소프트웨어는 browser 방문 기록, web server 로그 및 기타 데이터 구조에 있는 URL을 충분히 보호하지 못할 수 있습니다. 페이지 URL로 bearer token을 전달하면 공격자가 방문 기록 데이터, 로그 또는 그 밖의 보호되지 않은 위치에서 이를 탈취할 수 있습니다.
