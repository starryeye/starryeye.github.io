초록

OAuth 2.0 authorization framework는 제3자 애플리케이션이 HTTP 서비스에 제한적으로 접근할 수 있게 합니다. 이는 resource owner(리소스 소유자)와 HTTP 서비스 사이의 승인 상호작용을 조율하여 resource owner를 대신해 접근하도록 하거나, 제3자 애플리케이션이 자신을 위해 접근 권한을 얻도록 하는 방식으로 이루어집니다. 이 명세는 RFC 5849에 기술된 OAuth 1.0 프로토콜을 대체하고 폐기합니다.

1. 소개

기존 client-server 인증 모델에서는 client가 resource owner의 자격 증명으로 서버에 인증하여 서버의 접근 제한 리소스(protected resource)를 요청합니다. 제3자 애플리케이션이 접근 제한 리소스에 접근하도록 하려면 resource owner는 자신의 자격 증명을 제3자와 공유합니다. 이로 인해 여러 문제와 제약이 발생합니다.

o 제3자 애플리케이션은 나중에 사용하기 위해 resource owner의 자격 증명을 저장해야 하며, 이는 대개 평문 비밀번호입니다.

o 서버는 비밀번호에 내재된 보안 취약점에도 불구하고 비밀번호 인증을 지원해야 합니다.

o 제3자 애플리케이션은 resource owner의 protected resource에 지나치게 광범위하게 접근할 수 있게 되며, resource owner는 접근 기간을 제한하거나 접근 대상을 리소스의 일부로 한정할 수 없습니다.

o resource owner는 모든 제3자의 접근 권한을 취소하지 않고서는 특정 제3자의 접근 권한만 취소할 수 없으며, 이러한 취소는 제3자의 비밀번호를 변경하는 방식으로 해야 합니다.

o 어느 제3자 애플리케이션이든 침해되면 최종 사용자의 비밀번호와 그 비밀번호로 보호되는 모든 데이터가 함께 침해됩니다.

OAuth는 인가 계층을 도입하고 client와 resource owner의 역할을 분리하여 이러한 문제를 해결합니다. OAuth에서 client는 resource owner가 제어하고 resource server(리소스 서버)가 호스팅하는 리소스에 대한 접근을 요청하며, resource owner의 자격 증명과는 다른 별도의 자격 증명을 발급받습니다.

client는 resource owner의 자격 증명으로 protected resource에 접근하는 대신 access token을 얻습니다. access token은 특정 scope, 유효 기간 및 기타 접근 속성을 나타내는 문자열입니다. authorization server(인가 서버)는 resource owner의 승인을 받아 제3자 client에 access token을 발급합니다. client는 access token을 사용하여 resource server가 호스팅하는 protected resource에 접근합니다.

예를 들어 최종 사용자(resource owner)는 인쇄 서비스(client)에 자신의 사용자 이름과 비밀번호를 공유하지 않고도 사진 공유 서비스(resource server)에 저장된 자신의 보호된 사진에 대한 접근 권한을 부여할 수 있습니다. 사용자는 대신 사진 공유 서비스가 신뢰하는 서버(authorization server)에 직접 인증하며, 이 서버는 해당 위임에 특화된 자격 증명(access token)을 인쇄 서비스에 발급합니다.

이 명세는 HTTP([RFC2616])와 함께 사용하도록 설계되었습니다. HTTP 이외의 프로토콜을 통한 OAuth 사용은 이 명세의 범위를 벗어납니다.

정보성 문서로 발행된 OAuth 1.0 프로토콜([RFC5849])은 소규모의 비공식 커뮤니티가 기울인 노력의 결과였습니다. 이 표준 트랙 명세는 OAuth 1.0의 배포 경험뿐 아니라 더 넓은 IETF 커뮤니티에서 수집한 추가 사용 사례와 확장성 요구 사항을 바탕으로 합니다. OAuth 2.0 프로토콜은 OAuth 1.0과 하위 호환되지 않습니다. 두 버전은 네트워크에서 공존할 수 있으며, 구현체는 두 버전을 모두 지원하도록 선택할 수 있습니다. 그러나 이 명세의 의도는 새로운 구현체가 이 문서에 명시된 OAuth 2.0을 지원하고, OAuth 1.0은 기존 배포를 지원하는 데만 사용하도록 하는 것입니다. OAuth 2.0 프로토콜이 OAuth 1.0 프로토콜과 공유하는 구현 세부 사항은 거의 없습니다. OAuth 1.0에 익숙한 구현자는 이 문서의 구조와 세부 사항에 관해 어떠한 가정도 하지 않은 채 이 문서를 읽어야 합니다.

1.1. 역할

OAuth는 다음 네 가지 역할을 정의합니다.

resource owner protected resource에 대한 접근 권한을 부여할 수 있는 주체입니다. resource owner가 사람인 경우에는 최종 사용자라고 합니다.

resource server protected resource를 호스팅하며 access token을 사용하는 protected resource 요청을 수락하고 이에 응답할 수 있는 서버입니다.

client resource owner를 대신하여, 그 인가를 받아 protected resource를 요청하는 애플리케이션입니다. "client"라는 용어는 특정한 구현 특성(예: 애플리케이션이 서버, 데스크톱 또는 다른 기기에서 실행되는지 여부)을 뜻하지 않습니다.

authorization server resource owner 인증을 성공적으로 마치고 인가를 얻은 후 client에 access token을 발급하는 서버입니다.

authorization server와 resource server 사이의 상호작용은 이 명세의 범위를 벗어납니다. authorization server는 resource server와 동일한 서버일 수도 있고 별도의 개체일 수도 있습니다. 하나의 authorization server가 여러 resource server에서 받아들이는 access token을 발급할 수도 있습니다.

1.2. 프로토콜 흐름

     +--------+                               +---------------+
     |        |--(A)- Authorization Request ->|   Resource    |
     |        |                               |     Owner     |
     |        |<-(B)-- Authorization Grant ---|               |
     |        |                               +---------------+
     |        |
     |        |                               +---------------+
     |        |--(C)-- Authorization Grant -->| Authorization |
     | Client |                               |     Server    |
     |        |<-(D)----- Access Token -------|               |
     |        |                               +---------------+
     |        |
     |        |                               +---------------+
     |        |--(E)----- Access Token ------>|    Resource   |
     |        |                               |     Server    |
     |        |<-(F)--- Protected Resource ---|               |
     +--------+                               +---------------+

그림 1에 나타낸 추상화된 OAuth 2.0 흐름은 네 가지 역할 사이의 상호작용을 설명하며, 다음 단계를 포함합니다.

(A) client는 resource owner에게 인가를 요청합니다. 인가 요청은 (그림과 같이) resource owner에게 직접 할 수도 있고, authorization server를 중개자로 삼아 간접적으로 할 수도 있으며, 후자가 더 바람직합니다.

(B) client는 authorization grant를 받습니다. 이는 resource owner의 인가를 나타내는 자격 증명으로, 이 명세에서 정의하는 네 가지 grant type 중 하나 또는 확장 grant type을 사용하여 표현됩니다. authorization grant type은 client가 인가를 요청하는 데 사용하는 방법과 authorization server가 지원하는 유형에 따라 달라집니다.

(C) client는 authorization server에 자신을 인증하고 authorization grant를 제시하여 access token을 요청합니다.

(D) authorization server는 client를 인증하고 authorization grant의 유효성을 검증하며, 유효하면 access token을 발급합니다.

(E) client는 resource server에 protected resource를 요청하며, access token을 제시하여 자신을 인증합니다.

(F) resource server는 access token의 유효성을 검증하고, 유효하면 요청을 처리합니다.

client가 resource owner에게서 authorization grant를 얻는 방법((A) 및 (B) 단계에 묘사됨)으로는 authorization server를 중개자로 사용하는 방법이 권장되며, 이는 Section 4.1의 그림 3에 나와 있습니다.

1.3. Authorization Grant

authorization grant는 resource owner의 (자신의 protected resource에 접근하도록 하는) 인가를 나타내는 자격 증명이며, client가 access token을 얻는 데 사용합니다. 이 명세는 네 가지 grant type, 즉 authorization code, implicit, resource owner password credentials, client credentials와 함께 추가 유형을 정의하기 위한 확장 메커니즘을 정의합니다.

1.3.1. Authorization Code

authorization code는 authorization server를 client와 resource owner 사이의 중개자로 사용하여 얻습니다. client는 resource owner에게 직접 인가를 요청하는 대신, ([RFC2616]에서 정의한 user-agent(사용자 에이전트)를 통해) resource owner를 authorization server로 보냅니다. 그러면 authorization server는 authorization code와 함께 resource owner를 다시 client로 보냅니다.

authorization server는 authorization code와 함께 resource owner를 다시 client로 보내기 전에 resource owner를 인증하고 인가를 얻습니다. resource owner는 authorization server에만 자신을 인증하므로, resource owner의 자격 증명은 client와 결코 공유되지 않습니다.

authorization code는 몇 가지 중요한 보안상의 이점을 제공합니다. client를 인증할 수 있고, access token을 resource owner의 user-agent를 거치지 않고 client에 직접 전송할 수 있으므로, resource owner를 비롯한 다른 이에게 access token이 노출될 가능성을 피할 수 있습니다.

1.3.2. Implicit

implicit grant는 JavaScript 같은 스크립팅 언어를 사용하여 브라우저 안에서 구현된 client에 최적화된, 간소화된 authorization code 흐름입니다. implicit 흐름에서는 client에 authorization code를 발급하는 대신 access token을 직접 발급합니다 (resource owner가 인가한 결과로 발급됩니다). (authorization code 같은) 중간 자격 증명을 발급하지 않으며 (이를 나중에 access token을 얻는 데 사용하지도 않으므로), 이 grant type을 implicit이라고 합니다.

implicit grant 흐름에서 access token을 발급할 때 authorization server는 client를 인증하지 않습니다. 경우에 따라서는 access token을 client에 전달하는 데 쓰는 redirection URI를 통해 client의 신원을 확인할 수 있습니다. access token은 resource owner에게 노출되거나, resource owner의 user-agent에 접근할 수 있는 다른 애플리케이션에 노출될 수 있습니다.

implicit grant는 access token을 얻는 데 필요한 왕복 횟수를 줄이므로, 일부 client(예: 브라우저 내 애플리케이션으로 구현된 client)의 응답성과 효율성을 높입니다. 그러나 특히 authorization code grant type을 사용할 수 있을 때는 이러한 편의성과, Sections 10.3 및 10.16에 설명된 것과 같은 implicit grant 사용의 보안상 영향을 비교하여 판단해야 합니다.

1.3.3. Resource Owner Password Credentials

resource owner password credentials(즉, 사용자 이름과 비밀번호)는 access token을 얻기 위한 authorization grant로 직접 사용할 수 있습니다. 이 자격 증명은 resource owner와 client 사이에 높은 수준의 신뢰가 있고(예: client가 기기 운영 체제의 일부이거나 매우 높은 권한을 가진 애플리케이션인 경우), 다른 authorization grant type(예: authorization code)을 사용할 수 없을 때에만 사용해야 합니다.

이 grant type은 client가 resource owner의 자격 증명에 직접 접근해야 하지만, resource owner의 자격 증명은 단 한 번의 요청에 사용되며 access token으로 교환됩니다. 이 grant type에서는 자격 증명을 수명이 긴 access token이나 refresh token으로 교환함으로써, client가 나중에 사용하기 위해 resource owner의 자격 증명을 저장할 필요를 없앨 수 있습니다.

1.3.4. Client Credentials

인가 scope가 client의 통제하에 있는 protected resource 또는 authorization server와 사전에 합의한 protected resource로 제한되는 경우, client credentials(또는 다른 형태의 client 인증)를 authorization grant로 사용할 수 있습니다. 일반적으로 client가 자신을 위해 동작하거나(client 자체가 resource owner이기도 한 경우), authorization server와 사전에 합의한 인가에 따라 protected resource에 대한 접근을 요청할 때 client credentials를 authorization grant로 사용합니다.

1.4. Access Token

access token은 protected resource에 접근하는 데 사용하는 자격 증명입니다. access token은 client에 발급된 인가를 나타내는 문자열입니다. 이 문자열은 일반적으로 client가 그 내용을 해석할 수 없는 불투명한 값입니다. token은 resource owner가 허용하고 resource server와 authorization server가 집행하는 구체적인 접근 scope와 기간을 나타냅니다.

token은 인가 정보를 조회하는 데 사용하는 식별자를 나타낼 수도 있고, 검증 가능한 방식으로 인가 정보 자체를 담을 수도 있습니다(즉, 데이터와 서명으로 이루어진 token 문자열). client가 token을 사용하려면 추가 인증 자격 증명이 필요할 수도 있으며, 이는 이 명세의 범위를 벗어납니다.

access token은 서로 다른 인가 수단(예: 사용자 이름과 비밀번호)을 resource server가 이해하는 단일 token으로 대체하는 추상화 계층을 제공합니다. 이러한 추상화를 통해 access token을 얻는 데 사용한 authorization grant보다 더 제한적인 access token을 발급할 수 있으며, resource server가 다양한 인증 방법을 이해해야 할 필요도 없앨 수 있습니다.

access token은 resource server의 보안 요구 사항에 따라 형식, 구조, 활용 방법(예: 암호학적 속성)이 다를 수 있습니다. access token의 속성과 protected resource에 접근하는 데 사용하는 방법은 이 명세의 범위를 벗어나며, [RFC6750] 같은 동반 명세에서 정의합니다.

1.5. Refresh Token

refresh token은 access token을 얻는 데 사용하는 자격 증명입니다. authorization server가 client에 발급하며, 현재 access token이 유효하지 않게 되거나 만료되었을 때 새 access token을 얻거나, 동일하거나 더 좁은 scope의 access token을 추가로 얻는 데 사용합니다(access token의 수명이 resource owner가 허용한 것보다 짧거나 권한이 적을 수도 있습니다). refresh token 발급은 authorization server의 재량에 따른 선택 사항입니다. authorization server가 refresh token을 발급한다면, access token을 발급할 때 함께 포함합니다(즉, 그림 1의 (D) 단계).

refresh token은 resource owner가 client에 부여한 인가를 나타내는 문자열입니다. 이 문자열은 일반적으로 client가 그 내용을 해석할 수 없는 불투명한 값입니다. token이 나타내는 식별자는 인가 정보를 조회하는 데 사용됩니다. access token과 달리 refresh token은 authorization server에서만 사용하도록 의도되었으며, resource server로는 결코 전송되지 않습니다.

  +--------+                                           +---------------+
  |        |--(A)------- Authorization Grant --------->|               |
  |        |                                           |               |
  |        |<-(B)----------- Access Token -------------|               |
  |        |               & Refresh Token             |               |
  |        |                                           |               |
  |        |                            +----------+   |               |
  |        |--(C)---- Access Token ---->|          |   |               |
  |        |                            |          |   |               |
  |        |<-(D)- Protected Resource --| Resource |   | Authorization |
  | Client |                            |  Server  |   |     Server    |
  |        |--(E)---- Access Token ---->|          |   |               |
  |        |                            |          |   |               |
  |        |<-(F)- Invalid Token Error -|          |   |               |
  |        |                            +----------+   |               |
  |        |                                           |               |
  |        |--(G)----------- Refresh Token ----------->|               |
  |        |                                           |               |
  |        |<-(H)----------- Access Token -------------|               |
  +--------+           & Optional Refresh Token        +---------------+

그림 2에 나타낸 흐름은 다음 단계를 포함합니다.

(A) client는 authorization server에 자신을 인증하고 authorization grant를 제시하여 access token을 요청합니다.

(B) authorization server는 client를 인증하고 authorization grant의 유효성을 검증하며, 유효하면 access token과 refresh token을 발급합니다.

(C) client는 access token을 제시하여 resource server에 protected resource를 요청합니다.

(D) resource server는 access token의 유효성을 검증하고, 유효하면 요청을 처리합니다.

(E) access token이 만료될 때까지 (C) 및 (D) 단계를 반복합니다. client가 access token이 만료되었음을 알고 있으면 (G) 단계로 건너뛰고, 그렇지 않으면 protected resource를 다시 요청합니다.

(F) access token이 유효하지 않으므로 resource server는 유효하지 않은 token 오류를 반환합니다.

(G) client는 authorization server에 자신을 인증하고 refresh token을 제시하여 새 access token을 요청합니다. client 인증 요구 사항은 client 유형과 authorization server의 정책에 따라 정해집니다.

(H) authorization server는 client를 인증하고 refresh token의 유효성을 검증하며, 유효하면 새 access token을 발급합니다(선택적으로 새 refresh token도 발급합니다).

Section 7에서 설명하듯이 (C), (D), (E), (F) 단계는 이 명세의 범위를 벗어납니다.

1.6. TLS 버전

이 명세에서 Transport Layer Security(TLS)를 사용할 때마다, 적절한 TLS 버전(또는 여러 버전)은 보급 현황과 알려진 보안 취약점에 따라 시간이 지나면서 달라집니다. 이 문서 작성 시점에서 TLS 버전 1.2 [RFC5246]가 최신 버전이지만, 보급 기반이 매우 제한적이며 구현에 쉽게 이용하지 못할 수도 있습니다. TLS 버전 1.0 [RFC2246]은 가장 널리 보급된 버전으로, 가장 폭넓은 상호운용성을 제공할 것입니다.

구현은 자체 보안 요구 사항을 충족하는 추가적인 전송 계층 보안 메커니즘도 지원할 수 있습니다(MAY).

1.7. HTTP 리디렉션

이 명세는 HTTP 리디렉션을 광범위하게 사용하며, 이를 통해 client나 authorization server가 resource owner의 user-agent를 다른 목적지로 보냅니다. 이 명세의 예에서는 HTTP 302 상태 코드 사용을 보여 주지만, user-agent를 통해 이 리디렉션을 수행할 수 있는 다른 어떤 방법도 허용하며, 이는 구현 세부 사항으로 간주합니다.

1.8. 상호운용성

OAuth 2.0은 보안 속성이 명확하게 정의된 풍부한 authorization framework를 제공합니다. 그러나 선택적 구성 요소가 많고 기능이 풍부하며 확장성이 매우 높은 프레임워크이므로, 이 명세만으로는 서로 상호운용되지 않는 다양한 구현이 만들어질 가능성이 큽니다.

또한 이 명세는 몇몇 필수 구성 요소(예: client 등록, authorization server의 기능, endpoint 검색)를 부분적으로 또는 전적으로 정의하지 않은 채 남겨 둡니다. 이러한 구성 요소가 없으면 상호 운용을 위해서는 특정 authorization server와 resource server에 맞춰 client를 수동으로 개별 설정해야 합니다.

이 framework는 향후 작업에서 웹 규모의 완전한 상호 운용성을 달성하는 데 필요한 규범적 profile과 확장을 정의할 것이라는 명확한 기대를 바탕으로 설계되었습니다.

1.9. 표기 규약

이 명세에서 사용하는 핵심 단어 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", "OPTIONAL"은 [RFC2119]에 설명된 대로 해석해야 합니다.

이 명세는 [RFC5234]의 Augmented Backus-Naur Form (ABNF) 표기법을 사용합니다. 또한 "Uniform Resource Identifier (URI): Generic Syntax" [RFC3986]에서 URI-reference 규칙을 가져와 포함합니다.

일부 보안 관련 용어는 [RFC4949]에서 정의한 의미로 이해해야 합니다. 이러한 용어에는 "attack", "authentication", "authorization", "certificate", "confidentiality", "credential", "encryption", "identity", "sign", "signature", "trust", "validate", "verify" 등이 포함되며, 이에 국한되지 않습니다.

별도로 명시하지 않는 한 모든 protocol parameter 이름과 값은 대소문자를 구분합니다.

2. Client 등록

protocol을 시작하기 전에 client는 authorization server에 등록합니다. client가 authorization server에 등록하는 방식은 이 명세의 범위를 벗어나지만, 일반적으로 최종 사용자가 HTML 등록 양식과 상호 작용하는 과정이 수반됩니다.

client 등록에 client와 authorization server 사이의 직접적인 상호 작용이 필요한 것은 아닙니다. authorization server가 지원하는 경우, 등록 시 신뢰를 확립하고 필요한 client 속성(예: redirection URI, client 유형)을 얻기 위해 다른 수단을 이용할 수 있습니다. 예를 들어 자체 발급 또는 제3자 발급 assertion을 사용하거나, authorization server가 신뢰할 수 있는 채널을 통해 client 검색을 수행하는 방식으로 등록할 수 있습니다.

client를 등록할 때 client 개발자는 다음 사항을 이행해야 합니다(SHALL).

o 2.1절에 설명된 client 유형을 지정합니다.

o 3.1.2절에 설명된 client redirection URI를 제공합니다. 그리고

o authorization server가 요구하는 기타 정보(예: application 이름, 웹사이트, 설명, 로고 이미지, 법적 약관 동의)를 포함합니다.

2.1. Client 유형

OAuth는 authorization server와 안전하게 인증할 수 있는 능력(즉, client credentials의 기밀성을 유지할 수 있는 능력)을 기준으로 두 가지 client 유형을 정의합니다.

confidential 자신의 credentials에 대한 기밀성을 유지할 수 있거나(예: client credentials에 대한 접근이 제한된 안전한 서버에 구현된 client), 다른 수단으로 안전한 client 인증을 수행할 수 있는 client입니다.

public 자신의 credentials에 대한 기밀성을 유지할 수 없고(예: 설치된 native application이나 웹 브라우저 기반 application처럼 resource owner가 사용하는 기기에서 실행되는 client), 다른 어떤 수단으로도 안전한 client 인증을 수행할 수 없는 client입니다.

client 유형은 authorization server가 정의한 안전한 인증의 기준과 client credentials의 허용 가능한 노출 수준에 따라 지정됩니다. authorization server는 client 유형에 대해 임의로 가정하지 않는 것이 좋습니다(SHOULD NOT).

client는 각각 서로 다른 client 유형과 보안 맥락을 지닌 분산 구성 요소들의 집합으로 구현될 수 있습니다(예: confidential 서버 기반 구성 요소와 public 브라우저 기반 구성 요소를 모두 갖춘 분산 client). authorization server가 이러한 client를 지원하지 않거나 등록에 관한 지침을 제공하지 않는 경우, client는 각 구성 요소를 별도의 client로 등록하는 것이 좋습니다(SHOULD).

이 명세는 다음 client profile을 중심으로 설계되었습니다.

web application web application은 웹 서버에서 실행되는 confidential client(기밀 클라이언트)입니다. resource owner는 자신이 사용하는 기기의 user-agent에 렌더링되는 HTML 사용자 인터페이스를 통해 client에 접근합니다. client credentials와 client에 발급된 모든 access token은 웹 서버에 저장되며, resource owner에게 노출되지 않고 resource owner가 접근할 수도 없습니다.

user-agent-based application user-agent-based application은 client 코드를 웹 서버에서 다운로드하여 resource owner가 사용하는 기기의 user-agent(예: 웹 브라우저) 안에서 실행하는 public client(공개 클라이언트)입니다. resource owner는 protocol 데이터와 credentials에 쉽게 접근할 수 있으며, 흔히 그 내용을 볼 수도 있습니다. 이러한 application은 user-agent 안에 존재하므로 authorization을 요청할 때 user-agent의 기능을 원활하게 활용할 수 있습니다.

native application native application은 resource owner가 사용하는 기기에 설치되어 실행되는 public client입니다. resource owner는 protocol 데이터와 credentials에 접근할 수 있습니다. application에 포함된 모든 client 인증 credentials는 추출할 수 있다고 가정합니다. 반면 access token이나 refresh token처럼 동적으로 발급되는 credentials는 허용 가능한 수준의 보호를 받을 수 있습니다. 최소한 이러한 credentials는 application이 상호 작용할 수 있는 악의적인 서버로부터 보호됩니다. 일부 플랫폼에서는 이러한 credentials를 동일한 기기에 있는 다른 application으로부터 보호할 수도 있습니다.

2.2. Client identifier

authorization server는 등록된 client에 client identifier를 발급합니다. 이는 client가 제공한 등록 정보를 나타내는 고유한 문자열입니다. client identifier는 비밀 정보가 아니며 resource owner에게 노출됩니다. 이를 client 인증에 단독으로 사용해서는 안 됩니다(MUST NOT). client identifier는 해당 authorization server 내에서 고유합니다.

이 명세는 client identifier 문자열의 크기를 정의하지 않습니다. client는 식별자의 크기에 대해 임의로 가정하지 않는 것이 좋습니다. authorization server는 자신이 발급하는 모든 식별자의 크기를 문서화하는 것이 좋습니다(SHOULD).

2.3. Client 인증

client 유형이 confidential이면 client와 authorization server는 authorization server의 보안 요구 사항에 적합한 client 인증 방식을 정합니다. authorization server는 자신의 보안 요구 사항을 충족하는 어떤 형태의 client 인증이든 허용할 수 있습니다(MAY).

confidential client는 일반적으로 authorization server와의 인증에 사용할 client credentials 집합(예: 비밀번호, public/private key 쌍)을 발급받거나 설정합니다.

authorization server는 public client와 client 인증 방식을 정할 수 있습니다(MAY). 그러나 authorization server는 client를 식별할 목적으로 public client 인증에 의존해서는 안 됩니다(MUST NOT).

client는 각각의 요청에서 두 가지 이상의 인증 방식을 사용해서는 안 됩니다(MUST NOT).

2.3.1. Client 비밀번호

client 비밀번호를 보유한 client는 authorization server와 인증하기 위해 [RFC2617]에 정의된 HTTP Basic 인증 scheme을 사용할 수 있습니다(MAY). client identifier는 부록 B에 따른 "application/x-www-form-urlencoded" 인코딩 알고리즘으로 인코딩하며, 그 인코딩된 값을 username으로 사용합니다. client 비밀번호도 동일한 알고리즘으로 인코딩하여 password로 사용합니다. authorization server는 client 비밀번호를 발급받은 client를 인증하기 위해 HTTP Basic 인증 scheme을 지원해야 합니다(MUST).

예를 들면 다음과 같습니다(가독성을 위해서만 줄바꿈을 추가했습니다).

     Authorization: Basic czZCaGRSa3F0Mzo3RmpmcDBaQnIxS3REUmJuZlZkbUl3

또는 authorization server는 다음 parameter를 사용하여 요청 본문에 client credentials를 포함하는 방식을 지원할 수 있습니다(MAY).

client_id 필수(REQUIRED). 2.2절에 설명된 등록 과정에서 client에 발급된 client identifier입니다.

client_secret 필수(REQUIRED). client secret입니다. client secret이 빈 문자열인 경우 client는 이 parameter를 생략할 수 있습니다(MAY).

두 parameter를 사용해 요청 본문에 client credentials를 포함하는 방식은 권장하지 않습니다(NOT RECOMMENDED). 이 방식은 HTTP Basic 인증 scheme(또는 다른 비밀번호 기반 HTTP 인증 scheme)을 직접 사용할 수 없는 client로 제한하는 것이 좋습니다(SHOULD). 이 parameter들은 요청 본문으로만 전송할 수 있으며, 요청 URI에 포함해서는 안 됩니다(MUST NOT).

예를 들어 본문 parameter를 사용하여 access token을 갱신하는 요청(6절)은 다음과 같습니다(가독성을 위해서만 줄바꿈을 추가했습니다).

     POST /token HTTP/1.1
     Host: server.example.com
     Content-Type: application/x-www-form-urlencoded

     grant_type=refresh_token&refresh_token=tGzv3JOkF0XG5Qx2TlKWIA
     &client_id=s6BhdRkqt3&client_secret=7Fjfp0ZBr1KtDRbnfVdmIw

authorization server는 비밀번호 인증을 사용하는 요청을 전송할 때 1.6절에 설명된 TLS 사용을 요구해야 합니다(MUST).

이 client 인증 방식에는 비밀번호가 사용되므로, authorization server는 이 방식을 사용하는 모든 endpoint를 brute force attack으로부터 보호해야 합니다(MUST).

2.3.2. 기타 인증 방식

authorization server는 자신의 보안 요구 사항에 부합하는 적절한 HTTP 인증 scheme을 지원할 수 있습니다(MAY). 다른 인증 방식을 사용할 때 authorization server는 client identifier(등록 레코드)와 인증 scheme 사이의 매핑을 정의해야 합니다(MUST).

2.4. 등록되지 않은 Client

이 명세는 등록되지 않은 client의 사용을 배제하지 않습니다. 그러나 이러한 client의 사용은 이 명세의 범위를 벗어나며, 추가적인 보안 분석과 상호 운용성에 미치는 영향에 대한 검토가 필요합니다.

3. Protocol endpoint

authorization 과정에서는 authorization server의 두 endpoint(HTTP resource)를 사용합니다.

o Authorization endpoint - client가 user-agent redirection을 통해 resource owner로부터 authorization을 얻는 데 사용합니다.

o Token endpoint - client가 authorization grant를 access token으로 교환하는 데 사용하며, 일반적으로 client 인증이 수반됩니다.

이와 함께 client의 endpoint 하나도 사용합니다.

o Redirection endpoint - authorization server가 resource owner의 user-agent를 통해 authorization credentials를 포함하는 응답을 client에 반환하는 데 사용합니다.

모든 authorization grant 유형이 두 endpoint를 모두 사용하는 것은 아닙니다. 확장 grant 유형은 필요에 따라 추가 endpoint를 정의할 수 있습니다(MAY).

3.1. Authorization endpoint

authorization endpoint는 resource owner와 상호 작용하고 authorization grant를 얻는 데 사용됩니다. authorization server는 먼저 resource owner의 신원을 확인해야 합니다(MUST). authorization server가 resource owner를 인증하는 방법(예: username과 password를 사용하는 로그인, session cookie)은 이 명세의 범위를 벗어납니다.

client가 authorization endpoint의 위치를 알아내는 방식은 이 명세의 범위를 벗어나지만, 일반적으로 그 위치는 서비스 문서에 제공됩니다.

endpoint URI는 부록 B에 따른 "application/x-www-form-urlencoded" 형식의 query component([RFC3986] 3.4절)를 포함할 수 있으며(MAY), query parameter를 추가할 때 이 component를 유지해야 합니다(MUST). endpoint URI에는 fragment component를 포함해서는 안 됩니다(MUST NOT).

authorization endpoint로 보내는 요청은 사용자 인증과 (HTTP 응답에서의) 평문 credentials 전송을 수반하므로, authorization server는 authorization endpoint로 요청을 전송할 때 1.6절에 설명된 TLS 사용을 요구해야 합니다(MUST).

authorization server는 authorization endpoint에서 HTTP "GET" 메서드[RFC2616] 사용을 지원해야 하며(MUST), "POST" 메서드 사용도 지원할 수 있습니다(MAY).

값 없이 전송된 매개변수는 요청에서 생략된 것으로 처리해야 합니다(MUST). authorization server는 인식하지 못하는 요청 매개변수를 무시해야 합니다(MUST). 요청 및 응답 매개변수는 두 번 이상 포함해서는 안 됩니다(MUST NOT).

3.1.1. 응답 유형

authorization endpoint는 authorization code grant 유형과 implicit grant 유형의 흐름에서 사용됩니다. client는 다음 매개변수를 사용하여 원하는 grant 유형을 authorization server에 알립니다.

response_type 필수입니다(REQUIRED). 값은 Section 4.1.1에 설명된 authorization code를 요청하는 "code", Section 4.2.1에 설명된 access token(implicit grant)을 요청하는 "token", 또는 Section 8.4에 설명된 등록된 확장 값 중 하나여야 합니다(MUST).

확장 응답 유형에는 공백(%x20)으로 구분된 값 목록이 포함될 수 있으며(MAY), 값의 순서는 중요하지 않습니다(예를 들어 응답 유형 "a b"는 "b a"와 같습니다). 이러한 복합 응답 유형의 의미는 각각의 명세에서 정의합니다.

인가 요청에 "response_type" 매개변수가 없거나 응답 유형을 이해할 수 없는 경우, authorization server는 Section 4.1.2.1에 설명된 오류 응답을 반환해야 합니다(MUST).

3.1.2. redirection endpoint

resource owner와의 상호 작용을 마친 후, authorization server는 resource owner의 user-agent를 다시 client로 보냅니다. authorization server는 client 등록 과정이나 인가 요청 시 authorization server와 미리 정해 둔 client의 redirection endpoint로 user-agent를 리디렉션합니다.

redirection endpoint URI는 [RFC3986] Section 4.3에 정의된 절대 URI여야 합니다(MUST). endpoint URI에는 Appendix B에 따른 "application/x-www-form-urlencoded" 형식의 쿼리 구성 요소([RFC3986] Section 3.4)가 포함될 수 있으며(MAY), 쿼리 매개변수를 추가할 때 이 구성 요소를 유지해야 합니다(MUST). endpoint URI에는 fragment 구성 요소를 포함해서는 안 됩니다(MUST NOT).

3.1.2.1. endpoint 요청의 기밀성

요청된 응답 유형이 "code" 또는 "token"이거나 리디렉션 요청으로 인해 개방된 네트워크를 통해 민감한 자격 증명이 전송되는 경우, redirection endpoint는 Section 1.6에 설명된 TLS 사용을 요구하는 것이 좋습니다(SHOULD). 이 명세는 TLS 사용을 의무화하지 않습니다. 이 문서 작성 당시 client에 TLS 배포를 요구하는 것은 많은 client 개발자에게 상당한 장벽이기 때문입니다. TLS를 사용할 수 없는 경우, authorization server는 리디렉션하기 전에 안전하지 않은 endpoint에 대해 resource owner에게 경고하는 것이 좋습니다(SHOULD). 예를 들어 인가 요청 중에 메시지를 표시할 수 있습니다.

전송 계층 보안이 없으면 client와 해당 client가 접근하도록 인가받은 protected resource의 보안에 심각한 영향을 줄 수 있습니다. client가 인가 과정을 위임된 최종 사용자 인증의 한 형태로 사용하는 경우(예: 제3자 로그인 서비스)에는 전송 계층 보안의 사용이 특히 중요합니다.

3.1.2.2. 등록 요구 사항

authorization server는 다음 client가 자신의 redirection endpoint를 등록하도록 요구해야 합니다(MUST).

o public client.

o implicit grant 유형을 사용하는 confidential client.

authorization server는 모든 client가 authorization endpoint를 사용하기 전에 자신의 redirection endpoint를 등록하도록 요구하는 것이 좋습니다(SHOULD).

authorization server는 client가 완전한 리디렉션 URI를 제공하도록 요구하는 것이 좋습니다(SHOULD). client는 요청별 맞춤 설정을 위해 "state" 요청 매개변수를 사용할 수 있습니다(MAY). 완전한 리디렉션 URI의 등록을 요구할 수 없다면, authorization server는 URI의 scheme, authority, path를 등록하도록 요구하는 것이 좋습니다(SHOULD). 이 경우 client는 인가를 요청할 때 리디렉션 URI의 쿼리 구성 요소만 동적으로 변경할 수 있습니다.

authorization server는 client가 여러 redirection endpoint를 등록하도록 허용할 수 있습니다(MAY).

리디렉션 URI 등록 요구 사항이 없으면, Section 10.15에 설명된 것처럼 공격자가 authorization endpoint를 open redirector로 사용할 수 있게 될 수 있습니다.

3.1.2.3. 동적 구성

여러 리디렉션 URI가 등록되어 있거나, 리디렉션 URI의 일부만 등록되어 있거나, 리디렉션 URI가 등록되어 있지 않은 경우, client는 "redirect_uri" 요청 매개변수를 사용하여 인가 요청에 리디렉션 URI를 포함해야 합니다(MUST).

인가 요청에 리디렉션 URI가 포함되어 있고 등록된 리디렉션 URI가 있는 경우, authorization server는 [RFC3986] Section 6에 정의된 방식으로 수신한 값을 등록된 리디렉션 URI(또는 URI 구성 요소) 중 적어도 하나와 비교하여 일치하는지 확인해야 합니다(MUST). client 등록에 전체 리디렉션 URI가 포함되어 있었다면, authorization server는 [RFC3986] Section 6.2.1에 정의된 단순 문자열 비교를 사용하여 두 URI를 비교해야 합니다(MUST).

3.1.2.4. 유효하지 않은 endpoint

리디렉션 URI의 누락, 유효하지 않음 또는 불일치로 인해 인가 요청 검증이 실패하면, authorization server는 resource owner에게 오류를 알리는 것이 좋으며(SHOULD), user-agent를 유효하지 않은 리디렉션 URI로 자동 리디렉션해서는 안 됩니다(MUST NOT).

3.1.2.5. endpoint 콘텐츠

client의 endpoint로 보내는 리디렉션 요청은 일반적으로 user-agent가 처리하는 HTML 문서 응답을 생성합니다. 리디렉션 요청의 결과로 HTML 응답이 직접 제공되면, HTML 문서에 포함된 모든 스크립트는 리디렉션 URI와 그 안에 있는 자격 증명에 완전히 접근할 수 있는 상태로 실행됩니다.

client는 redirection endpoint 응답에 제3자 스크립트(예: 제3자 분석, 소셜 플러그인, 광고 네트워크)를 포함하지 않는 것이 좋습니다(SHOULD NOT). 대신 URI에서 자격 증명을 추출하고, 자격 증명을 URI나 그 밖의 위치에 노출하지 않은 채 user-agent를 다른 endpoint로 다시 리디렉션하는 것이 좋습니다(SHOULD). 제3자 스크립트가 포함되는 경우, client는 URI에서 자격 증명을 추출하고 제거하는 자신의 스크립트가 먼저 실행되도록 보장해야 합니다(MUST).

3.2. token endpoint

client는 자신의 authorization grant 또는 refresh token을 제시하여 access token을 얻기 위해 token endpoint를 사용합니다. token endpoint는 implicit grant 유형을 제외한 모든 authorization grant에서 사용됩니다. implicit grant 유형에서는 access token이 직접 발급되기 때문입니다.

client가 token endpoint의 위치를 얻는 방법은 이 명세의 범위를 벗어나지만, 그 위치는 일반적으로 서비스 문서에서 제공됩니다.

endpoint URI에는 Appendix B에 따른 "application/x-www-form-urlencoded" 형식의 쿼리 구성 요소([RFC3986] Section 3.4)가 포함될 수 있으며(MAY), 쿼리 매개변수를 추가할 때 이 구성 요소를 유지해야 합니다(MUST). endpoint URI에는 fragment 구성 요소를 포함해서는 안 됩니다(MUST NOT).

token endpoint에 대한 요청은 HTTP 요청과 응답에서 평문 자격 증명의 전송을 수반하므로, authorization server는 token endpoint로 요청을 보낼 때 Section 1.6에 설명된 TLS 사용을 요구해야 합니다(MUST).

client는 access token을 요청할 때 HTTP "POST" 메서드를 사용해야 합니다(MUST).

값 없이 전송된 매개변수는 요청에서 생략된 것으로 처리해야 합니다(MUST). authorization server는 인식하지 못하는 요청 매개변수를 무시해야 합니다(MUST). 요청 및 응답 매개변수는 두 번 이상 포함해서는 안 됩니다(MUST NOT).

3.2.1. client 인증

confidential client 또는 client credentials를 발급받은 그 밖의 client는 token endpoint에 요청할 때 Section 2.3에 설명된 대로 authorization server에 자신을 인증해야 합니다(MUST). client 인증은 다음 용도로 사용됩니다.

o refresh token과 authorization code를 발급 대상 client에 결속되도록 강제합니다. authorization code가 안전하지 않은 채널을 통해 redirection endpoint로 전송되거나 리디렉션 URI가 완전히 등록되어 있지 않은 경우에는 client 인증이 매우 중요합니다.

o 침해된 client를 비활성화하거나 해당 client의 자격 증명을 변경하여 침해로부터 복구하고, 이로써 공격자가 도난당한 refresh token을 악용하지 못하게 합니다. client credentials 한 세트를 변경하는 것은 refresh token 전체를 폐기하는 것보다 훨씬 빠릅니다.

o 주기적인 자격 증명 교체를 요구하는 인증 관리 모범 사례를 구현합니다. refresh token 전체를 교체하는 것은 어려울 수 있지만, client credentials 한 세트를 교체하는 것은 훨씬 쉽습니다.

client는 token endpoint로 요청을 보낼 때 "client_id" 요청 매개변수를 사용하여 자신을 식별할 수 있습니다(MAY). token endpoint로 보내는 "grant_type"이 "authorization_code"인 요청에서, 인증되지 않은 client는 다른 "client_id"를 가진 client를 위한 코드를 실수로 받아들이지 않도록 자신의 "client_id"를 보내야 합니다(MUST). 이는 인증 코드의 대체로부터 client를 보호합니다. (protected resource에 추가적인 보안을 제공하지는 않습니다.)

3.3. access token의 scope

authorization endpoint와 token endpoint에서는 client가 "scope" 요청 매개변수를 사용하여 접근 요청의 scope를 지정할 수 있습니다. 이에 대해 authorization server는 "scope" 응답 매개변수를 사용하여 발급된 access token의 scope를 client에 알립니다.

scope 매개변수의 값은 공백으로 구분된 대소문자 구별 문자열 목록으로 표현됩니다. 이 문자열은 authorization server가 정의합니다. 값에 공백으로 구분된 여러 문자열이 포함된 경우 순서는 중요하지 않으며, 각 문자열은 요청한 scope에 추가적인 접근 범위를 더합니다.

     scope       = scope-token *( SP scope-token )
     scope-token = 1*( %x21 / %x23-5B / %x5D-7E )

authorization server는 자신의 정책이나 resource owner의 지시에 따라 client가 요청한 scope의 전부 또는 일부를 무시할 수 있습니다(MAY). 발급된 access token의 scope가 client가 요청한 것과 다르면, authorization server는 실제로 부여된 scope를 client에 알리기 위해 "scope" 응답 매개변수를 포함해야 합니다(MUST).

client가 인가를 요청할 때 scope 매개변수를 생략하면, authorization server는 미리 정의된 기본값으로 요청을 처리하거나 유효하지 않은 scope임을 나타내며 요청을 실패시켜야 합니다(MUST). authorization server는 자신의 scope 요구 사항과 기본값(정의되어 있는 경우)을 문서화하는 것이 좋습니다(SHOULD).

4. 인가 받기

access token을 요청하기 위해 client는 resource owner로부터 인가를 받습니다. 인가는 authorization grant의 형태로 표현되며, client는 이를 사용하여 access token을 요청합니다. OAuth는 authorization code, implicit, resource owner password credentials, client credentials라는 네 가지 grant 유형을 정의합니다. 또한 추가 grant 유형을 정의하기 위한 확장 메커니즘도 제공합니다.

4.1. authorization code grant

authorization code grant 유형은 access token과 refresh token을 모두 얻는 데 사용되며, confidential client에 최적화되어 있습니다. 이는 리디렉션 기반 흐름이므로, client는 resource owner의 user-agent(일반적으로 웹 브라우저)와 상호 작용할 수 있어야 하며 authorization server에서 리디렉션을 통해 들어오는 요청을 수신할 수 있어야 합니다.

     +----------+
     | Resource |
     |   Owner  |
     |          |
     +----------+
          ^
          |
         (B)
     +----|-----+          Client Identifier      +---------------+
     |         -+----(A)-- & Redirection URI ---->|               |
     |  User-   |                                 | Authorization |
     |  Agent  -+----(B)-- User authenticates --->|     Server    |
     |          |                                 |               |
     |         -+----(C)-- Authorization Code ---<|               |
     +-|----|---+                                 +---------------+
       |    |                                         ^      v
      (A)  (C)                                        |      |
       |    |                                         |      |
       ^    v                                         |      |
     +---------+                                      |      |
     |         |>---(D)-- Authorization Code ---------'      |
     |  Client |          & Redirection URI                  |
     |         |                                             |
     |         |<---(E)----- Access Token -------------------'
     +---------+       (w/ Optional Refresh Token)

참고: (A), (B), (C) 단계를 나타내는 선은 user-agent를 통과하면서 두 부분으로 나뉩니다.

그림 3에 나타낸 흐름은 다음 단계를 포함합니다.

(A) client는 resource owner의 user-agent를 authorization endpoint로 보내 흐름을 시작합니다. client는 자신의 client identifier, 요청하는 scope, 로컬 상태, 그리고 접근이 허용되거나 거부되면 authorization server가 user-agent를 돌려보낼 redirection URI를 포함합니다.

(B) authorization server는 user-agent를 통해 resource owner를 인증하고, resource owner가 client의 접근 요청을 허용하는지 거부하는지 확인합니다.

(C) resource owner가 접근을 허용했다고 가정하면, authorization server는 앞서 요청에 포함되었거나 client 등록 시 제공된 redirection URI를 사용하여 user-agent를 client로 다시 리디렉션합니다. redirection URI에는 authorization code와 client가 앞서 제공한 로컬 상태가 포함됩니다.

(D) client는 이전 단계에서 받은 authorization code를 포함하여 authorization server의 token endpoint에 access token을 요청합니다. 이 요청을 할 때 client는 authorization server에 자신을 인증합니다. client는 검증을 위해 authorization code를 얻는 데 사용한 redirection URI를 포함합니다.

(E) authorization server는 client를 인증하고 authorization code의 유효성을 검증하며, 받은 redirection URI가 (C) 단계에서 client로 리디렉션하는 데 사용한 URI와 일치하는지 확인합니다. 유효하다면 authorization server는 access token과 선택적으로 refresh token을 응답으로 반환합니다.

4.1.1. Authorization 요청

client는 부록 B에 따라 "application/x-www-form-urlencoded" 형식으로 다음 매개변수를 authorization endpoint URI의 query 구성요소에 추가하여 요청 URI를 구성합니다.

response_type REQUIRED. 값은 "code"로 설정해야 합니다(MUST).

client_id REQUIRED. 2.2절에서 설명하는 client identifier입니다.

redirect_uri OPTIONAL. 3.1.2절에서 설명합니다.

scope OPTIONAL. 3.3절에서 설명하는 접근 요청의 scope입니다.

state RECOMMENDED. 요청과 콜백 사이에서 상태를 유지하기 위해 client가 사용하는 불투명한 값입니다. authorization server는 user-agent를 client로 다시 리디렉션할 때 이 값을 포함합니다. 10.12절에서 설명하는 cross-site request forgery를 방지하기 위해 이 매개변수를 사용하는 것이 좋습니다(SHOULD).

client는 HTTP 리디렉션 응답을 사용하거나 user-agent를 통해 이용할 수 있는 다른 수단으로 resource owner를 구성된 URI로 보냅니다.

예를 들어 client는 user-agent가 TLS를 사용하여 다음 HTTP 요청을 하도록 지시합니다(추가된 줄바꿈은 표시 목적일 뿐입니다).

    GET /authorize?response_type=code&client_id=s6BhdRkqt3&state=xyz
        &redirect_uri=https%3A%2F%2Fclient%2Eexample%2Ecom%2Fcb HTTP/1.1
    Host: server.example.com

authorization server는 필요한 매개변수가 모두 존재하고 유효한지 확인하기 위해 요청을 검증합니다. 요청이 유효하면 authorization server는 resource owner를 인증하고, resource owner에게 묻거나 다른 수단으로 승인을 확인하여 인가 결정을 얻습니다.

결정이 내려지면 authorization server는 HTTP 리디렉션 응답을 사용하거나 user-agent를 통해 이용할 수 있는 다른 수단으로 user-agent를 제공된 client redirection URI로 보냅니다.

4.1.2. Authorization 응답

resource owner가 접근 요청을 허용하면 authorization server는 authorization code를 발급하고, 부록 B에 따라 "application/x-www-form-urlencoded" 형식으로 다음 매개변수를 redirection URI의 query 구성요소에 추가하여 client에 전달합니다.

code REQUIRED. authorization server가 생성한 authorization code입니다. 유출 위험을 줄이기 위해 authorization code는 발급 후 짧은 시간 안에 만료되어야 합니다(MUST). authorization code의 최대 유효 기간은 10분으로 하는 것이 권장됩니다(RECOMMENDED). client는 authorization code를 두 번 이상 사용해서는 안 됩니다(MUST NOT). authorization code가 두 번 이상 사용되면 authorization server는 해당 요청을 거부해야 하며(MUST), 가능하다면 그 authorization code를 기반으로 이전에 발급한 모든 token을 폐기하는 것이 좋습니다(SHOULD). authorization code는 client identifier 및 redirection URI에 바인딩됩니다.

state client의 authorization 요청에 "state" 매개변수가 있었다면 REQUIRED입니다. client로부터 받은 값과 정확히 같은 값입니다.

예를 들어 authorization server는 다음 HTTP 응답을 보내 user-agent를 리디렉션합니다.

     HTTP/1.1 302 Found
     Location: https://client.example.com/cb?code=SplxlOBeZQQYbYS6WxSbIA
               &state=xyz

client는 인식하지 못하는 응답 매개변수를 무시해야 합니다(MUST). 이 명세는 authorization code 문자열의 크기를 정의하지 않습니다. client는 code 값의 크기를 가정하지 않는 것이 좋습니다. authorization server는 자신이 발급하는 모든 값의 크기를 문서화하는 것이 좋습니다(SHOULD).

4.1.2.1. 오류 응답

redirection URI가 누락되거나 유효하지 않거나 일치하지 않아 요청이 실패한 경우, 또는 client identifier가 누락되거나 유효하지 않은 경우, authorization server는 resource owner에게 오류를 알리는 것이 좋으며(SHOULD), user-agent를 유효하지 않은 redirection URI로 자동 리디렉션해서는 안 됩니다(MUST NOT).

resource owner가 접근 요청을 거부하거나, redirection URI의 누락 또는 유효하지 않음 이외의 이유로 요청이 실패하면 authorization server는 부록 B에 따라 "application/x-www-form-urlencoded" 형식으로 다음 매개변수를 redirection URI의 query 구성요소에 추가하여 client에 알립니다.

error REQUIRED. 다음 중 하나인 단일 ASCII [USASCII] 오류 코드입니다.

invalid_request 요청에 필수 매개변수가 누락되어 있거나, 유효하지 않은 매개변수 값이 포함되어 있거나, 같은 매개변수가 두 번 이상 포함되어 있거나, 그 밖의 형식 오류가 있습니다.

unauthorized_client client는 이 방법으로 authorization code를 요청할 권한이 없습니다.

access_denied resource owner 또는 authorization server가 요청을 거부했습니다.

unsupported_response_type authorization server는 이 방법으로 authorization code를 얻는 것을 지원하지 않습니다.

invalid_scope 요청한 scope가 유효하지 않거나, 알 수 없거나, 형식이 잘못되었습니다.

server_error authorization server에 예상치 못한 상황이 발생하여 요청을 이행하지 못했습니다. (HTTP 리디렉션을 통해서는 500 Internal Server Error HTTP 상태 코드를 client에 반환할 수 없으므로 이 오류 코드가 필요합니다.)

temporarily_unavailable 서버의 일시적인 과부하 또는 유지보수로 인해 authorization server가 현재 요청을 처리할 수 없습니다. (HTTP 리디렉션을 통해서는 503 Service Unavailable HTTP 상태 코드를 client에 반환할 수 없으므로 이 오류 코드가 필요합니다.)

"error" 매개변수의 값에는 %x20-21 / %x23-5B / %x5D-7E 집합에 속하지 않는 문자를 포함해서는 안 됩니다(MUST NOT).

error_description OPTIONAL. client 개발자가 발생한 오류를 이해하는 데 도움이 되도록 추가 정보를 제공하는 사람이 읽을 수 있는 ASCII [USASCII] 텍스트입니다. "error_description" 매개변수의 값에는 %x20-21 / %x23-5B / %x5D-7E 집합에 속하지 않는 문자를 포함해서는 안 됩니다(MUST NOT).

error_uri OPTIONAL. 오류에 관한 정보가 담긴 사람이 읽을 수 있는 웹 페이지를 식별하는 URI로, client 개발자에게 오류에 대한 추가 정보를 제공하는 데 사용합니다. "error_uri" 매개변수의 값은 URI-reference 문법을 따라야 하며(MUST), 따라서 %x21 / %x23-5B / %x5D-7E 집합에 속하지 않는 문자를 포함해서는 안 됩니다(MUST NOT).

state client의 authorization 요청에 "state" 매개변수가 있었다면 REQUIRED입니다. client로부터 받은 값과 정확히 같은 값입니다.

예를 들어 authorization server는 다음 HTTP 응답을 보내 user-agent를 리디렉션합니다.

   HTTP/1.1 302 Found
   Location: https://client.example.com/cb?error=access_denied&state=xyz

4.1.3. Access Token 요청

client는 부록 B에 따른 "application/x-www-form-urlencoded" 형식과 UTF-8 문자 인코딩으로 다음 매개변수를 HTTP 요청의 entity-body에 담아 보내 token endpoint에 요청합니다.

grant_type REQUIRED. 값은 "authorization_code"로 설정해야 합니다(MUST).

code REQUIRED. authorization server로부터 받은 authorization code입니다.

redirect_uri 4.1.1절에서 설명한 것처럼 authorization 요청에 "redirect_uri" 매개변수가 포함되었다면 REQUIRED이며, 두 값은 동일해야 합니다(MUST).

client_id 3.2.1절에서 설명한 방식으로 client가 authorization server에 자신을 인증하지 않는 경우 REQUIRED입니다.

client 유형이 confidential이거나 client가 client credentials를 발급받았거나 다른 인증 요구사항을 부여받았다면, client는 3.2.1절에서 설명한 방식으로 authorization server에 자신을 인증해야 합니다(MUST).

예를 들어 client는 TLS를 사용하여 다음 HTTP 요청을 합니다(추가된 줄바꿈은 표시 목적일 뿐입니다).

     POST /token HTTP/1.1
     Host: server.example.com
     Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW
     Content-Type: application/x-www-form-urlencoded

     grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA
     &redirect_uri=https%3A%2F%2Fclient%2Eexample%2Ecom%2Fcb

authorization server는 다음을 수행해야 합니다(MUST).

o confidential client 또는 client credentials를 발급받았거나 다른 인증 요구사항이 있는 모든 client에 대해 client 인증을 요구합니다.

o client 인증이 포함되어 있으면 client를 인증합니다.

o authorization code가 인증된 confidential client에 발급된 것인지 확인하고, client가 public인 경우에는 그 code가 요청의 "client_id"에 발급된 것인지 확인합니다.

o authorization code가 유효한지 검증합니다. 그리고

o 4.1.1절에서 설명한 것처럼 최초 authorization 요청에 "redirect_uri" 매개변수가 포함되었다면 이번 요청에도 "redirect_uri" 매개변수가 있는지 확인하고, 포함되어 있으면 두 값이 동일한지 확인합니다.

4.1.4. Access Token 응답

access token 요청이 유효하고 인가되었다면 authorization server는 5.1절에서 설명한 것처럼 access token과 선택적으로 refresh token을 발급합니다. 요청의 client 인증이 실패했거나 요청이 유효하지 않다면 authorization server는 5.2절에서 설명하는 오류 응답을 반환합니다.

성공 응답의 예:

     HTTP/1.1 200 OK
     Content-Type: application/json;charset=UTF-8
     Cache-Control: no-store
     Pragma: no-cache

     {
       "access_token":"2YotnFZFEjr1zCsicMWpAA",
       "token_type":"example",
       "expires_in":3600,
       "refresh_token":"tGzv3JOkF0XG5Qx2TlKWIA",
       "example_parameter":"example_value"
     }

4.2. Implicit Grant

implicit grant 유형은 access token을 얻는 데 사용되며(refresh token 발급은 지원하지 않습니다), 특정 redirection URI를 운영하는 것으로 알려진 public client에 최적화되어 있습니다. 이러한 client는 일반적으로 JavaScript와 같은 스크립트 언어를 사용하여 브라우저 안에 구현됩니다.

이는 리디렉션 기반 흐름이므로 client는 resource owner의 user-agent(일반적으로 웹 브라우저)와 상호작용할 수 있어야 하고, authorization server가 보내는 요청을 리디렉션을 통해 수신할 수 있어야 합니다.

client가 인가와 access token을 각각 별도의 요청으로 얻는 authorization code grant 유형과 달리, 이 흐름에서는 client가 authorization 요청의 결과로 access token을 받습니다.

implicit grant 유형은 client 인증을 포함하지 않으며, resource owner의 참여와 redirection URI의 등록에 의존합니다. access token이 redirection URI에 인코딩되므로 resource owner뿐 아니라 동일한 기기에 있는 다른 애플리케이션에도 노출될 수 있습니다.

     +----------+
     | Resource |
     |  Owner   |
     |          |
     +----------+
          ^
          |
         (B)
     +----|-----+          Client Identifier     +---------------+
     |         -+----(A)-- & Redirection URI --->|               |
     |  User-   |                                | Authorization |
     |  Agent  -|----(B)-- User authenticates -->|     Server    |
     |          |                                |               |
     |          |<---(C)--- Redirection URI ----<|               |
     |          |          with Access Token     +---------------+
     |          |            in Fragment
     |          |                                +---------------+
     |          |----(D)--- Redirection URI ---->|   Web-Hosted  |
     |          |          without Fragment      |     Client    |
     |          |                                |    Resource   |
     |     (F)  |<---(E)------- Script ---------<|               |
     |          |                                +---------------+
     +-|--------+
       |    |
      (A)  (G) Access Token
       |    |
       ^    v
     +---------+
     |         |
     |  Client |
     |         |
     +---------+

참고: 단계 (A)와 (B)를 나타내는 선은 user-agent를 통과하면서 두 부분으로 나뉩니다.

그림 4에 나타낸 흐름은 다음 단계로 구성됩니다.

(A) client는 resource owner의 user-agent를 authorization endpoint로 보내 흐름을 시작합니다. client는 자신의 client identifier, 요청하는 scope, 로컬 상태, 그리고 접근이 허용되거나 거부되면 authorization server가 user-agent를 되돌려 보낼 redirection URI를 포함합니다.

(B) authorization server는 user-agent를 통해 resource owner를 인증하고, resource owner가 client의 접근 요청을 허용하는지 거부하는지 결정합니다.

(C) resource owner가 접근을 허용한다고 가정하면, authorization server는 앞서 제공된 redirection URI를 사용하여 user-agent를 client로 다시 리디렉션합니다. redirection URI는 URI fragment에 access token을 포함합니다.

(D) user-agent는 리디렉션 지시에 따라 웹에 호스팅된 client 리소스에 요청을 보냅니다. 이 요청에는 [RFC2616]에 따라 fragment가 포함되지 않습니다. user-agent는 fragment 정보를 로컬에 보관합니다.

(E) 웹에 호스팅된 client 리소스는 user-agent가 보관한 fragment를 포함한 전체 redirection URI에 접근하고, fragment에 포함된 access token과 기타 매개변수를 추출할 수 있는 웹 페이지를 반환합니다. 이 페이지는 일반적으로 스크립트가 내장된 HTML 문서입니다.

(F) user-agent는 웹에 호스팅된 client 리소스가 제공한 스크립트를 로컬에서 실행하며, 이 스크립트가 access token을 추출합니다.

(G) user-agent는 access token을 client에 전달합니다.

implicit grant 사용에 관한 배경은 1.3.2절과 9절을 참조하십시오. implicit grant 사용 시 중요한 보안 고려 사항은 10.3절과 10.16절을 참조하십시오.

4.2.1. 인가 요청

client는 부록 B에 따라 "application/x-www-form-urlencoded" 형식을 사용하여 authorization endpoint URI의 query 구성 요소에 다음 매개변수를 추가함으로써 요청 URI를 구성합니다.

response_type REQUIRED. 값은 "token"으로 설정해야 합니다(MUST).

client_id REQUIRED. 2.2절에서 설명하는 client identifier입니다.

redirect_uri OPTIONAL. 3.1.2절에서 설명합니다.

scope OPTIONAL. 3.3절에서 설명하는 접근 요청의 scope입니다.

state RECOMMENDED. client가 요청과 콜백 사이의 상태를 유지하는 데 사용하는 불투명한 값입니다. authorization server는 user-agent를 client로 다시 리디렉션할 때 이 값을 포함합니다. 10.12절에서 설명하는 cross-site request forgery를 방지하기 위해 이 매개변수를 사용하는 것이 좋습니다(SHOULD).

client는 HTTP 리디렉션 응답이나 user-agent를 통해 사용할 수 있는 다른 수단을 사용하여 resource owner를 구성된 URI로 보냅니다.

예를 들어 client는 user-agent가 TLS를 사용하여 다음 HTTP 요청을 보내도록 합니다. 추가 줄바꿈은 표시상의 편의만을 위한 것입니다.

    GET /authorize?response_type=token&client_id=s6BhdRkqt3&state=xyz
        &redirect_uri=https%3A%2F%2Fclient%2Eexample%2Ecom%2Fcb HTTP/1.1
    Host: server.example.com

authorization server는 요청을 검증하여 모든 필수 매개변수가 존재하고 유효한지 확인합니다. authorization server는 access token을 리디렉션할 대상인 redirection URI가 3.1.2절에 설명된 대로 client가 등록한 redirection URI와 일치하는지 확인해야 합니다(MUST).

요청이 유효하면 authorization server는 resource owner를 인증하고 인가 결정을 얻습니다. 이는 resource owner에게 묻거나 다른 수단으로 승인을 확인하여 이루어집니다.

결정이 내려지면 authorization server는 HTTP 리디렉션 응답이나 user-agent를 통해 사용할 수 있는 다른 수단을 사용하여 user-agent를 제공된 client redirection URI로 보냅니다.

4.2.2. Access Token 응답

resource owner가 접근 요청을 허용하면 authorization server는 access token을 발급하고, 부록 B에 따라 "application/x-www-form-urlencoded" 형식을 사용하여 redirection URI의 fragment 구성 요소에 다음 매개변수를 추가함으로써 이를 client에 전달합니다.

access_token REQUIRED. authorization server가 발급한 access token입니다.

token_type REQUIRED. 7.1절에서 설명하는, 발급된 token의 유형입니다. 값은 대소문자를 구분하지 않습니다.

expires_in RECOMMENDED. access token의 유효 기간을 초 단위로 나타냅니다. 예를 들어 값 "3600"은 응답이 생성된 시점으로부터 한 시간 후에 access token이 만료됨을 나타냅니다. 생략하는 경우 authorization server는 다른 수단으로 만료 시간을 제공하거나 기본값을 문서화하는 것이 좋습니다(SHOULD).

scope client가 요청한 scope와 같으면 OPTIONAL이고, 그렇지 않으면 REQUIRED입니다. 3.3절에서 설명하는 access token의 scope입니다.

state client의 인가 요청에 "state" 매개변수가 있었다면 REQUIRED입니다. client로부터 받은 값과 정확히 같은 값입니다.

authorization server는 refresh token을 발급해서는 안 됩니다(MUST NOT).

예를 들어 authorization server는 다음 HTTP 응답을 보내 user-agent를 리디렉션합니다. 추가 줄바꿈은 표시상의 편의만을 위한 것입니다.

     HTTP/1.1 302 Found
     Location: http://example.com/cb#access_token=2YotnFZFEjr1zCsicMWpAA
               &state=xyz&token_type=example&expires_in=3600

개발자는 일부 user-agent가 HTTP "Location" 응답 헤더 필드에 fragment 구성 요소를 포함하는 것을 지원하지 않는다는 점에 유의해야 합니다. 이러한 client에서는 client를 리디렉션하기 위해 3xx 리디렉션 응답이 아닌 다른 방법이 필요합니다. 예를 들어 redirection URI에 연결된 동작을 수행하는 '계속' 버튼이 포함된 HTML 페이지를 반환할 수 있습니다.

client는 인식하지 못하는 응답 매개변수를 무시해야 합니다(MUST). 이 명세에서는 access token 문자열의 크기를 정의하지 않습니다. client는 값의 크기에 관해 가정하지 않는 것이 좋습니다. authorization server는 발급하는 모든 값의 크기를 문서화하는 것이 좋습니다(SHOULD).

4.2.2.1. 오류 응답

redirection URI가 누락되었거나 유효하지 않거나 일치하지 않아 요청이 실패하는 경우, 또는 client identifier가 누락되었거나 유효하지 않은 경우, authorization server는 resource owner에게 오류를 알리는 것이 좋으며(SHOULD), user-agent를 유효하지 않은 redirection URI로 자동 리디렉션해서는 안 됩니다(MUST NOT).

resource owner가 접근 요청을 거부하거나 redirection URI의 누락 또는 유효하지 않음 이외의 이유로 요청이 실패하면, authorization server는 부록 B에 따라 "application/x-www-form-urlencoded" 형식을 사용하여 redirection URI의 fragment 구성 요소에 다음 매개변수를 추가함으로써 client에 알립니다.

error REQUIRED. 다음 중 하나의 ASCII [USASCII] 오류 코드입니다.

invalid_request 요청에 필수 매개변수가 누락되었거나, 유효하지 않은 매개변수 값이 포함되었거나, 동일한 매개변수가 두 번 이상 포함되었거나, 그 밖의 형식 오류가 있습니다.

unauthorized_client client는 이 방법으로 access token을 요청할 권한이 없습니다.

access_denied resource owner 또는 authorization server가 요청을 거부했습니다.

unsupported_response_type authorization server는 이 방법을 통한 access token 획득을 지원하지 않습니다.

invalid_scope 요청한 scope가 유효하지 않거나, 알 수 없거나, 형식이 잘못되었습니다.

server_error authorization server에 예기치 않은 상황이 발생하여 요청을 이행하지 못했습니다. (HTTP 리디렉션으로는 500 Internal Server Error HTTP 상태 코드를 client에 반환할 수 없으므로 이 오류 코드가 필요합니다.)

temporarily_unavailable authorization server는 서버의 일시적인 과부하 또는 유지보수로 인해 현재 요청을 처리할 수 없습니다. (HTTP 리디렉션으로는 503 Service Unavailable HTTP 상태 코드를 client에 반환할 수 없으므로 이 오류 코드가 필요합니다.)

"error" 매개변수 값에는 %x20-21 / %x23-5B / %x5D-7E 집합에 속하지 않는 문자가 포함되어서는 안 됩니다(MUST NOT).

error_description OPTIONAL. 발생한 오류를 client 개발자가 이해하는 데 도움이 되는 추가 정보를 제공하는, 사람이 읽을 수 있는 ASCII [USASCII] 텍스트입니다. "error_description" 매개변수 값에는 %x20-21 / %x23-5B / %x5D-7E 집합에 속하지 않는 문자가 포함되어서는 안 됩니다(MUST NOT).

error_uri OPTIONAL. 오류에 관한 정보를 담은, 사람이 읽을 수 있는 웹 페이지를 식별하는 URI로, client 개발자에게 오류에 관한 추가 정보를 제공하는 데 사용됩니다. "error_uri" 매개변수 값은 URI-reference 문법을 따라야 하며(MUST), 따라서 %x21 / %x23-5B / %x5D-7E 집합에 속하지 않는 문자를 포함해서는 안 됩니다(MUST NOT).

state client의 인가 요청에 "state" 매개변수가 있었다면 REQUIRED입니다. client로부터 받은 값과 정확히 같은 값입니다.

예를 들어 authorization server는 다음 HTTP 응답을 보내 user-agent를 리디렉션합니다.

   HTTP/1.1 302 Found
   Location: https://client.example.com/cb#error=access_denied&state=xyz

4.3. Resource Owner Password Credentials Grant

resource owner password credentials grant 유형은 resource owner가 client와 신뢰 관계를 맺고 있는 경우에 적합합니다. 예를 들면 기기 운영체제나 높은 권한을 가진 애플리케이션이 이에 해당합니다. authorization server는 이 grant 유형을 활성화할 때 특별히 주의하고, 다른 흐름을 사용할 수 없는 경우에만 이를 허용하는 것이 좋습니다.

이 grant 유형은 resource owner의 자격 증명, 즉 사용자 이름과 비밀번호를 일반적으로 대화형 양식을 통해 얻을 수 있는 client에 적합합니다. 또한 저장된 자격 증명을 access token으로 변환함으로써 HTTP Basic 또는 Digest 인증과 같은 직접 인증 방식을 사용하는 기존 client를 OAuth로 이전하는 데도 사용됩니다.

     +----------+
     | Resource |
     |  Owner   |
     |          |
     +----------+
          v
          |    Resource Owner
         (A) Password Credentials
          |
          v
     +---------+                                  +---------------+
     |         |>--(B)---- Resource Owner ------->|               |
     |         |         Password Credentials     | Authorization |
     | Client  |                                  |     Server    |
     |         |<--(C)---- Access Token ---------<|               |
     |         |    (w/ Optional Refresh Token)   |               |
     +---------+                                  +---------------+

그림 5에 나타낸 흐름은 다음 단계로 구성됩니다.

(A) resource owner는 자신의 사용자 이름과 비밀번호를 client에 제공합니다.

(B) client는 resource owner로부터 받은 자격 증명을 포함하여 authorization server의 token endpoint에 access token을 요청합니다. 요청할 때 client는 authorization server에 자신을 인증합니다.

(C) authorization server는 client를 인증하고 resource owner의 자격 증명을 검증한 후, 유효하면 access token을 발급합니다.

4.3.1. 인가 요청과 응답

client가 resource owner의 자격 증명을 얻는 방법은 이 명세의 범위를 벗어납니다. client는 access token을 얻은 후 해당 자격 증명을 폐기해야 합니다(MUST).

4.3.2. Access Token 요청

client는 부록 B에 따른 "application/x-www-form-urlencoded" 형식과 UTF-8 문자 인코딩을 사용하여 HTTP 요청 entity-body에 다음 매개변수를 추가함으로써 token endpoint에 요청을 보냅니다.

grant_type REQUIRED. 값은 "password"로 설정해야 합니다(MUST).

username REQUIRED. resource owner의 사용자 이름입니다.

password REQUIRED. resource owner의 비밀번호입니다.

scope OPTIONAL. 3.3절에 설명된 접근 요청의 scope입니다.

client 유형이 confidential이거나 client가 client credentials를 발급받은 경우(또는 다른 인증 요건이 부과된 경우), client는 3.2.1절에 설명된 대로 authorization server에 인증해야 합니다(MUST).

예를 들어, client는 전송 계층 보안을 사용하여 다음과 같은 HTTP 요청을 보냅니다(추가 줄바꿈은 표시 목적으로만 삽입되었습니다).

     POST /token HTTP/1.1
     Host: server.example.com
     Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW
     Content-Type: application/x-www-form-urlencoded

     grant_type=password&username=johndoe&password=A3ddj3w

authorization server는 다음을 수행해야 합니다(MUST).

o confidential client 또는 client credentials를 발급받은 모든 client(또는 다른 인증 요건이 있는 client)에 대해 client 인증을 요구합니다.

o client 인증이 포함되어 있으면 client를 인증합니다. 그리고

o 기존 비밀번호 검증 알고리즘을 사용하여 resource owner password credentials를 검증합니다.

이 access token 요청은 resource owner의 비밀번호를 사용하므로, authorization server는 무차별 대입 공격으로부터 endpoint를 보호해야 합니다(MUST). 예를 들어 요청 빈도를 제한하거나 경고를 생성할 수 있습니다.

4.3.3. access token 응답

access token 요청이 유효하고 인가된 경우, authorization server는 5.1절에 설명된 대로 access token과 선택적인 refresh token을 발급합니다. 요청의 client 인증이 실패했거나 요청이 유효하지 않은 경우, authorization server는 5.2절에 설명된 대로 오류 응답을 반환합니다.

성공 응답의 예:

     HTTP/1.1 200 OK
     Content-Type: application/json;charset=UTF-8
     Cache-Control: no-store
     Pragma: no-cache

     {
       "access_token":"2YotnFZFEjr1zCsicMWpAA",
       "token_type":"example",
       "expires_in":3600,
       "refresh_token":"tGzv3JOkF0XG5Qx2TlKWIA",
       "example_parameter":"example_value"
     }

4.4. client credentials grant

client가 자신이 제어하는 protected resource에 대한 접근을 요청하거나, authorization server와 사전에 협의된 다른 resource owner의 protected resource에 대한 접근을 요청하는 경우, client는 자신의 client credentials만으로(또는 지원되는 다른 인증 수단으로) access token을 요청할 수 있습니다. 이러한 사전 협의 방법은 이 명세의 범위를 벗어납니다.

client credentials grant 유형은 confidential client만 사용해야 합니다(MUST).

     +---------+                                  +---------------+
     |         |                                  |               |
     |         |>--(A)- Client Authentication --->| Authorization |
     | Client  |                                  |     Server    |
     |         |<--(B)---- Access Token ---------<|               |
     |         |                                  |               |
     +---------+                                  +---------------+

그림 6에 나타낸 흐름은 다음 단계로 이루어집니다.

(A) client는 authorization server에 인증하고 token endpoint에 access token을 요청합니다.

(B) authorization server는 client를 인증하고, 유효하면 access token을 발급합니다.

4.4.1. 인가 요청과 응답

client 인증이 authorization grant로 사용되므로 추가적인 인가 요청은 필요하지 않습니다.

4.4.2. access token 요청

client는 부록 B에 따른 "application/x-www-form-urlencoded" 형식과 UTF-8 문자 인코딩을 사용하여 다음 매개변수를 HTTP 요청 entity-body에 추가함으로써 token endpoint에 요청을 보냅니다.

grant_type REQUIRED. 값을 "client_credentials"로 설정해야 합니다(MUST).

scope OPTIONAL. 3.3절에 설명된 접근 요청의 scope입니다.

client는 3.2.1절에 설명된 대로 authorization server에 인증해야 합니다(MUST).

예를 들어, client는 전송 계층 보안을 사용하여 다음과 같은 HTTP 요청을 보냅니다(추가 줄바꿈은 표시 목적으로만 삽입되었습니다).

     POST /token HTTP/1.1
     Host: server.example.com
     Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW
     Content-Type: application/x-www-form-urlencoded

     grant_type=client_credentials

authorization server는 client를 인증해야 합니다(MUST).

4.4.3. access token 응답

access token 요청이 유효하고 인가된 경우, authorization server는 5.1절에 설명된 대로 access token을 발급합니다. refresh token은 포함하지 않는 것이 좋습니다(SHOULD NOT). 요청의 client 인증이 실패했거나 요청이 유효하지 않은 경우, authorization server는 5.2절에 설명된 대로 오류 응답을 반환합니다.

성공 응답의 예:

     HTTP/1.1 200 OK
     Content-Type: application/json;charset=UTF-8
     Cache-Control: no-store
     Pragma: no-cache

     {
       "access_token":"2YotnFZFEjr1zCsicMWpAA",
       "token_type":"example",
       "expires_in":3600,
       "example_parameter":"example_value"
     }

4.5. 확장 grant

client는 token endpoint의 "grant_type" 매개변수 값으로 (authorization server가 정의한) 절대 URI를 사용하여 grant 유형을 지정하고 필요한 추가 매개변수를 더함으로써 확장 grant 유형을 사용합니다.

예를 들어, [OAuth-SAML2]에 정의된 Security Assertion Markup Language (SAML) 2.0 assertion grant 유형으로 access token을 요청하려면, client는 TLS를 사용하여 다음과 같은 HTTP 요청을 보낼 수 있습니다(추가 줄바꿈은 표시 목적으로만 삽입되었습니다).

     POST /token HTTP/1.1
     Host: server.example.com
     Content-Type: application/x-www-form-urlencoded

     grant_type=urn%3Aietf%3Aparams%3Aoauth%3Agrant-type%3Asaml2-
     bearer&assertion=PEFzc2VydGlvbiBJc3N1ZUluc3RhbnQ9IjIwMTEtMDU
     [...omitted for brevity...]aG5TdGF0ZW1lbnQ-PC9Bc3NlcnRpb24-

access token 요청이 유효하고 인가된 경우, authorization server는 5.1절에 설명된 대로 access token과 선택적인 refresh token을 발급합니다. 요청의 client 인증이 실패했거나 요청이 유효하지 않은 경우, authorization server는 5.2절에 설명된 대로 오류 응답을 반환합니다.

5. access token 발급

access token 요청이 유효하고 인가된 경우, authorization server는 5.1절에 설명된 대로 access token과 선택적인 refresh token을 발급합니다. 요청의 client 인증이 실패했거나 요청이 유효하지 않은 경우, authorization server는 5.2절에 설명된 대로 오류 응답을 반환합니다.

5.1. 성공 응답

authorization server는 access token과 선택적인 refresh token을 발급하고, 상태 코드가 200 (OK)인 HTTP 응답의 entity-body에 다음 매개변수를 추가하여 응답을 구성합니다.

access_token REQUIRED. authorization server가 발급한 access token입니다.

token_type REQUIRED. 7.1절에 설명된 발급 token의 유형입니다. 값은 대소문자를 구분하지 않습니다.

expires_in RECOMMENDED. access token의 수명으로, 단위는 초입니다. 예를 들어 "3600"이라는 값은 응답이 생성된 시점부터 한 시간 후에 access token이 만료됨을 나타냅니다. 이를 생략하면 authorization server는 다른 수단으로 만료 시각을 제공하거나 기본값을 문서화하는 것이 좋습니다(SHOULD).

refresh_token OPTIONAL. 6절에 설명된 대로 동일한 authorization grant를 사용하여 새로운 access token을 얻는 데 사용할 수 있는 refresh token입니다.

scope client가 요청한 scope와 동일하면 OPTIONAL이고, 그렇지 않으면 REQUIRED입니다. 3.3절에 설명된 access token의 scope입니다.

매개변수는 [RFC4627]에 정의된 "application/json" 미디어 유형을 사용하여 HTTP 응답의 entity-body에 포함됩니다. 각 매개변수를 구조의 최상위 수준에 추가하여 JavaScript Object Notation (JSON) 구조로 직렬화합니다. 매개변수 이름과 문자열 값은 JSON 문자열로 포함하고, 숫자 값은 JSON 숫자로 포함합니다. 매개변수 순서는 중요하지 않으며 달라질 수 있습니다.

authorization server는 token, 자격 증명 또는 그 밖의 민감한 정보가 포함된 모든 응답에 값이 "no-store"인 HTTP "Cache-Control" 응답 헤더 필드 [RFC2616]와 값이 "no-cache"인 "Pragma" 응답 헤더 필드 [RFC2616]를 포함해야 합니다(MUST).

예:

     HTTP/1.1 200 OK
     Content-Type: application/json;charset=UTF-8
     Cache-Control: no-store
     Pragma: no-cache

     {
       "access_token":"2YotnFZFEjr1zCsicMWpAA",
       "token_type":"example",
       "expires_in":3600,
       "refresh_token":"tGzv3JOkF0XG5Qx2TlKWIA",
       "example_parameter":"example_value"
     }

client는 응답에서 인식하지 못하는 값 이름을 무시해야 합니다(MUST). authorization server로부터 받는 token과 그 밖의 값의 크기는 정의하지 않습니다. client는 값의 크기에 대해 가정하지 않는 것이 좋습니다. authorization server는 발급하는 모든 값의 크기를 문서화하는 것이 좋습니다(SHOULD).

5.2. 오류 응답

authorization server는 별도로 지정되지 않은 한 HTTP 400 (Bad Request) 상태 코드로 응답하고, 응답에 다음 매개변수를 포함합니다.

error REQUIRED. 다음 중 하나의 ASCII [USASCII] 오류 코드입니다.

invalid_request 요청에 필수 매개변수가 누락되어 있거나, 지원하지 않는 매개변수 값(grant 유형 제외)이 포함되어 있거나, 매개변수가 중복되어 있거나, 여러 자격 증명이 포함되어 있거나, client 인증에 둘 이상의 메커니즘을 사용하거나, 그 밖의 형식 오류가 있습니다.

invalid_client client 인증이 실패했습니다(예: 알 수 없는 client, client 인증이 포함되지 않음, 지원하지 않는 인증 방법). authorization server는 지원하는 HTTP 인증 방식을 알리기 위해 HTTP 401 (Unauthorized) 상태 코드를 반환해도 됩니다(MAY). client가 "Authorization" 요청 헤더 필드를 통해 인증을 시도했다면 authorization server는 HTTP 401 (Unauthorized) 상태 코드로 응답하고, client가 사용한 인증 방식에 해당하는 "WWW-Authenticate" 응답 헤더 필드를 포함해야 합니다(MUST).

invalid_grant 제공된 authorization grant(예: authorization code, resource owner 자격 증명) 또는 refresh token이 유효하지 않거나, 만료되었거나, 취소되었거나, 인가 요청에 사용된 redirection URI와 일치하지 않거나, 다른 client에 발급된 것입니다.

unauthorized_client 인증된 client는 이 authorization grant 유형을 사용할 권한이 없습니다.

unsupported_grant_type authorization server가 이 authorization grant 유형을 지원하지 않습니다.

invalid_scope 요청한 scope가 유효하지 않거나, 알 수 없거나, 형식이 잘못되었거나, resource owner가 부여한 scope를 초과합니다.

"error" 매개변수 값에는 %x20-21 / %x23-5B / %x5D-7E 집합에 속하지 않는 문자를 포함해서는 안 됩니다(MUST NOT).

error_description OPTIONAL. 발생한 오류를 client 개발자가 이해하도록 돕기 위해 추가 정보를 제공하는, 사람이 읽을 수 있는 ASCII [USASCII] 텍스트입니다. "error_description" 매개변수 값에는 %x20-21 / %x23-5B / %x5D-7E 집합에 속하지 않는 문자를 포함해서는 안 됩니다(MUST NOT).

error_uri OPTIONAL. 오류에 관한 정보를 담은 사람이 읽을 수 있는 웹 페이지를 식별하는 URI로, client 개발자에게 오류에 대한 추가 정보를 제공하는 데 사용합니다. "error_uri" 매개변수 값은 URI-reference 구문을 따라야 하며(MUST), 따라서 %x21 / %x23-5B / %x5D-7E 집합에 속하지 않는 문자를 포함해서는 안 됩니다(MUST NOT).

매개변수는 [RFC4627]에 정의된 "application/json" 미디어 유형을 사용하여 HTTP 응답의 entity-body에 포함됩니다. 각 매개변수를 구조의 최상위 수준에 추가하여 JSON 구조로 직렬화합니다. 매개변수 이름과 문자열 값은 JSON 문자열로 포함하고, 숫자 값은 JSON 숫자로 포함합니다. 매개변수 순서는 중요하지 않으며 달라질 수 있습니다.

예:

     HTTP/1.1 400 Bad Request
     Content-Type: application/json;charset=UTF-8
     Cache-Control: no-store
     Pragma: no-cache

     {
       "error":"invalid_request"
     }

6. access token 갱신

authorization server가 client에 refresh token을 발급한 경우, client는 부록 B에 따른 "application/x-www-form-urlencoded" 형식과 UTF-8 문자 인코딩을 사용하여 다음 매개변수를 HTTP 요청 entity-body에 추가함으로써 token endpoint에 갱신 요청을 보냅니다.

grant_type REQUIRED. 값을 "refresh_token"으로 설정해야 합니다(MUST).

refresh_token REQUIRED. client에 발급된 refresh token입니다.

scope OPTIONAL. 3.3절에 설명된 접근 요청의 scope입니다. 요청한 scope에는 resource owner가 원래 부여하지 않은 scope를 포함해서는 안 되며(MUST NOT), 생략하면 resource owner가 원래 부여한 scope와 동일한 것으로 취급합니다.

refresh token은 일반적으로 추가 access token을 요청하는 데 사용되는 수명이 긴 자격 증명이므로, 발급받은 client에 결합됩니다. client 유형이 confidential이거나

client가 client credentials를 발급받은 경우(또는 다른 인증 요건이 부과된 경우), client는 3.2.1절에 설명된 대로 authorization server에 인증해야 합니다(MUST).

예를 들어 client는 전송 계층 보안을 사용하여 다음 HTTP 요청을 보냅니다(추가 줄바꿈은 표시 목적으로만 삽입되었습니다).

     POST /token HTTP/1.1
     Host: server.example.com
     Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW
     Content-Type: application/x-www-form-urlencoded

     grant_type=refresh_token&refresh_token=tGzv3JOkF0XG5Qx2TlKWIA

authorization server는 다음을 수행해야 합니다(MUST).

o confidential client 또는 client credentials를 발급받은 모든 client(또는 그 밖의 인증 요건이 있는 client)에 client 인증을 요구합니다.

o client 인증이 포함된 경우 client를 인증하고, refresh token이 인증된 client에게 발급되었는지 확인합니다. 그리고

o refresh token을 검증합니다.

요청이 유효하고 인가된 경우 authorization server는 5.1절에 설명된 대로 access token을 발급합니다. 요청이 검증에 실패하거나 유효하지 않은 경우 authorization server는 5.2절에 설명된 오류 응답을 반환합니다.

authorization server는 새 refresh token을 발급할 수 있습니다(MAY). 이 경우 client는 기존 refresh token을 폐기하고 새 refresh token으로 교체해야 합니다(MUST). authorization server는 client에게 새 refresh token을 발급한 뒤 기존 refresh token을 폐기할 수 있습니다(MAY). 새 refresh token이 발급되는 경우, 그 refresh token의 scope는 client가 요청에 포함한 refresh token의 scope와 동일해야 합니다(MUST).

7. protected resource에 접근하기

client는 resource server에 access token을 제시하여 protected resource에 접근합니다. resource server는 access token을 검증하고, 만료되지 않았으며 scope가 요청한 리소스를 포함하는지 확인해야 합니다(MUST). resource server가 access token을 검증하는 데 사용하는 방법과 오류 응답은 이 명세의 범위를 벗어나지만, 일반적으로 resource server와 authorization server 사이의 상호 작용이나 협조가 수반됩니다.

client가 resource server에 인증하기 위해 access token을 사용하는 방법은 authorization server가 발급한 access token의 유형에 따라 달라집니다. 일반적으로 [RFC6750]과 같이 사용되는 access token 유형의 명세에 정의된 인증 방식을 HTTP "Authorization" 요청 헤더 필드 [RFC2617]와 함께 사용합니다.

7.1. access token 유형

access token 유형은 유형별 속성과 함께, client가 access token을 성공적으로 사용하여 protected resource 요청을 보내는 데 필요한 정보를 제공합니다. client는 token 유형을 이해하지 못하면 해당 access token을 사용해서는 안 됩니다(MUST NOT).

예를 들어 [RFC6750]에 정의된 "bearer" token 유형은 다음과 같이 요청에 access token 문자열을 포함하기만 하면 사용할 수 있습니다.

     GET /resource/1 HTTP/1.1
     Host: example.com
     Authorization: Bearer mF_9.B5f-4.1JqM

반면 [OAuth-HTTP-MAC]에 정의된 "mac" token 유형은 access token과 함께 Message Authentication Code (MAC) 키를 발급하여 사용하며, 이 키는 다음과 같이 HTTP 요청의 특정 구성 요소에 서명하는 데 사용됩니다.

     GET /resource/1 HTTP/1.1
     Host: example.com
     Authorization: MAC id="h480djs93hd8",
                        nonce="274312:dj83hs9s",
                        mac="kDZvddkndxvhGRXZhvuDjEWhGeE="

위 예제는 설명 목적으로만 제공됩니다. 개발자는 사용 전에 [RFC6750] 및 [OAuth-HTTP-MAC] 명세를 참조하는 것이 좋습니다.

각 access token 유형 정의는 "access_token" 응답 매개변수와 함께 client에게 전송되는 추가 속성이 있다면 이를 명시합니다. 또한 protected resource 요청을 보낼 때 access token을 포함하는 데 사용하는 HTTP 인증 방법을 정의합니다.

7.2. 오류 응답

리소스 접근 요청이 실패하면 resource server는 client에게 오류를 알리는 것이 좋습니다(SHOULD). 이러한 오류 응답의 세부 사항은 이 명세의 범위를 벗어나지만, 이 문서는 OAuth token 인증 방식 간에 공유할 오류 값을 위한 공통 레지스트리를 11.4절에 마련합니다.

주로 OAuth token 인증을 위해 설계된 새로운 인증 방식은 client에게 오류 상태 코드를 제공하는 메커니즘을 정의하는 것이 좋으며(SHOULD), 여기서 허용하는 오류 값은 이 명세에서 마련한 오류 레지스트리에 등록되어 있어야 합니다.

이러한 방식은 유효한 오류 코드 집합을 등록된 값의 부분집합으로 제한할 수 있습니다(MAY). 이름이 있는 매개변수를 사용하여 오류 코드를 반환하는 경우, 매개변수 이름은 "error"로 하는 것이 좋습니다(SHOULD).

주로 OAuth token 인증을 위해 설계된 것은 아니지만 해당 용도로 사용할 수 있는 다른 방식도 동일한 방법으로 자체 오류 값을 레지스트리에 연결할 수 있습니다(MAY).

새로운 인증 방식은 이 명세의 사용 방식과 유사하게 오류 정보를 반환하기 위해 "error_description" 및 "error_uri" 매개변수의 사용을 추가로 명시할 수도 있습니다(MAY).

8. 확장성

8.1. access token 유형 정의하기

access token 유형은 두 가지 방법 중 하나로 정의할 수 있습니다. 11.1절의 절차에 따라 Access Token Types 레지스트리에 등록하거나, 고유한 절대 URI를 이름으로 사용합니다.

URI 이름을 사용하는 유형은 널리 적용되지 않으며 사용되는 resource server의 구현 세부 사항에 특화된 공급업체별 구현으로 제한하는 것이 좋습니다(SHOULD).

그 밖의 모든 유형은 등록해야 합니다(MUST). 유형 이름은 type-name ABNF를 따라야 합니다(MUST). 유형 정의에 새로운 HTTP 인증 방식이 포함된 경우, 유형 이름은 [RFC2617]에 정의된 HTTP 인증 방식 이름과 동일하게 하는 것이 좋습니다(SHOULD). token 유형 "example"은 예제에서 사용하도록 예약되어 있습니다.

     type-name  = 1*name-char
     name-char  = "-" / "." / "_" / DIGIT / ALPHA

8.2. 새로운 endpoint 매개변수 정의하기

authorization endpoint 또는 token endpoint에서 사용할 새로운 요청 또는 응답 매개변수는 11.2절의 절차에 따라 정의하고 OAuth Parameters 레지스트리에 등록합니다.

매개변수 이름은 param-name ABNF를 따라야 하며(MUST), 매개변수 값의 구문은 명확히 정의되어 있어야 합니다(MUST). 예를 들어 ABNF를 사용하거나 기존 매개변수의 구문을 참조할 수 있습니다.

     param-name  = 1*name-char
     name-char   = "-" / "." / "_" / DIGIT / ALPHA

널리 적용되지 않고 사용되는 authorization server의 구현 세부 사항에 특화된 미등록 공급업체별 매개변수 확장은 다른 등록 값과 충돌할 가능성이 낮은 공급업체별 접두사를 사용하는 것이 좋습니다(SHOULD). 예를 들어 'companyname_'으로 시작할 수 있습니다.

8.3. 새로운 authorization grant 유형 정의하기

새로운 authorization grant 유형은 "grant_type" 매개변수에 사용할 고유한 절대 URI를 할당하여 정의할 수 있습니다. 확장 grant 유형에 추가 token endpoint 매개변수가 필요하면 해당 매개변수를 11.2절에 설명된 대로 OAuth Parameters 레지스트리에 등록해야 합니다(MUST).

8.4. 새로운 authorization endpoint 응답 유형 정의하기

authorization endpoint에서 사용할 새로운 응답 유형은 11.3절의 절차에 따라 정의하고 Authorization Endpoint Response Types 레지스트리에 등록합니다. 응답 유형 이름은 response-type ABNF를 따라야 합니다(MUST).

     response-type  = response-name *( SP response-name )
     response-name  = 1*response-char
     response-char  = "_" / DIGIT / ALPHA

응답 유형에 하나 이상의 공백 문자(%x20)가 포함되면, 값의 순서가 중요하지 않은 공백으로 구분된 값 목록으로 비교합니다. 값의 순서는 하나만 등록할 수 있으며, 이 등록은 동일한 값 집합의 다른 모든 배열에도 적용됩니다.

예를 들어 이 명세는 응답 유형 "token code"를 정의하지 않습니다. 그러나 확장에서 "token code" 응답 유형을 정의하고 등록할 수 있습니다. 일단 등록되면 동일한 조합을 "code token"으로 등록할 수는 없지만, 두 값 모두 동일한 응답 유형을 나타내는 데 사용할 수 있습니다.

8.5. 추가 오류 코드 정의하기

프로토콜 확장(즉, access token 유형, 확장 매개변수 또는 확장 grant 유형)이 authorization code grant 오류 응답(4.1.2.1절), implicit grant 오류 응답(4.2.2.1절), token 오류 응답(5.2절) 또는 리소스 접근 오류 응답(7.2절)에서 사용할 추가 오류 코드를 필요로 하는 경우, 이러한 오류 코드를 정의할 수 있습니다(MAY).

확장 오류 코드가 함께 사용되는 확장이 등록된 access token 유형, 등록된 endpoint 매개변수 또는 확장 grant 유형인 경우, 해당 오류 코드를 11.4절의 절차에 따라 등록해야 합니다(MUST). 미등록 확장에서 사용하는 오류 코드도 등록할 수 있습니다(MAY).

오류 코드는 error ABNF를 따라야 하며(MUST), 가능하면 식별용 이름을 접두사로 붙이는 것이 좋습니다(SHOULD). 예를 들어 확장 매개변수 "example"에 설정된 잘못된 값을 나타내는 오류의 이름은 "example_invalid"로 지정하는 것이 좋습니다(SHOULD).

     error      = 1*error-char
     error-char = %x20-21 / %x23-5B / %x5D-7E

9. 네이티브 애플리케이션

네이티브 애플리케이션은 resource owner가 사용하는 장치에 설치되어 실행되는 client입니다(즉, 데스크톱 애플리케이션, 네이티브 모바일 애플리케이션). 네이티브 애플리케이션에는 보안, 플랫폼 기능 및 전반적인 최종 사용자 경험과 관련하여 특별한 고려가 필요합니다.

authorization endpoint에는 client와 resource owner의 user-agent 간 상호 작용이 필요합니다. 네이티브 애플리케이션은 외부 user-agent를 호출하거나 애플리케이션 내부에 user-agent를 내장할 수 있습니다. 예를 들면 다음과 같습니다.

o 외부 user-agent - 네이티브 애플리케이션은 여러 방법으로 authorization server의 응답을 받아올 수 있습니다. client를 처리기로 호출하도록 운영 체제에 등록된 scheme을 가진 redirection URI를 사용하거나, 자격 증명을 수동으로 복사하여 붙여넣거나, 로컬 웹 서버를 실행하거나, user-agent 확장 기능을 설치할 수 있습니다. 또는 client가 제어하는 서버 호스팅 리소스를 가리키는 redirection URI를 제공하고, 그 리소스가 응답을 네이티브 애플리케이션에 제공하도록 할 수 있습니다.

o 내장 user-agent - 네이티브 애플리케이션은 리소스를 불러오는 동안 발생하는 상태 변경을 감시하거나 user-agent의 쿠키 저장소에 접근하는 방식으로 내장 user-agent와 직접 통신하여 응답을 얻습니다.

개발자는 외부 user-agent와 내장 user-agent 중에서 선택할 때 다음 사항을 고려하는 것이 좋습니다.

o 외부 user-agent를 사용하면 resource owner가 authorization server와 이미 활성 세션을 맺고 있어 재인증할 필요가 없을 수 있으므로 완료율이 높아질 수 있습니다. 또한 최종 사용자에게 익숙한 경험과 기능을 제공합니다. resource owner는 인증을 돕는 user-agent 기능이나 확장 기능(예: 비밀번호 관리자, 2단계 인증 장치 판독기)을 이용할 수도 있습니다.

o 내장 user-agent는 작업 맥락을 전환하고 새 창을 열 필요가 없으므로 더 나은 사용성을 제공할 수 있습니다.

o 내장 user-agent는 resource owner가 대부분의 외부 user-agent에서 제공하는 시각적 보호 수단을 이용할 수 없는, 식별되지 않은 창에서 인증하게 되므로 보안상 어려움을 초래합니다. 내장 user-agent는 최종 사용자가 식별되지 않은 인증 요청을 신뢰하도록 학습시킵니다(따라서 피싱 공격을 실행하기 쉬워집니다).

implicit grant 유형과 authorization code grant 유형 중에서 선택할 때는 다음 사항을 고려하는 것이 좋습니다.

o 네이티브 애플리케이션은 client credentials를 기밀로 유지할 수 없으므로, authorization code grant 유형을 사용하는 네이티브 애플리케이션은 client credentials를 사용하지 않고 이 유형을 사용하는 것이 좋습니다(SHOULD).

o implicit grant 유형 흐름을 사용하면 refresh token이 반환되지 않으므로 access token이 만료되면 인가 과정을 반복해야 합니다.

10. 보안 고려 사항

OAuth는 유연하고 확장 가능한 프레임워크이므로 보안 고려 사항은 여러 요인에 따라 달라집니다. 다음 절들은 2.1절에 설명된 세 가지 client 프로필, 즉 웹 애플리케이션, user-agent 기반 애플리케이션 및 네이티브 애플리케이션에 초점을 맞추어 구현자를 위한 보안 지침을 제공합니다.

포괄적인 OAuth 보안 모델 및 분석과 프로토콜 설계 배경은 [OAuth-THREATMODEL]에서 제공합니다.

10.1. client 인증

authorization server는 client 인증을 위해 웹 애플리케이션 client와 client credentials를 설정합니다. authorization server는 client 비밀번호보다 강력한 client 인증 수단을 고려하는 것이 권장됩니다. 웹 애플리케이션 client는 client 비밀번호와 기타 client credentials의 기밀성을 보장해야 합니다(MUST).

authorization server는 client 인증을 목적으로 네이티브 애플리케이션 또는 user-agent 기반 애플리케이션 client에 client 비밀번호나 기타 client credentials를 발급해서는 안 됩니다(MUST NOT). authorization server는 특정 기기에 설치된 네이티브 애플리케이션 client의 특정 설치본에 대해 client 비밀번호나 기타 credentials를 발급할 수 있습니다(MAY).

client 인증이 불가능한 경우 authorization server는 client의 신원을 검증할 다른 수단을 사용하는 것이 좋습니다(SHOULD). 예를 들어 client redirection URI의 등록을 요구하거나 resource owner가 신원을 확인하도록 할 수 있습니다. 유효한 redirection URI만으로는 resource owner에게 인가를 요청할 때 client의 신원을 검증하기에 충분하지 않지만, resource owner의 인가를 얻은 후 위조 client에 credentials가 전달되는 것을 방지하는 데 사용할 수 있습니다.

authorization server는 인증되지 않은 client와 상호작용할 때 보안에 미치는 영향을 고려하고, 그러한 client에 발급된 다른 credentials(예: refresh token)의 잠재적 노출을 제한하는 조치를 취해야 합니다.

10.2. client 사칭

어떤 client가 자신의 client credentials에 대한 기밀성을 유지하지 못하거나 유지할 수 없다면, 악성 client가 해당 client를 사칭하여 protected resource에 접근할 수 있습니다.

authorization server는 가능할 때마다 client를 인증해야 합니다(MUST). client의 특성 때문에 authorization server가 client를 인증할 수 없는 경우, authorization server는 인가 응답 수신에 사용하는 모든 redirection URI의 등록을 요구해야 하며(MUST), 잠재적으로 악성일 수 있는 이러한 client로부터 resource owner를 보호할 다른 수단을 활용하는 것이 좋습니다(SHOULD). 예를 들어 authorization server는 client와 그 출처를 식별하는 데 resource owner의 도움을 받을 수 있습니다.

authorization server는 명시적인 resource owner 인증을 강제하고 resource owner에게 client 및 요청된 인가의 scope와 유효 기간에 관한 정보를 제공하는 것이 좋습니다(SHOULD). 현재 client의 맥락에서 이 정보를 검토하고 요청을 인가하거나 거부하는 것은 resource owner가 결정할 사항입니다.

authorization server는 client를 인증하거나 반복 요청이 사칭자가 아닌 원래 client에서 온 것임을 보장하는 다른 조치를 사용하지 않은 채, 반복되는 인가 요청을 자동으로(resource owner의 능동적 상호작용 없이) 처리하지 않는 것이 좋습니다(SHOULD NOT).

10.3. access token

access token credentials(및 기밀인 모든 access token 속성)는 전송 중과 저장 중에 기밀성을 유지해야 하며, authorization server, 해당 access token이 유효한 resource server, 그리고 해당 access token을 발급받은 client 사이에서만 공유해야 합니다(MUST). access token credentials는 1.6절에 설명된 TLS를 사용하고 [RFC2818]에 정의된 서버 인증을 적용하여 전송해야 합니다(MUST).

implicit grant 유형을 사용할 때 access token은 URI fragment로 전송되므로 권한이 없는 당사자에게 노출될 수 있습니다.

authorization server는 권한이 없는 당사자가 access token을 생성하거나 수정하거나 추측하여 유효한 access token을 만들어 낼 수 없도록 보장해야 합니다(MUST).

client는 필요한 최소 scope의 access token을 요청하는 것이 좋습니다(SHOULD). authorization server는 요청된 scope를 어떻게 수용할지 결정할 때 client의 신원을 고려하는 것이 좋으며(SHOULD), 요청된 것보다 적은 권한을 가진 access token을 발급할 수 있습니다(MAY).

이 명세는 특정 client가 resource server에 제시한 access token이 authorization server에서 그 client에 발급한 것인지 resource server가 확인할 수 있는 방법을 제공하지 않습니다.

10.4. refresh token

authorization server는 웹 애플리케이션 client와 네이티브 애플리케이션 client에 refresh token을 발급할 수 있습니다(MAY).

refresh token은 전송 중과 저장 중에 기밀성을 유지해야 하며, authorization server와 해당 refresh token을 발급받은 client 사이에서만 공유해야 합니다(MUST). authorization server는 refresh token과 이를 발급받은 client 간의 바인딩을 유지해야 합니다(MUST). refresh token은 1.6절에 설명된 TLS를 사용하고 [RFC2818]에 정의된 서버 인증을 적용하여 전송해야 합니다(MUST).

authorization server는 client의 신원을 인증할 수 있을 때마다 refresh token과 client 신원 간의 바인딩을 검증해야 합니다(MUST). client 인증이 불가능한 경우 authorization server는 refresh token의 악용을 탐지할 다른 수단을 적용하는 것이 좋습니다(SHOULD).

예를 들어 authorization server는 access token 갱신 응답마다 새 refresh token을 발급하는 refresh token rotation을 사용할 수 있습니다. 이전 refresh token은 무효화되지만 authorization server가 계속 보관합니다. refresh token이 유출되어 이후 공격자와 정당한 client가 모두 이를 사용하면, 둘 중 하나는 무효화된 refresh token을 제시하게 되며, 이를 통해 authorization server는 침해 사실을 알게 됩니다.

authorization server는 권한이 없는 당사자가 refresh token을 생성하거나 수정하거나 추측하여 유효한 refresh token을 만들어 낼 수 없도록 보장해야 합니다(MUST).

10.5. authorization code

authorization code는 보안 채널을 통해 전송하는 것이 좋으며(SHOULD), client의 redirection URI가 네트워크 리소스를 식별한다면 client는 해당 URI에 TLS 사용을 요구하는 것이 좋습니다(SHOULD). authorization code는 user-agent 리디렉션을 통해 전송되므로 user-agent 방문 기록과 HTTP referrer 헤더를 통해 노출될 가능성이 있습니다.

authorization code는 평문 bearer credentials로 작동하며, authorization server에서 인가를 부여한 resource owner와 절차를 완료하기 위해 client로 돌아오는 resource owner가 동일한지 검증하는 데 사용됩니다. 따라서 client가 자체 resource owner 인증에 authorization code를 사용한다면, client의 redirection endpoint는 TLS 사용을 요구해야 합니다(MUST).

authorization code는 유효 기간이 짧고 일회용이어야 합니다(MUST). authorization server가 하나의 authorization code를 access token으로 교환하려는 시도를 여러 번 관찰하면, authorization server는 유출된 해당 authorization code에 근거해 이미 부여한 모든 access token을 폐기하려고 시도하는 것이 좋습니다(SHOULD).

client를 인증할 수 있다면 authorization server는 client를 인증하고 authorization code가 동일한 client에 발급되었는지 확인해야 합니다(MUST).

10.6. authorization code redirection URI 조작

authorization code grant 유형으로 인가를 요청할 때 client는 "redirect_uri" 매개변수를 통해 redirection URI를 지정할 수 있습니다. 공격자가 redirection URI 값을 조작할 수 있다면 authorization server가 resource owner의 user-agent를 authorization code와 함께 공격자가 제어하는 URI로 리디렉션하도록 만들 수 있습니다.

공격자는 정당한 client에서 계정을 만들고 인가 흐름을 시작할 수 있습니다. 접근 권한을 부여하기 위해 공격자의 user-agent가 authorization server로 보내질 때, 공격자는 정당한 client가 제공한 인가 URI를 가로채고 client의 redirection URI를 공격자가 제어하는 URI로 바꿉니다. 그런 다음 공격자는 피해자가 조작된 링크를 따라가 정당한 client에 접근을 인가하도록 속입니다.

authorization server에 도착하면 피해자는 정당하고 신뢰할 수 있는 client를 대신한 정상적이고 유효한 요청을 제시받고 그 요청을 인가합니다. 그런 다음 피해자는 authorization code와 함께 공격자가 제어하는 endpoint로 리디렉션됩니다. 공격자는 client가 제공한 원래 redirection URI를 사용하여 authorization code를 client에 보내 인가 흐름을 완료합니다. client는 authorization code를 access token으로 교환하고 이를 공격자의 client 계정에 연결하며, 이제 이 계정은 피해자가 인가한 protected resource에 (client를 통해) 접근할 수 있습니다.

이러한 공격을 방지하기 위해 authorization server는 authorization code를 얻을 때 사용된 redirection URI와 authorization code를 access token으로 교환할 때 제공되는 redirection URI가 동일한지 확인해야 합니다(MUST). authorization server는 public client에 redirection URI 등록을 요구해야 하며(MUST), confidential client에도 등록을 요구하는 것이 좋습니다(SHOULD). 요청에 redirection URI가 제공되면 authorization server는 등록된 값과 대조하여 이를 검증해야 합니다(MUST).

10.7. resource owner password credentials

resource owner password credentials grant 유형은 레거시 시스템이나 마이그레이션 때문에 사용되는 경우가 많습니다. 이 유형은 client가 사용자 이름과 비밀번호를 저장하는 데 따른 전반적인 위험을 줄이지만, 높은 권한을 가진 credentials를 client에 노출해야 한다는 점까지 없애 주지는 않습니다.

이 grant 유형은 이 프로토콜이 피하고자 하는 비밀번호 anti-pattern을 그대로 유지하므로 다른 grant 유형보다 위험이 큽니다. client가 비밀번호를 악용할 수도 있고, 비밀번호가 의도치 않게 공격자에게 노출될 수도 있습니다(예: client가 보관하는 로그 파일이나 기타 기록을 통해).

또한 resource owner는 인가 절차를 통제할 수 없으므로(resource owner의 관여는 자신의 credentials를 client에 넘길 때 끝납니다), client는 resource owner가 원하는 것보다 넓은 scope의 access token을 얻을 수 있습니다. authorization server는 이 grant 유형을 통해 발급되는 access token의 scope와 유효 기간을 고려하는 것이 좋습니다.

authorization server와 client는 이 grant 유형의 사용을 최소화하고 가능할 때마다 다른 grant 유형을 활용하는 것이 좋습니다(SHOULD).

10.8. 요청의 기밀성

access token, refresh token, resource owner의 비밀번호 및 client credentials를 평문으로 전송해서는 안 됩니다(MUST NOT). authorization code는 평문으로 전송하지 않는 것이 좋습니다(SHOULD NOT).

"state"와 "scope" 매개변수는 안전하지 않은 채널을 통해 전송되거나 안전하지 않게 저장될 수 있으므로, 민감한 client 또는 resource owner 정보를 평문으로 포함하지 않는 것이 좋습니다(SHOULD NOT).

10.9. endpoint의 진위 보장

중간자 공격을 방지하기 위해 authorization server는 authorization endpoint와 token endpoint로 보내는 모든 요청에 [RFC2818]에 정의된 서버 인증을 적용한 TLS 사용을 요구해야 합니다(MUST). client는 [RFC6125]에 정의된 대로, 그리고 서버 신원 인증에 관한 해당 요구 사항에 따라 authorization server의 TLS 인증서를 검증해야 합니다(MUST).

10.10. credentials 추측 공격

authorization server는 공격자가 access token, authorization code, refresh token, resource owner의 비밀번호 및 client credentials를 추측하는 것을 방지해야 합니다(MUST).

공격자가 생성된 token(및 최종 사용자가 직접 다루도록 의도되지 않은 기타 credentials)을 추측해 맞힐 확률은 2^(-128) 이하여야 하며(MUST), 2^(-160) 이하인 것이 좋습니다(SHOULD).

authorization server는 최종 사용자가 사용하도록 의도된 credentials를 보호하기 위해 다른 수단을 활용해야 합니다(MUST).

10.11. 피싱 공격

이 프로토콜과 유사한 프로토콜이 널리 보급되면 최종 사용자는 비밀번호 입력을 요구하는 웹사이트로 리디렉션되는 관행에 무감각해질 수 있습니다. 최종 사용자가 자격 증명을 입력하기 전에 이러한 웹사이트의 진위를 주의 깊게 확인하지 않으면, 공격자가 이 관행을 악용하여 resource owner의 비밀번호를 훔칠 수 있게 됩니다.

서비스 제공자는 최종 사용자에게 phishing 공격이 초래하는 위험을 교육하도록 노력하는 것이 좋으며, 최종 사용자가 서비스 제공자 사이트의 진위를 쉽게 확인할 수 있는 수단을 제공하는 것이 좋습니다. client 개발자는 user-agent와 상호 작용하는 방식(예: 외부 방식, 내장 방식)이 보안에 미치는 영향과 최종 사용자가 authorization server의 진위를 확인할 수 있는지를 고려하는 것이 좋습니다.

phishing 공격의 위험을 줄이기 위해 authorization server는 최종 사용자와의 상호 작용에 사용되는 모든 endpoint에서 TLS 사용을 요구해야 합니다(MUST).

10.12. Cross-Site Request Forgery

Cross-site request forgery(CSRF)는 공격자가 피해 최종 사용자의 user-agent로 하여금 악의적인 URI를 따라가게 하여, 해당 user-agent를 신뢰하는 서버에 접근하도록 만드는 공격입니다. 악의적인 URI는 예를 들어 오해를 유도하는 링크, 이미지 또는 리디렉션 형태로 user-agent에 제공되며, 서버의 신뢰는 일반적으로 유효한 session cookie의 존재를 통해 성립합니다.

client의 redirection URI를 대상으로 한 CSRF 공격을 통해 공격자는 자신의 authorization code나 access token을 주입할 수 있습니다. 그 결과 client가 피해자의 protected resource가 아니라 공격자의 protected resource에 연결된 access token을 사용할 수 있습니다. 예를 들어 피해자의 은행 계좌 정보를 공격자가 제어하는 protected resource에 저장하게 할 수 있습니다.

client는 자신의 redirection URI에 대해 CSRF 방어를 구현해야 합니다(MUST). 일반적으로 이를 위해 redirection URI endpoint로 전송되는 모든 요청에 해당 요청을 user-agent의 인증된 상태와 결부시키는 값(예: user-agent를 인증하는 데 사용한 session cookie의 해시)을 포함하도록 요구합니다. client는 authorization 요청을 할 때 이 값을 authorization server에 전달하기 위해 "state" 요청 매개변수를 활용하는 것이 좋습니다(SHOULD).

최종 사용자에게서 인가를 얻으면 authorization server는 필요한 결부 값을 "state" 매개변수에 포함하여 최종 사용자의 user-agent를 client로 다시 리디렉션합니다. client는 이 결부 값을 user-agent의 인증된 상태와 대조하여 요청의 유효성을 확인할 수 있습니다. CSRF 방어에 사용되는 결부 값에는 추측할 수 없는 값이 포함되어야 하며(MUST, Section 10.10 참조), user-agent의 인증된 상태(예: session cookie, HTML5 local storage)는 client와 user-agent만 접근할 수 있는 위치에 보관해야 합니다(MUST). 즉, same-origin policy로 보호되어야 합니다.

authorization server의 authorization endpoint를 대상으로 한 CSRF 공격은 최종 사용자를 관여시키지도, 최종 사용자에게 알리지도 않은 채 공격자가 악성 client에 대한 최종 사용자의 인가를 얻는 결과를 초래할 수 있습니다.

authorization server는 자신의 authorization endpoint에 대해 CSRF 방어를 구현하고, resource owner가 인지하고 명시적으로 동의하지 않는 한 악성 client가 인가를 얻을 수 없도록 보장해야 합니다(MUST).

10.13. Clickjacking

clickjacking 공격에서 공격자는 정상적인 client를 등록한 다음 악성 사이트를 구성합니다. 이 사이트는 authorization server의 authorization endpoint 웹페이지를 투명한 iframe에 로드하고, 여러 가짜 버튼 위에 겹쳐 놓습니다. 가짜 버튼은 인가 페이지의 중요한 버튼 바로 아래에 놓이도록 정교하게 배치됩니다. 최종 사용자가 오해를 유도하는, 눈에 보이는 버튼을 클릭하면 실제로는 인가 페이지의 보이지 않는 버튼(예: "Authorize" 버튼)을 클릭하게 됩니다. 이로써 공격자는 resource owner를 속여 최종 사용자가 알지 못하는 사이에 공격자의 client에 접근 권한을 부여하게 할 수 있습니다.

이러한 형태의 공격을 방지하기 위해 native application은 최종 사용자에게 인가를 요청할 때 애플리케이션 안에 브라우저를 내장하는 대신 외부 브라우저를 사용하는 것이 좋습니다(SHOULD). 대부분의 최신 브라우저에서는 authorization server가 비표준 "x-frame-options" 헤더를 사용하여 iframe 사용을 차단할 수 있습니다. 이 헤더는 "deny"와 "sameorigin"이라는 두 값을 가질 수 있으며, 각각 모든 framing 또는 origin이 다른 사이트에 의한 framing을 차단합니다. 오래된 브라우저에서는 JavaScript frame-busting 기법을 사용할 수 있지만, 모든 브라우저에서 효과가 있는 것은 아닙니다.

10.14. Code Injection과 입력 검증

code injection 공격은 애플리케이션이 입력값이나 그 밖의 외부 변수를 무해화하지 않은 채 사용하여 애플리케이션 로직이 변경될 때 발생합니다. 이로 인해 공격자가 애플리케이션이 실행되는 기기나 그 데이터에 접근하거나, 서비스 거부를 일으키거나, 다양한 악의적 부작용을 유발할 수 있습니다.

authorization server와 client는 수신하는 모든 값, 특히 "state"와 "redirect_uri" 매개변수의 값을 무해화하고, 가능하면 검증도 해야 합니다(MUST).

10.15. Open Redirector

authorization server, authorization endpoint, client의 redirection endpoint는 잘못 구성되어 open redirector로 동작할 수 있습니다. open redirector는 아무런 검증 없이 매개변수 값이 지정한 위치로 user-agent를 자동 리디렉션하는 데 매개변수를 사용하는 endpoint입니다.

open redirector는 phishing 공격에 사용될 수 있으며, 공격자가 익숙하고 신뢰할 수 있는 목적지의 URI authority 구성 요소를 이용하여 최종 사용자가 악성 사이트를 방문하도록 유도하는 데도 사용될 수 있습니다. 또한 authorization server가 client에 redirection URI의 일부만 등록하도록 허용하는 경우, 공격자는 client가 운영하는 open redirector를 사용하여 authorization server의 검증은 통과하지만 authorization code나 access token은 공격자가 제어하는 endpoint로 보내는 redirection URI를 구성할 수 있습니다.

10.16. Implicit Flow에서 Resource Owner를 사칭하기 위한 Access Token 오용

implicit flow를 사용하는 public client에 대해 이 명세는 access token이 어느 client에 발급되었는지 client가 알아낼 수 있는 방법을 제공하지 않습니다.

resource owner는 공격자의 악성 client에 access token을 부여하여 리소스 접근 권한을 자발적으로 위임할 수 있습니다. 이는 phishing이나 그 밖의 구실에 넘어간 결과일 수 있습니다. 공격자는 다른 수단으로 token을 훔칠 수도 있습니다. 그런 다음 공격자는 정상적인 public client에 그 access token을 제공하여 resource owner를 사칭하려고 시도할 수 있습니다.

implicit flow(response_type=token)에서 공격자는 authorization server가 보낸 응답의 token을 쉽게 바꾸어, 실제 access token을 이전에 공격자에게 발급된 것으로 대체할 수 있습니다.

native application과 통신하면서 client 사용자를 식별하기 위해 back channel로 전달받은 access token에 의존하는 서버도 이와 유사하게 침해될 수 있습니다. 공격자가 임의의 도난당한 access token을 주입할 수 있는 변조된 애플리케이션을 만들면 이러한 공격이 가능합니다.

해당 리소스에 대한 유효한 access token을 자신에게 제시할 수 있는 사람은 resource owner뿐이라고 가정하는 모든 public client는 이러한 유형의 공격에 취약합니다.

이러한 유형의 공격은 정상적인 client에 있는 resource owner 정보를 공격자(악성 client)에게 노출할 수 있습니다. 또한 공격자는 원래 access token이나 authorization code를 부여한 resource owner와 동일한 권한으로 정상적인 client에서 작업을 수행할 수 있게 됩니다.

client에 대해 resource owner를 인증하는 것은 이 명세의 범위를 벗어납니다. 인가 절차를 client에 대한 위임된 최종 사용자 인증의 한 형태(예: 제삼자 로그인 서비스)로 사용하는 명세는, access token이 자신의 사용을 위해 발급되었는지 client가 판단할 수 있게 하는 추가 보안 수단(예: access token의 audience 제한) 없이 implicit flow를 사용해서는 안 됩니다(MUST NOT).

11. IANA 고려 사항

11.1. OAuth Access Token Types 레지스트리

이 명세는 OAuth Access Token Types 레지스트리를 신설합니다.

access token 유형은 oauth-ext-review@ietf.org 메일링 리스트에서 2주간의 검토 기간을 거친 후, 한 명 이상의 Designated Expert의 조언에 따라 Specification Required([RFC5226]) 절차로 등록됩니다. 다만 명세 발행 전에 값을 할당할 수 있도록, Designated Expert는 해당 명세가 발행될 것이라고 확신하면 등록을 승인할 수 있습니다.

등록 요청은 검토와 의견 수렴을 위해 적절한 제목(예: "Request for access token type: example")을 붙여 oauth-ext-review@ietf.org 메일링 리스트로 보내야 합니다.

Designated Expert는 검토 기간 안에 등록 요청을 승인하거나 거부하고, 그 결정을 검토 리스트와 IANA에 전달합니다. 거부 시에는 그 이유를 설명하고, 해당하는 경우 요청이 승인될 수 있도록 개선 방안을 제시하는 것이 좋습니다.

IANA는 Designated Expert가 제출한 레지스트리 갱신만 수락해야 하며, 모든 등록 요청을 검토 메일링 리스트로 안내하는 것이 좋습니다.

11.1.1. 등록 양식

유형 이름: 등록하려는 이름(예: "example").

추가 Token Endpoint 응답 매개변수: "access_token" 매개변수와 함께 반환되는 추가 응답 매개변수. 새 매개변수는 Section 11.2에 설명된 대로 OAuth Parameters 레지스트리에 별도로 등록해야 합니다(MUST).

HTTP Authentication Scheme: 이 유형의 access token을 사용하여 protected resource 요청을 인증하는 데 쓰이는 HTTP authentication scheme의 이름(있는 경우).

변경 관리 주체: Standards Track RFC의 경우 "IETF"라고 명시합니다. 그 밖의 경우에는 책임 주체의 이름을 기재합니다. 그 밖의 세부 정보(예: 우편 주소, 이메일 주소, 홈페이지 URI)도 포함할 수 있습니다.

명세 문서: 해당 매개변수를 명세하는 문서에 대한 참조. 문서 사본을 가져오는 데 사용할 수 있는 URI를 포함하는 것이 바람직합니다. 관련 절을 표시할 수도 있지만 필수는 아닙니다.

부록 B. application/x-www-form-urlencoded media type의 사용

이 명세가 발행될 당시 "application/x-www-form-urlencoded" media type은 [W3C.REC-html401-19991224]의 17.13.4절에 정의되어 있었지만, IANA MIME Media Types registry에는 등록되어 있지 않았습니다(<http://www.iana.org/assignments/media-types>). 또한 그 정의는 US-ASCII 이외의 문자를 고려하지 않으므로 불완전합니다.

이 media type으로 payload를 생성할 때 이러한 결점을 해결하려면, 이름과 값을 먼저 UTF-8 문자 인코딩 방식 [RFC3629]으로 인코딩해야 합니다(MUST). 그런 다음, 그 결과인 octet sequence를 [W3C.REC-html401-19991224]에 정의된 escaping 규칙에 따라 추가로 인코딩해야 합니다.

이 media type을 사용하는 payload의 데이터를 파싱할 때에는, 이름/값 인코딩을 역으로 처리하여 얻은 이름과 값을 octet sequence로 취급한 다음 UTF-8 문자 인코딩 방식으로 디코딩해야 합니다.

예를 들어, 여섯 개의 Unicode code point인 (1) U+0020 (SPACE), (2) U+0025 (PERCENT SIGN), (3) U+0026 (AMPERSAND), (4) U+002B (PLUS SIGN), (5) U+00A3 (POUND SIGN), (6) U+20AC (EURO SIGN)으로 이루어진 값은 다음 octet sequence로 인코딩됩니다(16진수 표기 사용). 

     20 25 26 2B C2 A3 E2 82 AC

그런 다음 payload에서는 다음과 같이 표현됩니다.

최초의 OAuth 2.0 프로토콜 명세는 이전에 발행된 두 문서, 즉 OAuth 1.0 커뮤니티 명세 [RFC5849]와 OAuth WRAP (OAuth Web Resource Authorization Profiles) [OAuth-WRAP]을 바탕으로 David Recordon이 편집했습니다. 이후 Eran Hammer가 이 RFC로 발전하기까지의 여러 중간 초안을 편집했습니다. 보안 고려 사항 절은 Torsten Lodderstedt, Mark McGloin, Phil Hunt, Anthony Nadalin 및 John Bradley가 초안을 작성했습니다. "application/x-www-form-urlencoded" media type의 사용에 관한 절은 Julian Reschke가 초안을 작성했습니다. ABNF 절은 Michael B. Jones가 초안을 작성했습니다.

OAuth 1.0 커뮤니티 명세는 Eran Hammer가 편집했으며, Mark Atwood, Dirk Balfanz, Darren Bounds, Richard M. Conlan, Blaine Cook, Leah Culver, Breno de Medeiros, Brian Eaton, Kellan Elliott-McCrea, Larry Halff, Eran Hammer, Ben Laurie, Chris Messina, John Panzer, Sam Quigley, David Recordon, Eran Sandler, Jonathan Sergent, Todd Sieling, Brian Slesinsky 및 Andy Smith가 작성했습니다.

OAuth WRAP 명세는 Dick Hardt가 편집했으며, Brian Eaton, Yaron Y. Goland, Dick Hardt 및 Allen Tom이 작성했습니다.

이 명세는 적극적이고 헌신적인 수십 명의 참여자로 구성된 OAuth Working Group의 작업 결과물입니다. 특히 다음 사람들이 제시한 아이디어, 의견 및 문구가 최종 명세의 형태와 내용을 이루는 데 기여했습니다.
