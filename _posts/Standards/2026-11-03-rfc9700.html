초록

이 문서는 OAuth 2.0을 위한 현행 보안 모범 사례를 설명합니다. OAuth 2.0이 발표된 이후 축적된 실무 경험을 반영하도록 RFC 6749, 6750, 6819에 제시된 위협 모델과 보안 지침을 갱신하고 확장하며, OAuth 2.0의 적용 범위가 넓어지면서 중요해진 새로운 위협을 다룹니다. 또한 보안성이 낮거나 심지어 안전하지 않은 것으로 간주되는 일부 운영 모드의 사용을 폐기 예정으로 지정합니다.¶

1. 소개

OAuth 2.0(이 문서에서는 간단히 "OAuth"라고 합니다)은 [RFC6749]와 [RFC6750]으로 발표된 이후 시장에서 폭넓게 채택되어 API 보호의 표준이자 OpenID Connect [OpenID.Core]를 사용하는 federated login의 기반이 되었습니다. OAuth는 다양한 시나리오와 여러 유형의 배포 환경에서 사용되지만, 다음과 같은 과제를 확인할 수 있습니다.¶

  • OAuth 구현은 알려진 구현상의 취약점과 anti-pattern(안전하지 않다고 여겨지는 잘 알려진 패턴)을 통해 공격받고 있습니다. 이러한 위협 대부분은 OAuth 2.0 Threat Model and Security Considerations [RFC6819]에서 다루지만, 악용이 계속된다는 사실은 더 구체적인 권고, 더 쉽게 구현할 수 있는 완화책, 그리고 더 강화된 defense in depth가 필요함을 보여 줍니다.¶

  • OAuth는 open banking, eHealth, eGovernment, 전자 서명 등 처음에 고려했던 것보다 더 높은 보안 요구 사항을 가진 환경에서 사용되고 있습니다. 이러한 사용 사례에는 더 엄격한 지침과 추가적인 보호가 필요합니다.¶

  • OAuth는 처음 예상했던 것보다 훨씬 더 동적인 구성에서 사용되고 있으며, 이로 인해 보안과 관련된 새로운 과제가 발생하고 있습니다. 이러한 과제는 [RFC6749], [RFC6750], [RFC6819]의 원래 범위를 벗어납니다.¶

    OAuth는 처음에 client, authorization server, resource server 간의 정적인 관계를 전제로 했습니다. 서버의 URL은 배포 시점에 client에 알려져 있었으며, 이 당사자들 사이의 신뢰 관계를 뒷받침하는 기준점이 되었습니다. client가 정당한 서버와 통신하고 있는지에 대한 검증은 TLS 서버 인증에 기반했습니다(4.5.4절, [RFC6819] 참조). OAuth의 채택이 늘어나면서 이 단순한 모델은 해체되었고, 여러 시나리오에서 한쪽의 client와 다른 쪽의 특정 배포 환경에 속한 authorization server 및 resource server 사이에 관계를 동적으로 수립하는 방식으로 대체되었습니다. 이렇게 하면 동일한 client를 사용하여 서로 다른 제공자의 서비스에 접근하거나(email 또는 OpenID Connect 같은 표준 API의 경우), multi-tenant 환경에서 특정 tenant의 front end로 활용할 수 있습니다. OAuth 2.0 Dynamic Client Registration Protocol [RFC7591] 및 OAuth 2.0 Authorization Server Metadata [RFC8414] 같은 OAuth 확장은 동적 시나리오에서 OAuth를 사용할 수 있도록 개발되었습니다.¶

  • 기술이 변했습니다. 예를 들어 브라우저가 요청을 redirect할 때 fragment를 처리하는 방식이 바뀌었고, 이에 따라 implicit grant의 기저 보안 모델도 바뀌었습니다.¶

이 문서는 이러한 과제에 대응하기 위해 갱신된 보안 권고 사항을 제공합니다. OAuth 2.0 [RFC6749] 및 OpenID Connect [OpenID.Core] 같은 기존 명세에 정의된 것 이상의 새로운 요구 사항을 도입하고, 보안성이 낮거나 심지어 안전하지 않다고 여겨지는 일부 동작 모드를 폐기 대상으로 지정합니다. 다만 이 문서는 [RFC6749], [RFC6750], [RFC6819]의 보안 지침을 대체하지 않고 이 문서들을 보완합니다.¶

당연히 기존의 모든 생태계와 구현이 새로운 요구 사항과 호환되는 것은 아니며, 이 문서에서 설명하는 모범 관행을 따르면 상호운용성이 깨질 수 있습니다. 그럼에도 구현자는 실행 가능한 한 조속히 구현과 생태계를 업그레이드할 것을 권고합니다(RECOMMENDED).¶

[OAUTH-V2.1]로 개발 중인 OAuth 2.1에는 이 문서의 보안 권고 사항이 반영될 예정입니다.¶

1.1. 구성

이 문서의 나머지 부분은 다음과 같이 구성됩니다. 2절에서는 모든 OAuth 구현자에게 가장 중요한 모범 관행을 요약합니다. 3절에서는 갱신된 OAuth 공격자 모델을 제시합니다. 4절에서는 작성 시점에 실제 환경에서 발견할 수 있는 위협과 구현상의 문제를 자세히 분석하고, 가능한 대응책을 논의합니다.¶

1.2. 표기 규칙과 용어

이 문서의 핵심 단어 "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", "OPTIONAL"는 여기에 표시된 것처럼 모두 대문자로 나타나는 경우에만 BCP 14 [RFC2119] [RFC8174]에 설명된 대로 해석합니다.¶

이 명세에서는 OAuth 2.0 [RFC6749]에 정의된 "access token", "authorization endpoint(인가 엔드포인트)", "authorization grant(권한 부여)", "authorization server", "client", "client identifier(클라이언트 식별자)"(client ID), "protected resource(보호된 리소스)", "refresh token", "resource owner", "resource server", "token endpoint(토큰 엔드포인트)"라는 용어를 사용합니다.¶

"open redirector"는 query parameter에서 얻은 임의의 URI로 사용자의 브라우저를 전달하는 웹 서버의 endpoint입니다.¶

2. 모범 관행

이 절에서는 작성 시점에 모범 관행으로 여겨지는 핵심 보안 메커니즘과 조치를 설명합니다. 이러한 보안 메커니즘과 조치에 관한 세부 사항(자세한 공격 설명 포함), 그리고 덜 일반적으로 사용되는 선택 사항에 대한 요구 사항은 4절에서 제공합니다.¶

2.1. redirect 기반 흐름 보호

client의 redirection URI(리디렉션 URI)를 사전 등록된 URI와 비교할 때 authorization server는 정확한 문자열 일치 검사를 사용해야 합니다(MUST). 단, native app의 localhost redirection URI에 있는 port 번호는 예외입니다(4.1.3절 참조). 이 조치는 authorization code(인가 코드)와 access token의 유출을 방지하는 데 기여합니다(4.1절 참조). 또한 mix-up attack(서버 혼동 공격)을 탐지하는 데 도움이 될 수 있습니다(4.4절 참조).¶

client와 authorization server는 query parameter에서 얻은 임의의 URI로 사용자의 브라우저를 전달하는 URL(open redirector)을 노출해서는 안 됩니다(MUST NOT). 이는 4.11절에서 설명합니다. open redirector는 authorization code와 access token의 외부 유출을 가능하게 할 수 있습니다.¶

client는 Cross-Site Request Forgery(CSRF(교차 사이트 요청 위조))를 방지해야 합니다(MUST). 여기서 CSRF란 authorization server가 아니라 악의적인 제3자로부터 시작되는 redirection endpoint(리디렉션 엔드포인트) 대상 요청을 말합니다(자세한 내용은 4.4.1.8절, [RFC6819] 참조). authorization server가 Proof Key for Code Exchange(PKCE) [RFC7636]를 지원함을 확인한 client는 PKCE가 제공하는 CSRF 보호에 의존해도 됩니다(MAY). OpenID Connect 흐름에서는 nonce parameter가 CSRF 보호를 제공합니다. 그 외의 경우에는 state parameter로 전달되며 user agent(사용자 에이전트)에 안전하게 바인딩된 일회용 CSRF token을 CSRF 보호에 사용해야 합니다(MUST)(4.7.1절 참조).¶

OAuth client가 둘 이상의 authorization server와 상호작용할 수 있다면 mix-up attack(4.4절 참조)에 대한 방어가 필수입니다(REQUIRED). 이를 위해 client에 다음을 권고합니다(SHOULD).¶

  • iss parameter를 [RFC9207]에 따른 대응책으로 사용하거나,¶
  • authorization response의 iss 값에 기반한 대체 대응책을 사용합니다. 예를 들어 ID Token의 iss claim을 포함하는 [OpenID.Core] 응답이나 [OpenID.JARM] 응답의 해당 값을 사용할 수 있으며, 그 값은 [RFC9207]에 설명된 대로 처리합니다.¶

이러한 선택지를 사용할 수 없다면 client는 그 대신 서로 다른 redirection URI를 사용하여 authorization endpoint와 token endpoint를 식별할 수 있습니다(MAY). 이는 4.4.2절에 설명되어 있습니다.¶

사용자 자격 증명이 포함되어 있을 수 있는 요청을 리디렉션하는 authorization server는 이러한 사용자 자격 증명이 실수로 전달되지 않도록 해야 합니다(MUST). 자세한 내용은 4.12절을 참조하세요.¶

2.1.1. Authorization Code Grant

client는 다음 선택지 중 하나를 사용하여 authorization code injection(인가 코드 주입) 공격과 authorization code의 오용을 방지해야 합니다(MUST). 공격에 대해서는 4.5절을 참조하세요.¶

  • public client(공개 클라이언트)는 이를 위해 PKCE를 사용해야 합니다(MUST) [RFC7636]. 그 이유는 4.5.3.1절에 설명되어 있습니다.¶
  • confidential client(기밀 클라이언트)에는 PKCE [RFC7636] 사용을 권고합니다(RECOMMENDED). PKCE는 4.5.3.1절에 설명된 대로 authorization code의 오용과 주입을 강력하게 방어하기 때문입니다. 또한 부수적인 효과로, 4.7.1절에 설명된 강력한 공격자가 존재하더라도 CSRF를 방지합니다.¶
  • 4.5.3.2절에 설명된 추가 예방 조치를 취하면 confidential OpenID Connect [OpenID.Core] client는 그 대신 다음 항목을 사용할 수 있습니다(MAY): nonce 매개변수와 ID Token의 해당 Claim입니다.¶

어느 경우든 PKCE challenge 또는 OpenID Connect nonce는 transaction별로 고유해야 하며, client 및 해당 transaction이 시작된 user agent에 안전하게 바인딩되어야 합니다(MUST). authorization server는 PKCE challenge 또는 OpenID Connect nonce에 상수 값이 사용되는 것을 탐지하고 방지하기 위해 합리적인 노력을 기울이는 것이 바람직합니다.¶

참고: PKCE는 네이티브 앱을 보호하기 위한 메커니즘으로 설계되었지만, 이 권고는 웹 애플리케이션을 포함한 모든 종류의 OAuth client에 적용됩니다.¶

PKCE를 사용하는 경우, client는 authorization request에서 PKCE verifier를 노출하지 않는 PKCE code challenge 방식을 사용하는 것이 좋습니다(SHOULD). 그렇지 않으면 authorization request를 읽을 수 있는 공격자((A4) 공격자에 대해서는 3절 참조)가 PKCE가 제공하는 보안을 무력화할 수 있습니다. 현재 이러한 방식은 S256뿐입니다.¶

authorization server는 PKCE를 지원해야 합니다(MUST) [RFC7636].¶

client가 authorization request에 유효한 PKCE code_challenge 매개변수를 보내면, authorization server는 다음 사항을 강제해야 합니다(MUST): token endpoint에서 code_verifier가 올바르게 사용되어야 합니다.¶

authorization server는 다음 사항을 보장하여 PKCE downgrade 공격을 완화해야 합니다(MUST): code_verifier 매개변수를 포함한 token request는 authorization request에 code_challenge 매개변수가 있었던 경우에만 수락합니다. 자세한 내용은 4.8.2절을 참조하세요.¶

authorization server는 자신의 PKCE 지원 여부를 탐지할 수 있는 방법을 제공해야 합니다(MUST). authorization server에는 다음 사항을 권고합니다(RECOMMENDED): 지원하는 PKCE challenge 방식들을 담은 code_challenge_methods_supported 요소를 Authorization Server Metadata [RFC8414]에 게시합니다(client는 이를 통해 PKCE 지원 여부를 탐지할 수 있습니다). authorization server는 그 대신 배포 환경별 방법을 제공하여 authorization server의 PKCE 지원을 보장하거나 확인할 수 있습니다(MAY).¶

2.1.2. Implicit Grant

implicit grant(response type이 token인 경우)와 authorization server가 authorization response에서 access token을 발급하게 하는 그 밖의 response type은 4.1절, 4.2절, 4.3절 및 4.6절에 설명된 access token 유출 및 access token 재전송에 취약합니다.¶

또한 access token이 authorization response에서 발급되는 경우에는, 2.2절에서 권고하는 것처럼 access token을 특정 client에 바인딩하는 표준화된 sender-constraining 방식이 없습니다. 따라서 공격자가 유출되거나 도난당한 access token을 resource endpoint에서 사용할 수 있습니다.¶

이러한 문제를 피하기 위해, client는 다음 방식들을 사용하지 않는 것이 좋습니다(SHOULD NOT): implicit grant(response type이 token인 경우) 또는 authorization response에서 access token을 발급하는 그 밖의 response type입니다. 다만 authorization response의 access token injection(액세스 토큰 주입)을 방지하고 앞서 언급한 token 유출 경로들을 완화한 경우는 예외입니다.¶

client는 그 대신 다음 response type을 사용하는 것이 좋습니다(SHOULD): code(즉, authorization code grant type)를 2.1.1절에 명시된 대로 사용하거나, code id_token response type처럼 authorization server가 token response에서 access token을 발급하게 하는 다른 response type을 사용합니다. 이를 통해 authorization server는 공격자의 재전송 시도를 탐지할 수 있으며, access token이 URL에 노출되지 않으므로 일반적으로 공격 표면이 줄어듭니다. 또한 authorization server가 발급한 token에 sender constraint를 적용할 수 있게 됩니다(2.2절 참조).¶

2.2. Token 재전송 방지

2.2.1. Access Token

sender-constrained access token은 access token의 사용 범위를 특정 발신자로 한정합니다. 수신자(예: resource server)가 해당 token을 수락하려면, 그 발신자는 특정 비밀을 알고 있음을 먼저 입증해야 합니다.¶

authorization server와 resource server는 도난당하거나 유출된 access token의 오용을 방지하기 위해 access token에 sender constraint를 적용하는 메커니즘을 사용하는 것이 좋습니다(SHOULD). 이러한 메커니즘으로는 OAuth 2.0용 mutual TLS [RFC8705] 또는 OAuth 2.0 Demonstrating Proof of Possession(DPoP) [RFC9449]가 있습니다(4.10.1절 참조).¶

2.2.2. Refresh Token

public client용 refresh token에는 sender constraint를 적용하거나 refresh token rotation(리프레시 토큰 교체)을 사용해야 합니다(MUST). 이는 4.14절에 설명되어 있습니다. [RFC6749]는 이미 confidential client용 refresh token을 발급 대상인 client만 사용할 수 있도록 의무화하고 있습니다.¶

2.3. Access Token 권한 제한

access token에 연결된 권한은 해당 애플리케이션이나 사용 사례에 필요한 최소한으로 제한하는 것이 좋습니다(SHOULD). 이렇게 하면 client가 resource owner가 인가한 권한을 넘어서는 것을 방지합니다. 또한 사용자가 해당 보안 정책에 따라 인가받은 권한을 넘어서는 것도 방지합니다. 권한 제한은 access token 유출의 영향을 줄이는 데도 도움이 됩니다.¶

특히 access token의 audience(수신 대상)는 특정 resource server로 제한하거나, 이것이 가능하지 않다면 소수의 resource server로 제한하는 것이 좋습니다(SHOULD). 이를 구현하기 위해 authorization server는 access token을 특정 resource server들과 연결하며, 모든 resource server는 각 요청에 대해 함께 전송된 access token이 바로 그 resource server에서 사용하도록 의도된 것인지 검증할 의무가 있습니다. 그렇지 않다면 resource server는 해당 요청의 처리를 거부해야 합니다(MUST). aud claim은 [RFC9068]에 정의되어 있으며, access token의 audience를 제한하는 데 사용할 수 있습니다(MAY). client와 authorization server는 접근하려는 resource server를 정하기 위해 다음 매개변수를 활용할 수 있습니다(MAY): scope 또는 resource이며, 각각 [RFC6749]와 [RFC8707]에 명시되어 있습니다.¶

또한 access token은 특정 resource 및 resource server나 resource에 대한 특정 동작으로 제한하는 것이 좋습니다(SHOULD). 이를 구현하기 위해 authorization server는 access token을 해당 resource 및 동작들과 연결하며, 모든 resource server는 각 요청에 대해 함께 전송된 access token이 바로 그 resource에서 바로 그 동작을 수행하도록 의도된 것인지 검증할 의무가 있습니다. 그렇지 않다면 resource server는 해당 요청의 처리를 거부해야 합니다. client와 authorization server는 해당 resource 및/또는 동작을 정하기 위해 다음 매개변수를 활용할 수 있습니다(MAY): scope는 [RFC6749]에, authorization_details는 [RFC9396]에 명시되어 있습니다.¶

2.4. Resource Owner Password Credentials Grant

resource owner password credentials(리소스 소유자 비밀번호 자격 증명) grant [RFC6749]는 사용해서는 안 됩니다(MUST NOT). 이 grant type은 resource owner의 자격 증명을 안전하지 않은 방식으로 client에 노출합니다. client가 선의로 동작하더라도 이 grant를 사용하면 공격 표면이 넓어지고(즉, 자격 증명이 authorization server뿐 아니라 더 많은 곳에서 유출될 수 있습니다), 사용자가 authorization server가 아닌 곳에도 자격 증명을 입력하도록 길들이게 됩니다.¶

또한 resource owner password credentials grant는 두 요소 인증이나 여러 단계의 사용자 상호작용이 필요한 인증 절차와 함께 작동하도록 설계되지 않았습니다. 암호학적 자격 증명을 사용하는 인증(WebCrypto [W3C.WebCrypto] 및 WebAuthn [W3C.WebAuthn] 참조)은 보통 특정 웹 origin에 바인딩되므로, 이 grant type으로는 구현할 수 없을 수도 있습니다.¶

2.5. Client 인증

authorization server는 해당 배포 환경에서 client의 자격 증명 발급/등록 절차를 마련하고 그 자격 증명의 기밀성을 보장하는 것이 가능하다면 client 인증을 강제하는 것이 좋습니다(SHOULD).¶

client 인증에는 비대칭 암호 기법을 사용하는 것이 권고됩니다(RECOMMENDED). 예를 들어 OAuth 2.0용 mutual TLS [RFC8705] 또는 [RFC7521] 및 [RFC7523]에 따른 서명된 JWT("Private Key JWT")가 있습니다. 후자는 [OpenID.Core]에서 client 인증 방법 private_key_jwt로 정의됩니다). client 인증에 비대칭 암호 기법을 사용하면 authorization server가 민감한 대칭 키를 저장할 필요가 없으므로, 이러한 방법은 키 유출에 더 강합니다.¶

2.6. 기타 권고 사항

OAuth Authorization Server Metadata [RFC8414]를 사용하면 OAuth 배포 환경의 보안을 개선하는 데 도움이 될 수 있습니다.¶

  • 이를 통해 규격을 준수하는 소프트웨어 라이브러리가 보안 기능과 그 밖의 새로운 OAuth 기능을 자동으로 활성화할 수 있도록 보장합니다.¶
  • 잘못 구성할 가능성을 줄여 줍니다. 예를 들어 endpoint URL을 잘못 구성하거나(공격자에게 속한 URL일 수 있습니다), 보안 기능을 잘못 구성하는 경우가 있습니다.¶
  • 암호학적 키의 교체를 용이하게 하고 cryptographic agility를 보장하는 데 도움이 될 수 있습니다.¶

따라서 다음과 같이 하는 것이 권고됩니다(RECOMMENDED). authorization server는 [RFC8414]에 따라 OAuth Authorization Server Metadata를 공개하고, client는 이 Authorization Server Metadata를 사용할 수 있는 경우 이를 이용해 자체 구성을 수행합니다.¶

4.15.1절에서 설명하는 조건에서는 authorization server가 다음을 허용하지 않는 것이 좋습니다(SHOULD NOT). client가 자신의 client_id 또는 실제 resource owner와 혼동을 일으킬 수 있는 다른 claim에 영향을 주도록 허용하는 것입니다.¶

client와 resource server 사이에서는 end-to-end TLS를 사용하는 것이 권고되며(RECOMMENDED), 이는 [BCP195]에 따른 사용을 의미합니다. 중간 장치에서 TLS 트래픽을 종단해야 하는 경우에는 추가 보안 지침을 위해 4.13절을 참조하십시오.¶

인가 응답은 암호화되지 않은 네트워크 연결로 전송해서는 안 됩니다(MUST NOT). 이를 위해 authorization server는 http scheme을 사용하는 redirection URI를 허용해서는 안 됩니다(MUST NOT). 이 redirection URI 제한은 7.3절([RFC8252])에서 설명하는 loopback interface redirection을 사용하는 native client에는 적용되지 않습니다.¶

인가 응답을 HTTP redirect 대신 postMessage [WHATWG.postmessage_api]와 같은 브라우저 내 통신 기법으로 보내는 경우, 브라우저 내 메시지의 발신자와 수신자를 모두 엄격하게 검증해야 합니다(MUST). 검증 방법은 4.17절에서 설명합니다.¶

브라우저 기반 client를 지원하기 위해, Token Endpoint, Authorization Server Metadata Endpoint, jwks_uri Endpoint, Dynamic Client Registration Endpoint 등 이러한 client가 직접 접근하는 endpoint는 Cross-Origin Resource Sharing(CORS)을 지원해도 됩니다(MAY). CORS는 [WHATWG.CORS]를 참조하십시오. 그러나 authorization endpoint에서는 CORS를 지원해서는 안 됩니다(MUST NOT). client는 이 endpoint에 직접 접근하지 않고 user agent를 이곳으로 redirect하기 때문입니다.¶

3. 갱신된 OAuth 2.0 공격자 모델

[RFC6819]는 OAuth 배포 환경을 보호해야 하는 위협을 설명하는 위협 모델을 제시합니다. 이 과정에서 [RFC6819]는 공격자와 그 능력에 관해 특정한 가정을 하며, 즉 암묵적으로 공격자 모델을 수립합니다. 아래에서는 이 공격자 모델을 명시적으로 제시하고 갱신·확장하여, 여러 당사자 사이의 잠재적으로 동적인 관계(1절에서 설명)를 고려하고, 새로운 유형의 공격자를 포함하며, 공격자 모델을 더 명확하게 정의합니다.¶

이 문서의 목표는 resource owner가 user agent를 사용하여 authorization server에서 인가를 받는 과정과 이후 resource server에서 access token을 사용하는 과정이, 실질적으로 가능한 한 최소한 다음 공격자로부터 보호되도록 하는 것입니다.¶

(A1)

브라우저와 서버를 포함하여 임의 개수의 네트워크 endpoint를 ("정직한" endpoint 외에) 구축하고 운영할 수 있는 웹 공격자입니다. 웹 공격자는 resource owner가 방문하는 웹사이트를 구축하고, 자신의 user agent를 운영하며, 프로토콜에 참여할 수 있습니다.¶

특히 웹 공격자는 authorization server에 등록된 OAuth client를 운영할 수 있으며, resource owner 및 다른 resource owner가 ("정직한" 서버와 병행하여) 사용할 수 있는 자체 authorization server와 resource server를 운영할 수도 있습니다.¶

웹 공격자가 언제든 사용자를 유인하여 브라우저로 공격자가 선택한 임의의 URI에 접속하게 할 수 있다는 점도 가정해야 합니다. 실제로 이는 여러 방법으로 가능하며, 예를 들어 광고 네트워크에 악성 광고를 삽입하거나 정상적으로 보이는 이메일을 보내는 방법이 있습니다.¶

웹 공격자는 자신의 사용자 자격 증명뿐 아니라 이전에 알아낸 비밀 정보를 사용하여 새 메시지를 만들 수 있습니다. 예를 들어 웹 공격자가 잘못 구성된 redirection URI를 통해 사용자의 authorization code를 알아내면, 그 code를 access token으로 교환하려고 시도할 수 있습니다.¶

그러나 자신을 대상으로 하지 않는 메시지(예: 공격자가 통제하지 않는 authorization server의 URL로 전송된 메시지)는 읽거나 조작할 수 없습니다.¶

(A2)

추가로 프로토콜 참여자들이 통신하는 네트워크를 완전히 통제하는 네트워크 공격자입니다. 메시지가 암호학적 방법(예: TLS)으로 적절하게 보호되는 경우를 제외하면, 이들은 메시지를 도청하고 조작하며 위조할 수 있습니다. 네트워크 공격자는 임의의 메시지를 차단할 수도 있습니다.¶

웹 공격자의 예로 인터넷 서비스 제공자의 고객을 들 수 있다면, 네트워크 공격자의 예로는 인터넷 서비스 제공자 자체, 공용 (Wi-Fi) 네트워크에서 ARP spoofing을 사용하는 공격자, 또는 인터넷 교환 지점에 접근할 수 있는 국가 지원 공격자 등을 들 수 있습니다.¶

앞서 설명한 공격자 (A1)과 (A2)는 OAuth의 형식적 분석 연구 [arXiv.1601.01229]에 사용된 공격자 모델에 부합합니다. 이는 최소한의 공격자 모델입니다. 구현자는 자신의 OAuth 구현 환경에서 가능한 모든 공격자 유형을 고려해야 합니다(MUST). 예를 들어 [arXiv.1901.11520]에서는 token endpoint를 완전히 통제하는 공격자를 포함한 매우 강력한 공격자 모델을 사용합니다. 이는 생태계에서 발생할 수 있는 endpoint 구성 오류의 영향을 모델링한 것이며, 이러한 오류는 2.6절에서 설명하는 authorization server metadata를 사용하여 피할 수 있습니다. 따라서 그러한 공격자는 여기에 나열하지 않습니다.¶

그러나 과거의 OAuth 공격은 특히 다음 유형의 공격자가 중요하다는 것을 보여 주었습니다.¶

(A3)

인가 응답의 내용을 읽을 수는 있지만 수정할 수는 없는 공격자입니다(즉, 인가 응답이 공격자에게 유출될 수 있습니다).¶

이러한 공격의 예로는 open redirector 공격과 mix-up attack(4.4절 참조)이 있으며, client를 속여 공격자가 통제하는 authorization server로 자격 증명을 보내게 합니다.¶

여기에는 다음을 악용하는 공격도 포함됩니다.¶

  • redirect URI에 대한 불충분한 검사(4.1절 참조);¶
  • 서로 다른 앱이 동일한 URI에 자신을 등록할 수 있는 모바일 운영체제의 문제; 그리고¶
  • 브라우저(방문 기록), proxy server 및 운영체제가 저장하거나 로그로 기록하는 URL.¶
(A4)

인가 요청의 내용을 읽을 수는 있지만 수정할 수는 없는 공격자입니다(즉, 위와 같은 방식으로 인가 요청이 공격자에게 유출될 수 있습니다).¶

(A5)

authorization server가 발급한 access token을 획득할 수 있는 공격자입니다. 예를 들어 공격자가 resource server를 침해할 수 있고, 잘못된 구성으로 인해 공격자가 통제하는 resource server에 access token이 전송될 수 있으며, social engineering을 통해 resource owner가 공격자가 통제하는 resource server를 사용하게 할 수도 있습니다. 4.9.2절도 참조하십시오.¶

(A3), (A4), (A5)는 일반적으로 (A1) 또는 (A2)와 함께 나타납니다. 공격자들은 공통의 목표를 달성하기 위해 협력할 수 있습니다.¶

공격자 (A1) 또는 (A2)가 resource owner이거나 그 역할을 할 수 있다는 점에 유의하십시오. 예를 들어 이러한 공격자는 자신의 브라우저를 사용하여, 앞서 설명한 공격 중 어느 하나로 얻은 token이나 authorization code를 client 또는 resource server에서 재전송할 수 있습니다.¶

이 문서는 공격자 (A1)부터 (A5)까지로 인해 발생하는 위협에 초점을 맞춥니다.¶

4. 공격과 완화책

이 절에서는 OAuth 구현에 대한 공격과 가능한 대응책을 자세히 설명합니다. 새로운 권고를 제시하는 경우를 제외하고, [RFC6819]에서 이미 다룬 공격과 완화책은 여기에 나열하지 않습니다.¶

이 절에서는 특정 상황과 프로토콜 옵션에 대해 (2절에 정의된 요구 사항 외에) 추가 요구 사항도 정의합니다.¶

4.1. 불충분한 redirection URI 검증

일부 authorization server는 client가 완전한 redirection URI 대신 redirection URI 패턴을 등록하도록 허용합니다. 그러면 authorization server는 실행 시점에 authorization endpoint의 redirection URI 매개변수 값을 등록된 패턴과 대조합니다. 이 방식으로 client는 추가 redirect URI 매개변수에 트랜잭션 상태를 인코딩하거나, 여러 redirection URI에 대해 하나의 패턴을 등록할 수 있습니다.¶

이 방식은 redirection URI를 정확히 일치시키는 방식보다 구현이 더 복잡하고 관리 중 오류가 발생하기 쉬운 것으로 드러났습니다. 패턴 일치 구현이나 구체적인 구성의 결함을 악용하여 성공한 여러 공격이 실제 환경에서 관찰되었습니다(예: [research.rub2] 참조). redirection URI 검증이 불충분하면 사실상 client 식별 또는 인증이 무력화되고(grant 및 client 유형에 따라 달라집니다), 공격자는 다음 중 한 방법으로 authorization code나 access token을 얻을 수 있습니다.¶

  • user agent를 공격자가 통제하는 URI로 직접 보내거나,¶
  • client의 open redirector와 user agent의 URL fragment 처리 방식을 함께 활용하여 공격자에게 OAuth 자격 증명을 노출합니다.¶

이러한 공격은 다음 하위 절에서 자세히 설명합니다.¶

4.1.1. Authorization Code Grant에 대한 Redirect URI 검증 공격

grant type code를 사용하는 client에 대해서는 다음과 같이 공격이 이루어질 수 있습니다.¶

redirection URL 패턴 https://*.somesite.example/*이 client ID가 s6BhdRkqt3인 client에 등록되어 있다고 가정합니다. 이는 somesite.example의 모든 하위 도메인을 해당 client의 유효한 redirection URI로 허용하려는 의도로, 예를 들면 https://app1.somesite.example/redirect이 있습니다. 그러나 authorization server의 단순한 구현에서는 와일드카드 *를 "도메인 이름에 유효한 모든 문자"가 아니라 "모든 문자"로 해석할 수 있습니다. 따라서 authorization server는 https://attacker.example/.somesite.example를 redirection URI로 허용할 수 있습니다. attacker.example은 악의적인 당사자가 제어할 수도 있는 별개의 도메인인데도 말입니다.¶

그러면 다음과 같이 공격을 수행할 수 있습니다.¶

먼저 공격자는 사용자를 속여, 공격자가 제어하는 페이지(예: https://www.evil.example)를 여는 변조된 URL을 사용자의 브라우저에서 열도록 해야 합니다(공격자 A1에 대해서는 3절 참조).¶

이 URL은 정상 client의 client ID를 사용하여 authorization endpoint에 다음 인가 요청을 시작합니다(줄바꿈은 표시만을 위한 것입니다).¶

GET /authorize?response_type=code&client_id=s6BhdRkqt3&state=9ad67f13
     &redirect_uri=https%3A%2F%2Fattacker.example%2F.somesite.example
     HTTP/1.1
Host: server.somesite.example
¶

authorization server는 redirection URI를 검증하고 client s6BhdRkqt3에 등록된 redirection URL 패턴과 비교합니다. 인가 요청은 처리되어 사용자에게 제시됩니다.¶

사용자가 redirection URI를 보지 못하거나 공격을 알아차리지 못하면 code가 발급되어 즉시 공격자의 도메인으로 전송됩니다. 인가 자동 승인이 활성화되어 있다면([RFC6749]에서는 public client에 이를 권장하지 않습니다), 사용자 상호작용 없이도 공격을 수행할 수 있습니다.¶

공격자가 public client를 사칭하면 해당 token endpoint에서 code를 token으로 교환할 수 있습니다.¶

confidential client의 경우 code 교환에 정상 client의 비밀값을 사용한 인증이 필요하므로 이 공격이 그만큼 쉽게 통하지는 않습니다. 그러나 공격자는 authorization code injection 공격을 수행하여 정상 confidential client가 code를 교환하도록 할 수 있습니다. 4.5절을 참조하십시오.¶

authorization server가 와일드카드를 올바르게 처리하더라도 redirection URI 검증 취약점이 존재할 수 있다는 점에 유의해야 합니다. 예를 들어 client가 redirection URL 패턴 https://*.somesite.example/*을 등록하고 authorization server가 이를 "도메인 somesite.example에 속한 모든 호스트를 가리키는 redirection URI 허용"으로 해석한다고 가정합니다. 공격자가 somesite.example에 호스트나 하위 도메인을 만드는 데 성공하면 정상 client를 사칭할 수 있습니다. 예를 들어 하위 도메인 탈취 공격 [research.udel]이 원인이 될 수 있습니다. 이 공격에서는 오래된 CNAME 레코드(예: external-service.somesite.example)가 더 이상 존재하지 않는 외부 DNS 이름(예: customer-abc.service.example)을 가리키고, 공격자가 이를 장악할 수 있습니다(예: 외부 서비스에 customer-abc로 등록하여).¶

4.1.2. Implicit Grant에 대한 Redirect URI 검증 공격

위에서 설명한 공격은 implicit grant에도 통합니다. 공격자가 인가 응답을 자신이 제어하는 URI로 보낼 수 있다면 access token을 담고 있는 fragment에 직접 접근할 수 있습니다.¶

또한 implicit grant(그리고 response_mode=fragment를 사용하는 다른 grant도 마찬가지이며, 이는 [OAuth.Responses]에 정의되어 있습니다)는 또 다른 종류의 공격을 받을 수 있습니다. 이 공격은 Location 헤더에 fragment가 없으면 user agent가 리디렉션 대상 URL에 fragment를 다시 붙인다는 사실을 이용합니다(17.11절([RFC9110]) 참조). 여기서 설명하는 공격은 access token을 얻기 위해 이러한 동작과 open redirector 역할을 하는 client를 결합합니다(4.11.1절 참조). 이를 통해 매우 제한적인 redirection URI 패턴까지 우회할 수 있지만, 엄격한 URL 일치 검사는 우회할 수 없습니다.¶

client s6BhdRkqt3에 등록된 URL 패턴이 https://client.somesite.example/cb?*이라고 가정합니다. 즉, https://client.somesite.example/cb로 리디렉션할 때 모든 매개변수가 허용됩니다. 안타깝게도 이 client는 open redirector를 노출하고 있습니다. 이 endpoint는 대상 URL을 받는 매개변수 redirect_to를 지원하며, HTTP Location 헤더의 303 리디렉션을 사용해 브라우저를 해당 URL로 보냅니다.¶

이제 다음과 같이 공격을 수행할 수 있습니다.¶

먼저 위와 마찬가지로 공격자는 사용자를 속여, 공격자가 제어하는 페이지(예: https://www.evil.example)를 여는 변조된 URL을 사용자의 브라우저에서 열도록 해야 합니다.¶

그런 다음 웹사이트는 code flow 공격에서와 매우 유사한 인가 요청을 시작합니다. 위와 달리 redirect_to=https://attacker.example를 redirection URI의 매개변수에 인코딩하여 open redirector를 이용하며, response type token을 사용합니다(줄바꿈은 표시만을 위한 것입니다).¶

GET /authorize?response_type=token&state=9ad67f13
    &client_id=s6BhdRkqt3
    &redirect_uri=https%3A%2F%2Fclient.somesite.example
     %2Fcb%26redirect_to%253Dhttps%253A%252F
     %252Fattacker.example%252F HTTP/1.1
Host: server.somesite.example
¶

이어서 redirection URI가 등록된 패턴과 일치하므로 authorization server는 요청을 허용하고, 그 결과로 발급된 access token을 303 리디렉션으로 전송합니다(읽기 쉽도록 일부 응답 매개변수는 생략했습니다).¶

HTTP/1.1 303 See Other
Location: https://client.somesite.example/cb?
          redirect_to%3Dhttps%3A%2F%2Fattacker.example%2Fcb
          #access_token=2YotnFZFEjr1zCsicMWpAA&...
¶

client.somesite.example에서 요청은 open redirector에 도착합니다. 이 endpoint는 redirect 매개변수를 읽고 URL https://attacker.example/로 향하는 HTTP 303 Location 헤더 리디렉션을 발행합니다.¶

HTTP/1.1 303 See Other
Location: https://attacker.example/
¶

client.somesite.example의 redirector가 Location 헤더에 fragment를 포함하지 않으므로 user agent는 원래 fragment #access_token=2YotnFZFEjr1zCsicMWpAA&amp;...를 URL에 다시 붙이고 다음 URL로 이동합니다.¶

https://attacker.example/#access_token=2YotnFZFEjr1z...
¶

그러면 attacker.example에 있는 공격자의 페이지는 fragment에 접근하여 access token을 얻을 수 있습니다.¶

4.1.3. 대응책

패턴 일치를 올바르게 구현하고 관리하는 일의 복잡성은 분명히 보안 문제를 일으킵니다. 따라서 이 문서는 정확한 redirection URI 일치를 사용하여 필요한 로직과 구성을 단순화하도록 권고합니다. 이는 authorization server가 두 URI가 같은지 반드시 확인해야 함을 의미합니다(MUST). 자세한 내용은 6.2.1절([RFC3986]), 단순 문자열 비교를 참조하십시오. 유일한 예외는 localhost URI를 사용하는 네이티브 앱입니다. 이 경우 authorization server는 가변 포트 번호를 반드시 허용해야 합니다(MUST). 이는 7.3절([RFC8252])에 설명되어 있습니다.¶

추가 권고사항은 다음과 같습니다.¶

  • redirection URI를 호스팅하는 웹 서버는 open redirector를 노출해서는 안 됩니다(MUST NOT)(4.11절 참조).¶
  • 브라우저는 Location 헤더의 URL에 fragment가 아직 없는 경우에만 Location 리디렉션 URL에 URL fragment를 다시 붙입니다. 따라서 서버는 브라우저가 리디렉션 URL에 fragment를 다시 붙이지 못하게 할 수 있습니다(MAY). 이를 위해 Location 헤더의 URL에 임의의 fragment 식별자(예: #_)를 붙입니다.¶
  • client는 authorization endpoint에서 access token을 발급하게 하는 response type 대신 authorization code response type을 사용하는 것이 좋습니다(SHOULD). 이는 authorization server와의 교환 과정을 통해 유출된 자격 증명의 재사용에 대한 대응책을 제공하고, access token에 발신자 제약을 적용하여 token 재전송에 대한 대응책을 제공합니다.¶

예를 들어 client 인증과 함께 [RFC9101] 또는 [RFC9126]을 사용하는 경우처럼, redirection URI를 포함하는 인가 요청의 출처와 무결성을 검증할 수 있다면 authorization server는 추가 검사 없이 redirection URI를 신뢰할 수 있습니다(MAY).¶

4.2. Referer 헤더를 통한 자격 증명 유출

인가 요청 URI 또는 인가 응답 URI의 내용은 각각 authorization server 또는 client의 웹사이트에서 유출되어 Referer HTTP 헤더를 통해 의도치 않게 공격자에게 공개될 수 있습니다(10.1.3절([RFC9110]) 참조). 특히 authorization code나 state 값이 이 방식으로 공개될 수 있습니다. 10.1.3절([RFC9110])에서는 이와 다르게 규정하지만, Chromium 프로젝트의 문제(현재는 수정됨) [bug.chromium]에서 볼 수 있듯이 브라우저 구현 문제로 인해 URI fragment로 전달되는 access token에도 같은 일이 일어날 수 있습니다.¶

4.2.1. OAuth client에서의 유출

OAuth client에서 유출이 발생하려면 client가 성공한 인가 요청의 결과로 다음과 같은 페이지를 렌더링해야 합니다.¶

  • 공격자가 제어하는 다른 페이지로 향하는 링크가 포함되어 있고 사용자가 그러한 링크를 클릭하는 경우, 또는¶
  • 제3자 콘텐츠(iframe의 광고, 이미지 등)가 포함된 경우. 예를 들어 페이지에 사용자 생성 콘텐츠(블로그)가 포함된 경우가 이에 해당합니다.¶

브라우저가 공격자의 페이지로 이동하거나 제3자 콘텐츠를 로드하는 즉시 공격자는 인가 응답 URL을 수신하고 code 또는 state(그리고 경우에 따라 access_token)를 추출할 수 있습니다.¶

4.2.2. authorization server에서의 유출

마찬가지로 authorization server의 authorization endpoint에 위와 같은 링크나 제3자 콘텐츠가 포함되어 있다면 공격자는 인가 요청에서 state를 알아낼 수 있습니다.¶

4.2.3. 결과

Referer 헤더를 통해 유효한 code나 access token을 알아낸 공격자는 4.1.1절, 4.5절 및 4.6절에 설명된 공격을 수행할 수 있습니다. 공격자가 state를 알아내면 state를 사용하여 얻는 CSRF 보호가 사라져 4.4.1.8절([RFC6819])에 설명된 CSRF 공격으로 이어집니다.¶

4.2.4. 대응책

OAuth 인가 응답의 결과로 렌더링된 페이지와 authorization endpoint에는 제3자 리소스나 외부 사이트로 향하는 링크를 포함하지 않는 것이 좋습니다(SHOULD NOT).¶

다음 조치는 공격이 성공할 가능성을 더욱 줄입니다.¶

  • 문서에 적절한 Referrer Policy [W3C.webappsec-referrer-policy]를 적용하여("referrer" meta 속성의 일부로 적용하거나 Referrer-Policy 헤더를 설정하여) Referer 헤더를 억제합니다. 예를 들어 응답의 Referrer-Policy: no-referrer 헤더는 그 결과로 생성된 문서에서 시작되는 모든 요청의 Referer 헤더를 완전히 억제합니다.¶
  • authorization endpoint에서 access token을 발급하게 하는 response type 대신 authorization code를 사용합니다.¶
  • authorization code를 confidential client 또는 PKCE challenge에 바인딩합니다. 이 경우 공격자에게는 code 교환을 요청하는 데 필요한 secret이 없습니다.¶

  • 4.1.2절([RFC6749])에 설명된 대로, authorization server는 authorization code가 token endpoint에서 처음 사용된 후 해당 code를 무효화해야 합니다(MUST). 예를 들어, 정상 client가 code를 교환한 후 authorization server가 이를 무효화하면, 공격자는 나중에 이 code를 교환할 수 없습니다.¶

    공격자가 정상 client보다 먼저 code를 token으로 교환하는 데 성공하면 이 조치로는 공격을 완화할 수 없습니다. 따라서 [RFC6749]는 code를 두 번 교환하려는 시도가 발생하면 authorization server가 그 code를 기반으로 이전에 발급한 모든 token을 폐기할 것을 추가로 권고합니다(SHOULD).¶

  • client는 state 값이 redirection endpoint에서 처음 사용된 후 이를 무효화하는 것이 좋습니다(SHOULD). 이렇게 구현한 상태에서 공격자가 client 웹사이트의 Referer header를 통해 token을 받더라도, state는 이미 사용되어 client에 의해 무효화되었으므로 공격자가 다시 사용할 수 없습니다. (state가 authorization server의 웹사이트에서 유출되는 경우에는 도움이 되지 않습니다. 이때는 state가 아직 client의 redirection endpoint에서 사용되지 않았기 때문입니다.)¶

  • authorization response에 redirect 대신 form post response mode를 사용합니다([OAuth.Post] 참조).¶

4.3. 브라우저 방문 기록을 통한 credential 유출

authorization code와 access token이 브라우저의 방문 URL 기록에 남아, 아래에 설명하는 공격이 가능해질 수 있습니다.¶

4.3.1. 브라우저 방문 기록에 남은 authorization code

브라우저가 제공자의 authorization endpoint에서 보낸 redirect에 따라 client.example/redirection_endpoint?code=abcd로 이동하면, authorization code가 포함된 URL이 브라우저 방문 기록에 남을 수 있습니다. 기기에 접근할 수 있는 공격자는 이 code를 획득하여 replay를 시도할 수 있습니다.¶

대응책:¶

  • 4.4.1.1절([RFC6819]) 및 4.5절에 설명된 authorization code replay 방지를 적용합니다.¶
  • authorization response에 redirect 대신 form post response mode를 사용합니다([OAuth.Post] 참조).¶

4.3.2. 브라우저 방문 기록에 남은 access token

이미 token을 보유한 client나 웹사이트가 의도적으로 provider.com/get_user_profile?access_token=abcdef와 같은 페이지로 이동하면 access token이 브라우저 방문 기록에 남을 수 있습니다. [RFC6750]는 이러한 방식을 지양하고 header를 통해 token을 전송하도록 권고하지만, 실제로는 웹사이트가 query parameter로 access token을 전달하는 경우가 많습니다.¶

implicit grant의 경우에도 제공자의 authorization endpoint에서 보낸 redirect로 인해 client.example/redirection_endpoint#access_token=abcdef와 같은 URL이 브라우저 방문 기록에 남을 수 있습니다.¶

대응책:¶

  • client는 MUST NOT 요구 사항에 따라 2.3절([RFC6750])에 설명된 방식으로 URI query parameter에 access token을 넣어 전달해서는 안 됩니다. 이를 위해 authorization code grant나 form post response mode [OAuth.Post]와 같은 다른 OAuth response mode를 사용할 수 있습니다.¶

4.4. Mix-Up attack

OAuth client가 둘 이상의 authorization server와 상호작용하고 그중 적어도 하나가 공격자의 통제하에 있는 상황에서는 mix-up attack이 발생할 수 있습니다. 예를 들어 공격자가 dynamic registration을 사용하여 자신의 authorization server에 client를 등록하거나, authorization server가 침해된 경우가 이에 해당합니다.¶

이 공격의 목표는 침해되지 않은 authorization server의 authorization code 또는 access token을 획득하는 것입니다. 공격자는 client를 속여 이러한 credential을 침해되지 않은 authorization server/resource server의 해당 endpoint에서 사용하는 대신 침해된 authorization server(공격자)로 보내게 함으로써 이 목표를 달성합니다.¶

4.4.1. 공격 설명

여기서는 [arXiv.1601.01229]에 따라 설명하며, 아래에서 이 공격의 변형을 개략적으로 소개합니다.¶

전제 조건: 이 변형 공격이 성립하려면 다음을 가정합니다.¶

  • 여러 authorization server를 대상으로 implicit grant 또는 authorization code grant를 사용하며, 이 중 하나는 “정직한” 서버(H-AS)로 간주하고 다른 하나는 공격자가 운영하는 서버(A-AS)입니다. 또한,¶
  • client는 사용자가 선택한 authorization server를 사용자 브라우저에 바인딩된 session에 저장하고, 각 authorization server에 동일한 redirection URI를 사용합니다.¶

이하에서는 client가 H-AS(URI: https://honest.as.example, client ID: 7ZGZldHQ)와 A-AS(URI: https://attacker.example, client ID: 666RVZJTA)에 등록되어 있다고 추가로 가정합니다. 다음 예시에 나오는 URL은 설명의 편의를 위해 공격과 관련된 parameter만 포함하도록 줄였습니다.¶

authorization code grant에 대한 공격:¶

  1. 사용자가 A-AS를 사용하여 grant를 시작하도록 선택합니다(예: client 웹사이트의 버튼 클릭).¶
  2. client는 사용자가 “A-AS”를 선택했다는 사실을 사용자의 session에 저장하고, URL https://attacker.example/authorize?response_type=code&client_id=666RVZJTA가 포함된 Location header로 사용자를 A-AS의 authorization endpoint로 redirect합니다.¶
  3. 사용자의 브라우저가 공격자의 authorization endpoint로 이동하면, 공격자는 즉시 브라우저를 H-AS의 authorization endpoint로 redirect합니다. 공격자는 authorization request에서 A-AS에 등록된 client의 client ID를 H-AS에 등록된 client의 ID로 바꿉니다. 따라서 브라우저는 다음을 가리키는 Location header가 포함된 redirection(303 See Other)을 받습니다. https://honest.as.example/authorize?response_type=code&client_id=7ZGZldHQ¶

  4. 사용자가 client에 H-AS의 자신의 resource에 접근할 권한을 부여합니다. (주의 깊은 사용자는 이 시점에서 자신이 H-AS가 아니라 A-AS를 사용하려 했음을 알아차릴 수 있습니다. 아래에 나열된 첫 번째 변형 공격에는 이러한 제약이 없습니다.) H-AS는 code를 발급하고 브라우저를 통해 client에 돌려보냅니다.¶

  5. client는 여전히 이 code가 A-AS에서 발급되었다고 가정하므로, A-AS의 token endpoint에서 code 교환을 시도합니다.¶

  6. 따라서 공격자는 code를 획득하며, 이를 access token으로 교환하거나(public client의 경우) 4.5절에 설명된 authorization code injection attack을 수행할 수 있습니다.¶

변형:¶

  • 가로채기를 동반한 Mix-Up: 이 변형은 공격자가 공격자(A2)와 같이(3절 참조), 사용자의 브라우저와 client 사이의 첫 번째 요청/응답 쌍을 가로채고 조작할 수 있을 때만 성립합니다. 이 요청/응답 쌍에서 사용자는 특정 authorization server를 선택하고, 이어서 client가 사용자를 해당 authorization server로 redirect합니다. 예를 들어, 이러한 능력은 사용자의 client 연결에 대한 attacker-in-the-middle attack으로 확보될 수 있습니다. 이 공격에서 사용자는 H-AS로 flow를 시작합니다. 공격자는 이 요청을 가로채 사용자의 선택을 A-AS로 바꿉니다. 나머지 공격은 위의 2단계 및 그 이후와 같이 진행됩니다.¶
  • Implicit Grant: implicit grant에서는 공격자가 4단계에서 code 대신 access token을 받습니다. client가 A-AS의 userinfo endpoint([OpenID.Core]에 정의됨)에 요청하거나 공격자의 resource server에 요청할 때, 공격자의 authorization server가 access token을 받습니다(client가 A-AS와의 flow를 완료했다고 믿기 때문입니다).¶
  • AS별 Redirect URI: client가 authorization server마다 다른 redirection URI를 사용하고, 선택된 authorization server를 사용자의 session에 저장하지 않으며, authorization server가 redirection URI를 적절히 검사하지 않는 경우, 공격자는 “Cross Social-Network Request Forgery”라는 공격을 수행할 수 있습니다. 이러한 공격은 실제로 관찰되었습니다. 자세한 내용은 [research.jcs_14]를 참조하십시오.¶
  • OpenID Connect: 일부 변형은 OpenID Connect를 공격하는 데 사용할 수 있습니다. 이러한 공격에서 공격자는 OpenID Connect Discovery [OpenID.Discovery] 메커니즘의 기능을 악용하거나 access token 또는 ID Token을 replay하여 mix-up attack을 수행합니다. 이 공격들은 [arXiv.1704.08539]의 부록 A와 [arXiv.1508.04324v2]의 6절(“Malicious Endpoints Attacks”)에 자세히 설명되어 있습니다.¶

4.4.2. 대응책

OAuth client가 하나의 authorization server와만 상호작용할 수 있다면 mix-up 방어는 필요하지 않습니다. 그러나 OAuth client가 둘 이상의 authorization server와 상호작용하는 상황에서는 client가 mix-up attack을 방지해야 합니다(MUST). 아래에서 두 가지 서로 다른 방법을 설명합니다.¶

두 방어 방법 모두에서 client는 각 authorization request를 보낸 issuer를 요청별로 저장하고, 이 정보를 user agent에 바인딩해야 합니다(MUST). issuer는 관련 metadata를 통해 해당 flow에서 사용할 authorization endpoint와 token endpoint의 조합을 나타내는 추상적 식별자 역할을 합니다. issuer identifier를 사용할 수 없는 경우(예를 들어 OAuth Authorization Server Metadata [RFC8414]와 OpenID Connect Discovery [OpenID.Discovery]를 모두 사용하지 않는 경우)에는 이 tuple을 나타내는 다른 고유 식별자나 tuple 자체를 대신 사용할 수 있습니다. 설명을 간결하게 하기 위해 이하에서는 이러한 배포 환경별 식별자도 issuer(또는 issuer identifier)에 포함하여 지칭합니다.¶

authorization server URL을 저장하는 것만으로는 mix-up attack을 식별하기에 충분하지 않다는 점이 중요합니다. 공격자는 침해되지 않은 authorization server의 authorization endpoint URL을 “자신의” authorization server URL로 선언하면서, token endpoint는 자신의 통제하에 있는 것으로 선언할 수 있습니다.¶

4.4.2.1. Issuer 식별을 통한 Mix-Up 방어

이 방어 방법에서는 authorization server가 authorization response에 자신의 issuer identifier를 포함하여 client에 보내야 합니다. authorization response를 받으면 client는 수신한 issuer identifier를 저장된 issuer identifier와 비교해야 합니다(MUST). 일치하지 않으면 client는 상호작용을 중단해야 합니다(MUST).¶

이 issuer identifier를 client에 전달하는 방법에는 여러 가지가 있습니다.¶

  • 예를 들어 issuer 정보는 별도의 response parameter iss를 통해 전달할 수 있으며, 이 parameter는 [RFC9207]에 정의되어 있습니다.¶
  • OpenID Connect를 사용하고 authorization response로 ID Token이 반환되는 경우, client는 ID Token의 iss claim을 평가할 수 있습니다.¶

두 경우 모두 iss 값을 [RFC9207]에 따라 평가해야 합니다(MUST).¶

이 방어 방법은 issuer 정보를 전달하기 위해 새로운 OAuth 기능을 배포해야 할 수 있지만, mix-up에 대한 견고하면서도 비교적 간단한 방어 방법입니다.¶

4.4.2.2. 서로 다른 Redirect URI를 통한 Mix-Up 방어

이 방어 방법을 사용하려면 client는 상호 작용하는 각 issuer마다 서로 다른 redirection URI를 사용해야 합니다(MUST).¶

client는 해당 issuer에 고유한 redirection URI를 authorization response가 수신된 URI와 비교하여, 올바른 issuer로부터 authorization response를 받았는지 확인해야 합니다(MUST). 일치하지 않으면 client는 흐름을 중단해야 합니다(MUST).¶

이 방어 방법은 기존 OAuth 기능을 기반으로 하지만, 일부 open banking 체계처럼 client가 여러 issuer를 이용하기 위해 한 번만 등록하는 시나리오에는 사용할 수 없습니다. 또한 client 등록과 긴밀하게 결합되어 있어 자동으로 배포하기가 더 어렵습니다.¶

또한 공격자는 client가 공격자의 authorization server에 할당한 redirect URI를 사용하여 "정직한" authorization server에 새 client를 등록함으로써, 이 방어 방법이 제공하는 보호를 우회할 수도 있습니다. 그런 다음 client ID를 자신이 새로 만든 client의 client ID로 바꾸어 앞서 설명한 공격을 수행할 수 있습니다.¶

따라서 이 방어 방법은 다른 선택지가 없는 경우에만 사용하는 것이 좋습니다(SHOULD).¶

4.5. Authorization Code Injection

authorization response에 포함된 authorization code에 접근하게 된 공격자(공격자 (A3), 3절 참조)는 해당 authorization code를 access token으로 교환하거나 그 밖의 방식으로 이용하려고 시도할 수 있습니다.¶

authorization code가 public client를 위해 생성된 경우, 공격자는 이 authorization code를 authorization server의 token endpoint로 보내 access token을 얻을 수 있습니다. 이 공격은 4.4.1.1절([RFC6819])에 설명되어 있습니다.¶

confidential client의 경우 또는 일부 특수한 상황에서는, 공격자가 다음에 설명하는 authorization code injection attack을 수행할 수 있습니다.¶

authorization code injection attack에서 공격자는 탈취한 authorization code를 자신과 client 사이의 세션에 주입하려고 시도합니다. 그 목적은 client에서의 공격자 세션을 피해자의 리소스나 신원에 연결하여, 공격자가 피해자의 리소스에 적어도 제한적으로 접근할 수 있게 하는 것입니다.¶

confidential client의 client 인증을 우회하는 것 외에도, 이 공격의 활용 사례에는 다음이 포함됩니다.¶

  • 공격자가 해당 client의 특정 기능에 접근하려는 경우입니다. 예를 들어 공격자가 특정 앱이나 웹사이트에서 피해자를 사칭하려고 합니다.¶
  • authorization server 또는 resource server가 공격자가 직접 접근할 수 없는 특정 네트워크로 제한되어 있는 경우입니다.¶

이러한 특수한 경우를 제외하면, public client를 위해 생성된 code에 대한 authorization code injection은 대개 공격자의 관심 대상이 아닙니다. 앞서 설명했듯이 code를 token endpoint로 보내는 것이 더 간단하면서도 더 강력한 공격이기 때문입니다.¶

4.5.1. 공격 설명

authorization code injection attack은 다음과 같이 이루어집니다.¶

  1. 공격자가 authorization code를 획득합니다(공격자 (A3), 3절 참조). 나머지 공격 과정에는 web attacker (A1)의 능력만 필요합니다.¶
  2. 공격자가 자신의 장치에서 정상 client와 일반적인 OAuth 인가 절차를 시작합니다.¶
  3. 공격자가 authorization server에서 정상 client로 보내는 응답의 새로 생성된 authorization code를 탈취한 authorization code로 바꿉니다. 이 응답은 공격자의 장치를 통과하므로, 공격자는 authorization response를 가로채고 조작할 수 있는 어떤 도구든 이 목적으로 사용할 수 있습니다. 공격자가 네트워크를 제어할 필요는 없습니다.¶
  4. 정상 client가 code를 redirect_uri 및 자신의 client ID와 client secret(또는 다른 client 인증 수단)과 함께 authorization server의 token endpoint로 보냅니다.¶
  5. authorization server가 client secret, 해당 client에 code가 발급되었는지 여부, 실제 redirection URI가 redirect_uri 매개변수와 일치하는지 여부를 확인합니다([RFC6749] 참조).¶
  6. 모든 검사가 성공하고 authorization server가 client에 access token과 그 밖의 token을 발급합니다. 이제 공격자는 자신과 정상 client 사이의 세션을 피해자의 리소스 및/또는 신원과 연결한 상태입니다.¶

4.5.2. 논의

분명히, code가 공격자가 설정한 client처럼 다른 client ID에 발급되었다면 확인 단계(5단계)의 검사는 실패합니다. 또한 authorization code가 일회용이며 정상 사용자가 이미 교환했다면 검사에 실패합니다.¶

authorization server가 authorization request에서 사용된 완전한 redirection URI를 저장하고 이를 redirect_uri 매개변수와 비교한다면, 조작된 redirection URI를 통해 얻은 code를 주입하려는 시도 역시 탐지될 것으로 예상됩니다.¶

4.1.3절([RFC6749])은 authorization server가 다음을 수행하도록 요구합니다.¶

4.1.1절에 설명된 대로 최초 authorization request에 "redirect_uri" 매개변수가 포함되어 있었다면 "redirect_uri" 매개변수가 존재하는지 확인하고, 포함되어 있다면 두 값이 동일한지 확인합니다.¶

4.5.1절에 설명된 공격 시나리오에서 정상 client는 authorization request에 항상 사용하는 올바른 redirection URI를 사용할 것입니다. 그러나 이 URI는 공격자가 사용한 변조된 redirection URI와 일치하지 않을 것입니다(일치한다면 redirect가 공격자의 페이지에 도착하지 않을 것입니다). 따라서 authorization server는 공격을 탐지하고 code 교환을 거부할 것입니다.¶

이 검사는 다음과 같은 특정 조건이 충족되면, 다른 장치에 있는 동일 client의 다른 인스턴스에서 획득한 authorization code를 주입하려는 시도도 탐지할 수 있습니다.¶

  • redirection URI 자체에 nonce 또는 다른 종류의 일회용 비밀 데이터가 포함되어 있고,¶
  • client가 이 데이터를 해당 client 인스턴스에 바인딩한 경우입니다.¶

그러나 이 접근 방식은 authorization endpoint에서 redirect URI의 정확한 일치를 강제한다는 취지와 충돌합니다. 더욱이 provider가 이 단계에서 redirect_uri 검사 요구 사항을 매우 자주 무시한다는 사실이 관찰되었습니다. 이는 명세를 읽었을 때 해당 검사가 보안에 결정적으로 중요해 보이지 않기 때문일 수 있습니다.¶

다른 provider는 redirect_uri 매개변수를 등록된 redirection URI 패턴과 패턴 매칭하기만 합니다. 이렇게 하면 authorization server가 매 transaction마다 실제 redirect URI와 해당 authorization code 사이의 연결을 저장할 필요가 없어집니다. 그러나 이러한 검사는 변조된 redirection URI를 고려하지 않으므로, 명세의 취지를 충족하지 못하는 것이 분명합니다. 따라서 이러한 배포 환경에서는 정상 client의 client_id를 사용하거나 다른 장치의 정상 client를 이용하여 획득한 authorization code를 주입하려는 어떠한 시도도 탐지되지 않습니다.¶

또한 4.1.3절([RFC6749])에 정의된 요구 사항은 client 구현의 복잡성을 높이는 것으로 여겨집니다. client가 token endpoint를 호출하기 위해 올바른 redirection URI를 저장하거나 재구성해야 하기 때문입니다.¶

정상 client가 token endpoint에서 인증하므로, 비대칭 방식의 client 인증으로는 이 공격을 막을 수 없습니다.¶

따라서 이 문서는 대신 다음에 설명하는 메커니즘 중 하나를 사용하여, 특정 transaction의 맥락에서 모든 authorization code를 특정 장치(또는 특정 user agent)의 특정 client 인스턴스에 바인딩할 것을 권장합니다.¶

4.5.3. 대응책

authorization code를 client 인스턴스에 바인딩하는 데는 다음과 같은 두 가지 유용한 기술적 해결책이 있습니다.¶

4.5.3.1. PKCE

[RFC7636]에 명시된 PKCE 메커니즘은 원래 native app을 보호하기 위해 설계되었지만, 이 공격의 대응책으로도 사용할 수 있습니다. 공격자가 authorization code 주입을 시도하면 code_verifier 검사가 실패합니다. client는 자신의 올바른 verifier를 사용하지만, code는 이 verifier와 일치하지 않는 code_challenge에 연결되어 있기 때문입니다.¶

PKCE는 authorization code injection attack을 방어할 뿐 아니라 public client를 위해 생성된 authorization code도 보호합니다. PKCE는 공격자가 code_verifier를 알지 못하면 authorization server의 token endpoint에서 탈취한 authorization code를 교환할 수 없도록 보장합니다.¶

4.5.3.2. Nonce

OpenID Connect의 기존 nonce 매개변수는 authorization code injection attack을 방어할 수 있습니다. nonce 값은 일회용이며 client가 생성합니다. client는 이를 user agent 세션에 바인딩하고 OpenID Provider(OP)에 보내는 최초 요청에 함께 전송하도록 되어 있습니다. OP는 수신한 nonce 값을 token endpoint에서 code를 교환하는 과정의 일부로 발급되는 ID Token에 넣습니다. 공격자가 authorization response에 authorization code를 주입하면, client 세션의 nonce 값과 token endpoint에서 받은 ID Token의 nonce 값이 일치하지 않아 공격이 탐지됩니다. 여기서는 공격자가 해당 authorization code를 탈취한 피해자의 장치에서 user agent 상태를 획득할 수 없다고 가정합니다.¶

이 대응책은 client가 token endpoint에서 얻은 ID Token의 nonce 매개변수를 올바르게 검사하고, 이 검사가 성공하기 전까지는 발급된 token을 하나도 사용하지 않는 경우에만 작동한다는 점에 유의해야 합니다. 보다 구체적으로, nonce 매개변수를 사용하여 code injection을 방어하는 client는 다음을 수행합니다.¶

  1. token endpoint에서 얻은 ID Token의 nonce를 검증해야 합니다(MUST). authorization response에서 다른 ID Token을 얻었더라도(예: response_type=code+id_token) 마찬가지입니다.¶
  2. 해당 검사가 성공할 때까지는 모든 token(ID Token과 access token)을 무시하고, 다른 어떤 목적으로도 사용해서는 안 됩니다(MUST).¶

nonce는 public client의 authorization code를 보호하지 않는다는 점에 유의해야 합니다. 공격자는 authorization code injection 공격을 수행할 필요 없이, 탈취한 authorization code로 token endpoint를 직접 호출할 수 있기 때문입니다.¶

4.5.3.3. 기타 해결책

state를 code에 바인딩하거나, 암호학적 수단으로 code에 sender constraint를 적용하거나, 인스턴스별 client credentials(클라이언트 자격 증명)를 사용하는 등의 다른 해결책도 생각할 수 있습니다. 하지만 이러한 방법은 지원이 부족하며 새로운 보안 요구 사항을 수반합니다.¶

PKCE는 이 문서 작성 시점에 사용할 수 있으므로 OAuth client에 가장 명백한 해결책이며, OpenID Connect client에는 nonce가 적합합니다.¶

4.5.4. 한계

공격자가 피해자의 authorization request에 사용된 nonce 또는 code_challenge 값을 수정할 수 있다면 앞서 설명한 대응책을 우회할 수 있습니다. 공격자는 이 값을 위 공격의 2단계에서 자신의 세션에 대해 client가 선택한 값과 같게 수정할 수 있습니다. (그러려면 공격자가 client와의 세션을 시작한 뒤에 피해자의 client 세션이 시작되어야 합니다.) 그런 다음 공격자가 피해자의 authorization code를 가로챌 수 있다면, 3단계에서 탈취한 code를 주입할 수 있으며, PKCE 또는 nonce를 사용하더라도 마찬가지입니다.¶

이 공격은 복잡하며 공격자와 피해자의 세션 사이에 긴밀한 상호작용이 필요합니다. 그렇더라도 4.1절, 4.2절, 4.3절, 4.4절 및 4.11절에 설명된 대로 공격자가 authorization response의 내용을 읽지 못하도록 하는 조치는 여전히 필요합니다.¶

4.6. Access Token Injection

access token injection 공격에서 공격자는 탈취한 access token을 정상적인 client(공격자가 제어하지 않는 client)에 주입하려고 시도합니다. 일반적으로 이는 공격자가 유출된 access token을 이용하여 특정 client에서 사용자를 사칭하려 할 때 발생합니다.¶

공격을 수행하기 위해 공격자는 implicit grant를 사용하여 client와 OAuth flow를 시작하고, authorization server가 발급한 access token을 바꾸어 authorization response를 수정하거나 유출된 access token을 포함하는 authorization server 응답을 직접 만들어 냅니다. 이 응답에는 client가 해당 transaction을 위해 생성한 state 값이 포함되어 있으므로, client는 이를 CSRF 공격으로 취급하지 않고 공격자가 주입한 access token을 사용합니다.¶

4.6.1. 대응책

순수한 OAuth flow에서는 token이 transaction이나 특정 user agent에 전혀 바인딩되지 않은 채 발급되므로, 이러한 주입 공격을 탐지할 방법이 없습니다.¶

OpenID Connect에서는 authorization response에 at_hash claim이 담긴 ID Token도 포함되므로 이 공격을 완화할 수 있습니다. 따라서 공격자는 응답의 access token과 ID Token을 모두 바꾸어야 합니다. ID Token은 서명되거나 인증을 제공하는 방식으로 암호화되므로 공격자는 이를 위조할 수 없습니다. 또한 공격자는 탈취한 access token에 대응하는 유출된 ID Token을 주입할 수도 없습니다. 유출된 ID Token의 nonce claim에는 매우 높은 확률로 authorization response에서 기대하는 값과 다른 값이 들어 있기 때문입니다.¶

공격자가 resource endpoint에서 access token을 직접 사용하지 못하도록 하려면 sender-constrained access token과 같은 추가 보호가 여전히 필요하다는 점에 유의해야 합니다.¶

2.1.2절의 권고 사항은 이러한 이유에서 도출됩니다.¶

4.7. Cross-Site Request Forgery

공격자는 예를 들어 client가 공격자의 제어하에 있는 resource에 접근하게 만들기 위해, 피해자의 기기에서 정상적인 client의 redirection URI로 향하는 요청을 주입하려고 시도할 수 있습니다. 이는 Cross-Site Request Forgery(CSRF)로 알려진 공격의 변형입니다.¶

4.7.1. 대응책

오랫동안 확립되어 온 대응책은 client가 앞서 설명한 대로 redirection URI로 향하는 요청을 user agent 세션에 연결하는 state parameter에 CSRF Token이라고도 하는 난수를 전달하는 것입니다. 이 대응책은 5.3.5절([RFC6819])에 자세히 설명되어 있습니다. PKCE 또는 OpenID Connect의 nonce 값도 동일한 보호를 제공합니다.¶

CSRF 보호를 위해 state 또는 nonce 대신 PKCE를 사용할 때는 다음 사항에 유의해야 합니다.¶

  • client는 CSRF 보호를 위해 PKCE를 사용하기 전에 authorization server가 PKCE를 지원하는지 확인해야 합니다(MUST). authorization server가 PKCE를 지원하지 않는다면 CSRF 보호를 위해 state 또는 nonce를 사용해야 합니다(MUST).¶

  • state를 애플리케이션 상태 전달에 사용하며 그 내용의 무결성이 중요하다면, client는 반드시(MUST) state가 변조되거나 서로 바뀌지 않도록 보호해야 합니다. 이는 state의 내용을 브라우저 세션에 바인딩하거나 state 값을 서명/암호화하거나, 두 방법을 함께 사용하여 달성할 수 있습니다. 그 한 예는 만료된 Internet-Draft [JWT-ENCODED-STATE]에서 다룹니다.¶

따라서 authorization server는 자신의 PKCE 지원 여부를 탐지할 수 있는 방법을 제공해야 합니다(MUST). [RFC8414]에 따른 Authorization Server Metadata 사용이 권장됩니다(RECOMMENDED). 다만 authorization server는 대신 배포 환경에 고유한 방법으로 PKCE 지원을 보장하거나 확인할 수 있도록 해도 됩니다(MAY).¶

PKCE는 authorization response를 읽을 수 있는 공격자가 있더라도 CSRF 공격에 대한 강력한 보호를 제공합니다(공격자 (A3), 3절 참조). state를 사용하거나 authorization response에서 ID Token을 반환하는 경우(예: response_type=code+id_token), 공격자는 state 값을 알아내어 위조된 authorization response에 재전송하거나, ID Token에서 nonce를 추출하여 authorization server로 보내는 새 요청에 사용함으로써 동일한 nonce를 갖는 ID Token을 발급받을 수 있습니다. 그런 다음 이 새로운 ID Token을 CSRF 공격에 사용할 수 있습니다.¶

4.8. PKCE Downgrade Attack

PKCE를 지원하지만 모든 flow에서 그 사용을 의무화하지 않는 authorization server는 PKCE downgrade 공격에 취약할 수 있습니다.¶

이 공격의 첫 번째 전제 조건은 authorization request에 해당 flow의 PKCE를 활성화하거나 비활성화하는, 공격자가 제어할 수 있는 플래그가 존재하는 것입니다. code_challenge parameter의 유무가 이 용도로 쓰일 수 있습니다. 즉, authorization server는 authorization request에 이 parameter가 있으면 PKCE를 활성화하고 강제하지만, 없으면 PKCE를 강제하지 않습니다.¶

이 공격의 두 번째 전제 조건은 client가 state를 전혀 사용하지 않거나(예: CSRF 방지를 PKCE에 의존하기 때문), state를 올바르게 검사하지 않는 것입니다.¶

대략적으로 말하면 이 공격은 CSRF 공격의 변형입니다. 공격자는 4.7절에 설명된 공격과 동일한 목표를 달성합니다. 즉, 공격자의 resource에 바인딩된 authorization code(그리고 그에 따라 access token)를 피해자와 client 사이의 세션에 주입합니다.¶

4.8.1. 공격 설명

  1. 사용자가 어떤 client를 사용하여 authorization server에서 OAuth 세션을 시작했습니다. client는 authorization request에서 PKCE code challenge로 code_challenge=hash(abc) parameter를 설정했습니다(해시 함수와 parameter 인코딩은 [RFC7636]에 정의된 대로 적용합니다). 이제 client는 사용자의 브라우저에서 authorization response를 받기를 기다립니다.¶
  2. 공격을 수행하기 위해 공격자는 자신의 기기를 사용하여 표적 client와 authorization flow를 시작합니다. 이제 client는 authorization request에 다른 PKCE code challenge, 예를 들어 code_challenge=hash(xyz)를 사용합니다. 공격자는 이 요청을 가로채고 요청에서 code_challenge parameter 전체를 제거합니다. 이 단계는 공격자의 기기에서 수행되므로 공격자는 예를 들어 브라우저 디버깅 도구를 사용하여 요청 내용에 완전히 접근할 수 있습니다.¶
  3. authorization server가 PKCE 없는 flow를 허용한다면, 어떤 PKCE code challenge에도 바인딩되지 않은 code를 생성합니다.¶
  4. 이제 공격자는 authorization server와 맺은 자신의 세션에 해당하는 code가 포함된 authorization response URL로 사용자의 브라우저를 리디렉션합니다.¶
  5. 사용자의 브라우저가 client에 authorization code를 보내면, client는 authorization server에서 이 code를 access token으로 교환하려고 시도합니다. client는 token request에서 PKCE code verifier로 code_verifier=abc를 보냅니다.¶
  6. authorization server는 이 code가 어떤 PKCE code challenge에도 바인딩되지 않았음을 확인하므로, code_verifier parameter의 존재 여부나 내용을 검사하지 않습니다. 그리고 사용자가 제어하는 client에 access token(공격자의 resource에 속하는 token)을 발급합니다.¶

4.8.2. 대응책

state를 올바르게 사용하면 이 공격을 방지할 수 있습니다. 하지만 실제로는 많은 OAuth client가 state를 올바르게 사용하거나 검사하지 않는 것으로 나타났습니다.¶

따라서 authorization server는 이 공격을 완화해야 합니다(MUST).¶

앞서 설명한 공격을 authorization server 관점에서 보면, token endpoint에서 code_verifier parameter가 수신되지만 authorization code가 발급된 OAuth flow의 authorization request에는 code_challenge parameter가 없었다는 점에 유의해야 합니다.¶

이 사실을 이용하여 이 공격을 완화할 수 있습니다. [RFC7636]은 이미 다음 사항을 의무화하고 있습니다.¶

  • PKCE를 지원하는 authorization server는 authorization request에 code challenge가 포함되어 있는지 검사하고, 이 정보를 발급하는 code에 바인딩해야 합니다(MUST). 그리고¶
  • token endpoint에 code가 도착했을 때 그 code를 발급하게 한 authorization request에 code_challenge가 있었다면, token request에는 유효한 code_verifier가 있어야 합니다.¶

여기에 더해 PKCE downgrade 공격을 방지하기 위해 authorization server는 반드시(MUST) authorization request에 code_challenge가 없었다면, code_verifier를 포함하여 token endpoint로 보내는 요청이 거부되도록 해야 합니다.¶

PKCE 사용을 의무화하는 authorization server는(일반적으로 의무화하든 특정 client에 대해 의무화하든) 이 보안 조치를 암묵적으로 구현합니다.¶

4.9. Resource Server에서의 Access Token 유출

특정 상황에서는 resource server에서 access token이 유출될 수 있습니다.¶

4.9.1. 위조 resource server에 의한 access token 피싱

공격자는 자신의 resource server를 구축하고, 다른 resource server에서 유효한 access token을 그 서버로 보내도록 client를 속일 수 있습니다((A1) 및 (A5) 공격자는 Section 3 참조). Client가 이 위조 resource server에 유효한 access token을 보내면, 공격자는 그 token을 사용하여 resource owner를 대신해 다른 서비스에 접근할 수 있습니다.¶

이 공격은 client가 개발 시점에 하나의 특정 resource server 및 그 URL에 바인딩되지 않고, 실행 시점에 client 인스턴스에 resource server URL이 제공된다고 가정합니다. 이러한 late binding은 client가 표준화된 API를 구현하는 서비스(예: 이메일, 일정 관리, eHealth 또는 open banking용 서비스)를 사용하고 사용자나 관리자가 client를 설정하는 상황에서 일반적입니다.¶

4.9.2. 침해된 resource server

공격자는 해당 배포 환경의 리소스에 접근하기 위해 resource server를 침해할 수 있습니다. 침해의 범위는 로그 파일 등 시스템 일부에 대한 접근부터 해당 서버의 완전한 제어까지 다양할 수 있으며, 완전한 제어권을 얻으면 모든 통제를 우회하고 모든 리소스에 접근할 수 있습니다. 또한 공격자는 침해된 시스템에 보관된 다른 access token을 획득할 수 있으며, 이러한 token은 다른 resource server에 접근하는 데에도 유효할 수 있습니다.¶

서버 시스템의 보안을 강화하고 모니터링하여 서버 침해를 방지하는 일은 표준 운영 절차로 간주되므로 이 문서의 범위를 벗어납니다. Section 4.9는 OAuth 관련 침해의 영향과 탈취된 access token의 재사용에 초점을 맞춥니다.¶

4.9.3. 대응책

구현자는 악의적 행위자의 access token 재사용에 대응하기 위해 다음 조치를 고려하는 것이 좋습니다.¶

  • Section 4.10.1에 설명된 sender-constrained access token을 사용하여 공격자가 다른 resource server에서 access token을 재사용하지 못하도록 하는 것이 좋습니다(SHOULD). 공격자가 웹 서버 로그에 대한 읽기 전용 접근처럼 침해된 시스템의 일부에만 접근할 수 있다면, sender-constrained access token은 침해된 시스템에서의 재사용도 방지할 수 있습니다.¶
  • Section 4.10.2에 설명된 audience restriction을 사용하여 탈취된 access token이 다른 resource server에서 재사용되지 않도록 하는 것이 좋습니다(SHOULD).¶
  • Resource server는 access token을 다른 민감한 비밀 정보와 마찬가지로 취급하고, 평문으로 저장하거나 전송하지 않아야 합니다(MUST).¶

첫 번째와 두 번째 권고는 access token이 유출되는 다른 시나리오에도 적용됩니다(공격자 (A5)는 Section 3 참조).¶

4.10. 도난당한 access token의 악용

공격자는 다양한 방법으로 access token을 훔칠 수 있습니다. 예를 들어 4.1, 4.2, 4.3, 4.4 및 4.9절에 설명된 공격을 이용할 수 있습니다. 이 중 일부 공격은 각 절에 설명된 특정 보안 조치로 완화할 수 있습니다. 그러나 어떤 경우에는 이러한 조치가 충분하지 않거나 올바르게 구현되지 않습니다. 따라서 authorization server는 아래에 설명하는 대로 access token에 sender constraint와 audience restriction이 적용되도록 하는 것이 좋습니다(SHOULD). 일부 배포 환경에서는 아키텍처 및 성능상의 이유로 이러한 조치를 사용하지 못할 수 있습니다.¶

4.10.1. Sender-constrained access token

이름에서 알 수 있듯이 sender-constrained access token은 access token의 적용 범위를 특정 발신자로 제한합니다. Resource server가 해당 token을 수락하려면, 이 발신자는 먼저 특정 비밀 정보를 알고 있음을 입증해야 합니다.¶

일반적인 흐름은 다음과 같습니다.¶

  1. Authorization server는 해당 access token을 특정 client에 바인딩하는 데이터를 access token에 연결합니다. 이 바인딩에는 client의 신원을 활용할 수 있지만, 대부분의 경우 authorization server는 client가 알고 있는 키 자료 또는 그 키 자료에서 파생된 데이터를 활용합니다.¶
  2. 이 키 자료는 어떤 방식으로든 배포되어야 합니다. Authorization server가 바인딩을 생성하기 전에 키 자료가 이미 존재하거나, authorization server가 임시 키를 생성합니다. 기존 키 자료의 배포 방식은 접근법마다 다릅니다. 예를 들어 X.509 인증서를 사용할 수 있으며, 이 경우 등록 과정에서 명시적으로 배포가 이루어집니다. 또는 TLS 계층에서 키 자료를 생성하고 배포할 수 있으며, 이 경우 TLS 연결 설정 중에 자동으로 이루어질 수 있습니다.¶
  3. Resource server는 실제 proof-of-possession(소유 증명) 검사를 구현해야 합니다. 일반적으로 이 검사는 애플리케이션 수준에서 이루어지며, 전송 계층(예: TLS)이 제공하는 특정 자료와 연결되는 경우가 많습니다. Resource server는 proof-of-possession의 재사용이 불가능하도록 보장해야 합니다.¶

OAuth 작업반은 proof-of-possession을 사용하는 sender-constrained access token의 두 가지 방식을 정의했으며, 두 방식 모두 실제로 사용되고 있습니다.¶

  • "OAuth 2.0 Mutual-TLS Client Authentication and Certificate-Bound Access Tokens" [RFC8705]: 이) 문서에 명시된 접근법에서는 client 인증과 sender-constrained access token 모두에 mutual TLS를 사용할 수 있습니다. Sender-constrained access token을 위해 resource server는 client의 공개 키 fingerprint로 client를 식별합니다. Authorization server는 access token 요청을 처리하는 동안 TLS 스택에서 client의 공개 키를 얻고, 그 fingerprint를 해당 access token에 연결합니다. Resource server도 같은 방식으로 TLS 스택에서 공개 키를 얻고, 그 fingerprint를 access token에 연결된 fingerprint와 비교합니다.¶
  • "OAuth 2.0 Demonstrating Proof of Possession (DPoP)" [RFC9449]: DPoP는 access token과 refresh token에 sender constraint를 적용하기 위한 애플리케이션 수준의 메커니즘을 제시합니다. 이 메커니즘은 공개 키/개인 키 쌍과 애플리케이션 수준의 서명에 기반한 proof-of-possession을 사용합니다. DPoP는 public client에서 사용할 수 있으며, confidential client의 경우 어떤 client 인증 방식과도 결합할 수 있습니다.¶

공격자가 token과 키 자료에 접근하면 sender-constrained token의 보안이 약화된다는 점에 유의해야 합니다. 특히 client 소프트웨어가 변조되었거나, client가 브라우저에서 실행될 때 cross-site scripting 공격을 당하는 경우가 이에 해당합니다. 키 자료가 하드웨어 또는 소프트웨어 보안 모듈로 보호되거나 TLS 스택에서처럼 간접적으로만 접근할 수 있다면, sender-constrained token은 적어도 client가 오프라인인 동안, 즉 공격자가 보안 모듈이나 인터페이스를 사용할 수 없을 때 token이 사용되는 것을 방지합니다. 이는 access token뿐만 아니라 refresh token에도 적용됩니다(Section 4.14 참조).¶

4.10.2. Audience-restricted access token

Audience restriction은 기본적으로 access token을 특정 resource server에서만 사용하도록 제한합니다. Authorization server가 access token을 특정 resource server에 연결하면, resource server는 의도된 audience를 검증해야 합니다. Access token이 의도된 audience 검증을 통과하지 못하면 resource server는 해당 요청의 처리를 거부합니다.¶

일반적으로 audience restriction은 token 유출의 영향을 제한합니다. 위조 resource server의 경우에는 아래에 설명하는 대로 피싱으로 탈취한 access token이 정상적인 resource server에서 악용되는 것도 방지할 수 있습니다.¶

Audience는 논리적 이름이나 URL과 같은 물리적 주소로 표현할 수 있습니다. 피싱을 방지하려면 client가 실제로 요청을 보낼 URL을 사용해야 합니다. 피싱의 경우 이 URL은 위조 resource server를 가리킵니다. 공격자가 URL이 다른 정상적인 resource server에서 access token을 사용하려고 하면, resource server는 불일치, 즉 잘못된 audience를 탐지하고 요청의 처리를 거부합니다.¶

Authorization server가 모든 resource server의 URL을 알고 있는 배포 환경에서는, 알 수 없는 resource server URL에 대한 access token 발급을 단순히 거부할 수도 있습니다.¶

이 방식이 동작하려면 client는 의도한 resource server를 authorization server에 알려야 합니다. 이를 위해 [RFC8707]의 메커니즘을 사용하거나 scope(접근 범위) 값에 정보를 인코딩할 수 있습니다(Section 3.3, [RFC6749] 참조).¶

URL 대신 resource server의 X.509 인증서 fingerprint를 audience 값으로 활용할 수도 있습니다. 이 변형 방식은 다른 CA에서 발급받은 유효한 TLS 인증서를 사용하여 정상적인 resource server의 URL을 사칭하려는 시도도 탐지할 수 있게 합니다. Resource server URL을 authorization server로부터 숨기는 것이 개인정보 보호상의 이점으로 여겨질 수도 있습니다.¶

Audience restriction은 client 측에서 암호학적 처리가 필요하지 않으므로 사용하기 더 쉬워 보일 수 있습니다. 그러나 모든 access token이 특정 resource server에 바인딩되므로, client가 여러 resource server에 접근할 때에는 각 resource server 전용 access token도 개별적으로 얻어야 합니다. ([RFC8707]에 명시된 resource indicator가 이를 달성하는 데 도움이 될 수 있습니다.) [TOKEN-BINDING]도 서로 다른 token-binding ID를 access token에 연결해야 했기 때문에 같은 특성이 있었습니다. 반면 OAuth 2.0용 mutual TLS [RFC8705]를 사용하면 client가 여러 resource server에서 access token을 사용할 수 있습니다.¶

Audience restriction, 더 일반적으로는 client가 access token을 사용하려는 곳을 authorization server에 알리는 것에는 token 유출 방지의 범위를 넘어서는 추가 이점이 있다는 점에 유의해야 합니다. 이를 통해 authorization server는 해당 서버에 맞게 형식과 내용을 특별히 구성한 별도의 access token을 생성할 수 있습니다. 이는 구조화된 access token을 사용하는 배포 환경에서 기능 및 개인정보 보호 측면의 큰 이점을 제공합니다.¶

4.10.3. 논의: 메타데이터를 통한 유출 방지

Authorization server는 access token을 안전하게 사용할 수 있는 위치에 관한 추가 정보를 client에 제공할 수 있습니다. 아래에서는 이 접근법과 이를 권장하지 않는 이유를 논의합니다.¶

가장 단순한 형태에서는 authorization server가 자신이 알고 있는 resource server의 목록을 게시해야 합니다. 다음 예제는 비표준 Authorization Server Metadata 매개변수 resource_servers를 사용하여 이를 보여 줍니다.¶

HTTP/1.1 200 OK
Content-Type: application/json

{
  "issuer":"https://server.somesite.example",
  "authorization_endpoint":
    "https://server.somesite.example/authorize",
  "resource_servers":[
    "email.somesite.example",
    "storage.somesite.example",
    "video.somesite.example"
  ]
  ...
}
¶

authorization server는 access token이 유효한 URL도 token response에 반환할 수 있습니다. 다음 예시와 비표준 반환 매개변수 access_token_resource_server가 이를 보여 줍니다.¶

HTTP/1.1 200 OK
Content-Type: application/json;charset=UTF-8
Cache-Control: no-store
Pragma: no-cache

{
  "access_token":"2YotnFZFEjr1zCsicMWpAA",
  "access_token_resource_server":
    "https://hostedresource.somesite.example/path1",
...
}
¶

이 완화 전략은 client가 보안 정책을 시행하고 정당한 목적지로만 access token을 전송하는 데 의존합니다. OAuth 관련 보안 연구 결과(예: [research.ubc] 및 [research.cmu] 참조)에 따르면, 상당수 client 구현은 state 검사와 같은 보안 통제를 구현하지 않거나 제대로 구현하지 못합니다. 따라서 access token 피싱 방지도 client에 의존하면 실패할 가능성이 높습니다. 또한 authorization server 및 resource server 대비 client의 수를 고려하면, 보안 관련 로직을 가능한 한 많이 이들 서버로 옮기는 것이 더 실현 가능한 접근 방식으로 여겨집니다. client가 전체적인 보안에 기여해야 한다는 점은 분명합니다. 그러나 4.10.1절 및 4.10.2절에서 설명하는 것처럼, 관련 당사자 사이에 더 나은 균형을 제공하는 대안적 대응책도 있습니다.¶

4.11. Open Redirection

authorization server 또는 client에 open redirector가 있으면 다음 공격이 발생할 수 있습니다. 이러한 endpoint는 예를 들어 사용자를 외부 웹사이트로 리디렉션하기 전에 메시지를 표시하거나, 로그인 안내 등으로 중단되기 전에 사용자가 방문하려던 URL로 다시 리디렉션하기 위해 구현되기도 합니다.¶

4.11.1. Open Redirector로 동작하는 Client

client는 open redirector를 노출해서는 안 됩니다(MUST NOT). 공격자는 4.1.2절에서 설명한 것처럼 open redirector를 이용하여 client를 가리키는 URL을 만들고, 이를 활용해 authorization code와 access token을 유출할 수 있습니다. 또 다른 악용 사례는 client를 가리키는 것처럼 보이는 URL을 만드는 것입니다. 그러면 사용자가 속아서 그 URL을 신뢰하고 브라우저에서 열 수 있습니다. 이는 피싱에 악용될 수 있습니다.¶

open redirection을 방지하려면 client는 대상 URL이 허용되거나 요청의 출처와 무결성을 인증할 수 있는 경우에만 리디렉션하는 것이 좋습니다. open redirection에 대한 대응책은 OWASP [owasp.redir]에 설명되어 있습니다.¶

4.11.2. Open Redirector로 동작하는 Authorization Server

client의 경우와 마찬가지로 공격자는 authorization server, 특히 그 URL에 대한 사용자의 신뢰를 이용해 피싱 공격을 시도할 수 있습니다. OAuth authorization server는 일상적으로 사용자를 다른 웹사이트(client)로 리디렉션하지만, 이를 안전하게 수행해야 합니다.¶

4.1.2.1절([RFC6749])은 authorization server가 user agent를 자동으로 리디렉션해서는 안 된다는(MUST NOT) 규정을 client_id와 redirect_uri의 조합이 유효하지 않은 경우에 적용함으로써 이미 open redirect를 방지하고 있습니다.¶

그러나 공격자는 올바르게 등록된 redirection URI를 이용해 피싱 공격을 수행할 수도 있습니다. 예를 들어 공격자는 dynamic client registration [RFC7591]을 통해 client를 등록하고 다음 공격 중 하나를 수행할 수 있습니다.¶

  1. 유효하지 않은 scope 값을 사용하는 등 의도적으로 잘못된 authorization request를 전송하여, authorization server가 user agent를 공격자의 피싱 사이트로 리디렉션하도록 지시합니다.¶
  2. 공격자가 제어하는 client_id와 redirect_uri를 사용하여 의도적으로 유효한 authorization request를 전송합니다. 사용자 인증 후 authorization server는 사용자에게 해당 요청에 동의할지 묻습니다. 사용자가 요청에 문제가 있음을 알아차리고 거절하더라도 authorization server는 여전히 user agent를 피싱 사이트로 리디렉션합니다. 이 경우 사용자가 어떤 행동을 하든 user agent는 피싱 사이트로 리디렉션됩니다.¶
  3. 유효한 silent authentication 요청(prompt=none)을 공격자가 제어하는 client_id와 redirect_uri를 사용하여 의도적으로 전송합니다. 이 경우 authorization server는 user agent를 피싱 사이트로 자동으로 리디렉션합니다.¶

authorization server는 이러한 위협을 방지하기 위한 예방 조치를 취해야 합니다(MUST). authorization server는 사용자를 리디렉션하기 전에 항상 먼저 사용자를 인증하고, silent authentication 사용 사례를 제외하고는 필요할 때 사용자에게 자격 증명을 요청해야 합니다(MUST). authorization server는 자체 위험 평가를 바탕으로 redirection URI를 신뢰할 수 있는지 판단해야 합니다. 이때 URI 뒤에 있는 콘텐츠의 신빙성과 신뢰성을 평가하기 위해 내부적으로 또는 외부 서비스를 통해 수행한 URI 분석, 그리고 redirection URI 및 기타 client 데이터의 출처를 고려할 수 있습니다.¶

authorization server는 redirection URI를 신뢰하는 경우에만 user agent를 자동으로 리디렉션하는 것이 좋습니다(SHOULD). URI를 신뢰하지 않는 경우 authorization server는 사용자에게 이를 알리고 사용자가 올바른 결정을 내리도록 맡길 수 있습니다(MAY).¶

4.12. 307 Redirect

authorization endpoint의 일반적인 프로토콜 흐름에서는 authorization server가 사용자에게 양식에 자격 증명을 입력하도록 요청하고, 이 양식은 HTTP POST 메서드로 authorization server에 다시 제출됩니다. authorization server는 자격 증명을 확인하고, 확인에 성공하면 user agent를 client의 redirection endpoint로 리디렉션합니다.¶

[RFC6749]에서는 이 목적으로 HTTP 상태 코드 302 (Found)를 사용하지만, "user agent를 통해 사용할 수 있는 다른 어떤 방법으로 이 리디렉션을 수행해도 허용됩니다". 대신 상태 코드 307을 사용하여 리디렉션하면 user agent는 HTTP POST로 사용자의 자격 증명을 client에 전송합니다.¶

이로 인해 민감한 자격 증명이 client에 공개됩니다. client가 악의적이라면 이 자격 증명을 사용하여 authorization server에서 사용자를 사칭할 수 있습니다.¶

개발자에게는 예상 밖의 동작일 수 있지만, 이는 15.4.8절([RFC9110])에 정의되어 있습니다. 이 상태 코드(307)는 user agent가 POST 요청을 GET 요청으로 다시 작성하여 POST 요청 본문의 양식 데이터를 제거하도록 요구하지 않습니다.¶

HTTP 표준 [RFC9110]에서 HTTP POST 요청을 HTTP GET 요청으로 다시 작성하도록 명확히 강제하는 것은 상태 코드 303뿐입니다. 널리 사용되는 302를 포함한 다른 모든 상태 코드에서는 user agent가 POST 요청을 GET 요청으로 다시 작성하지 않기로 선택할 수 있으며, 그 결과 사용자의 자격 증명이 client에 공개될 수 있습니다. (다만 실제로 대부분의 user agent는 307 redirect에서만 이러한 동작을 보입니다.)¶

따라서 사용자의 자격 증명이 포함되어 있을 가능성이 있는 요청을 리디렉션하는 authorization server는 리디렉션에 HTTP 상태 코드 307을 사용해서는 안 됩니다(MUST NOT). 그러한 요청에 예를 들어 JavaScript가 아닌 HTTP redirection을 사용하는 경우 authorization server는 HTTP 상태 코드 303 (See Other)을 사용하는 것이 좋습니다(SHOULD).¶

4.13. TLS를 종료하는 Reverse Proxy

HTTP 애플리케이션의 일반적인 배포 아키텍처는 TLS 연결을 종료하고 들어오는 요청을 해당 애플리케이션 서버 노드에 전달하는 reverse proxy 뒤에 애플리케이션 서버를 숨기는 방식입니다.¶

이 절에서는 이 배포 아키텍처에서 OAuth와 관련된 몇 가지 공격 관점을 살펴보고 보안 통제를 권고합니다.¶

일부 상황에서는 reverse proxy가 추가 처리를 위해 보안 관련 데이터를 upstream 애플리케이션 서버에 전달해야 합니다. 예를 들면 요청 발신자의 IP 주소, token-binding ID, 인증된 TLS client 인증서가 있습니다. 이러한 데이터는 보통 upstream 요청에 추가하는 HTTP 헤더로 전달됩니다. 이 헤더는 애플리케이션별로 정의한 사용자 정의 헤더인 경우가 많지만, client 인증서와 client 인증서 체인을 위한 표준화된 헤더 필드는 [RFC9440]에 정의되어 있습니다.¶

reverse proxy가 외부에서 전송된 헤더를 그대로 통과시키면 공격자는 위조한 헤더 값을 proxy를 통해 애플리케이션 서버에 직접 보내 보안 통제를 우회하려고 시도할 수 있습니다. 예를 들어 reverse proxy는 일반적으로 X-Forwarded-For 헤더를 받아들이고 여기에 들어오는 요청의 출처만 추가하여 목록으로 만듭니다. 애플리케이션 서버에서 수행하는 로직에 따라 공격자는 허용된 IP 주소를 헤더에 추가하는 것만으로 보호 기능을 무력화할 수 있습니다.¶

따라서 reverse proxy는 애플리케이션 서버의 보안과 관련된 모든 헤더 값의 진정성과 무결성을 보장하도록 모든 수신 요청을 정제해야 합니다(MUST).¶

공격자가 proxy와 애플리케이션 서버 사이의 내부 네트워크에 접근할 수 있다면, 적용된 보안 통제를 우회하려고 시도할 수도 있습니다. 따라서 통신하는 주체의 진정성을 보장하는 것이 필수적입니다. 또한 reverse proxy와 애플리케이션 서버 사이의 통신 링크는 메시지의 도청, 주입, 재전송 공격으로부터 보호되어야 합니다(MUST).¶

4.14. Refresh Token 보호

refresh token은 새로운 access token을 얻는 편리하고 사용자 친화적인 방법입니다. 또한 authorization server가 수명이 짧고 scope가 축소된 access token을 발급할 수 있게 하여 access token 유출의 잠재적 영향을 줄이므로 OAuth의 보안에도 기여합니다.¶

4.14.1. 논의

refresh token은 특정 client에 부여된 접근 권한의 전체 범위를 나타내며 특정 리소스로 더 제한되지 않으므로 공격자에게 매력적인 표적입니다. 공격자가 refresh token을 유출하고 이를 재전송 공격에 성공적으로 사용할 수 있다면, access token을 생성하고 이를 사용하여 resource owner를 대신해 resource server에 접근할 수 있게 됩니다.¶

[RFC6749]는 다음 사항을 요구하여 이미 견고한 기본 보호를 제공합니다.¶

  • 전송 중이거나 저장된 refresh token의 기밀성,¶
  • authorization server와 client 사이에서 TLS로 보호되는 연결을 통한 refresh token 전송,¶
  • authorization server가 refresh token과 특정 client 사이의 바인딩을 유지하고 확인하며, 가능하다면 token 갱신 중 해당 client를 인증하는 것, 그리고¶
  • refresh token을 생성하거나 수정하거나 추측할 수 없도록 하는 것.¶

[RFC6749]는 또한 관련 오류 코드와 응답 동작을 정의함으로써 refresh token 만료 및 폐기와 refresh token rotation 같은 추가적인 구현별 보안 조치의 기반도 마련합니다.¶

이 명세는 [RFC6749]의 범위를 넘어서는 권고 사항과 명확한 설명을 제공합니다.¶

4.14.2. 권고 사항

authorization server는 위험 평가를 바탕으로 특정 client에 refresh token을 발급할지 결정해야 합니다(MUST). authorization server가 refresh token을 발급하지 않기로 결정하면, client는 authorization code grant type과 같은 다른 grant type을 이용하여 새 access token을 얻을 수 있습니다(MAY). 이 경우 authorization server는 사용자 경험을 최적화하기 위해 쿠키와 지속적인 grant를 이용할 수 있습니다.¶

refresh token을 발급하는 경우, 해당 refresh token을 resource owner가 동의한 scope 및 resource server에 바인딩해야 합니다(MUST). 이는 정당한 client의 권한 상승을 방지하고 refresh token 유출의 영향을 줄이기 위한 것입니다.¶

confidential client의 경우, [RFC6749]는 이미 refresh token이 발급 대상 client에 의해서만 사용될 수 있어야 한다고 요구합니다.¶

authorization server는 public client에 대한 악의적 행위자의 refresh token 재전송을 탐지하기 위해 다음 방법 중 하나를 이용해야 합니다(MUST).¶

  • Sender-constrained refresh tokens: authorization server는 예를 들어 [RFC8705] 또는 [RFC9449]를 이용하여 refresh token을 특정 client 인스턴스에 암호학적으로 바인딩합니다.¶

  • Refresh token rotation: authorization server는 access token 갱신 응답마다 새 refresh token을 발급합니다. 이전 refresh token은 무효화되지만, 그 관계에 대한 정보는 authorization server가 유지합니다. refresh token이 침해되어 이후 공격자와 정당한 client 모두가 이를 사용하면, 둘 중 하나는 무효화된 refresh token을 제시하게 되며, 이를 통해 authorization server가 침해 사실을 알게 됩니다. authorization server는 어느 쪽이 유효하지 않은 refresh token을 제출했는지 판단할 수 없지만, 활성 refresh token을 폐기합니다. 이렇게 하면 정당한 client가 새로운 authorization grant를 얻어야 하는 대가를 치르지만 공격은 중단됩니다.¶

    구현 참고 사항: refresh token이 속한 grant를 refresh token 자체에 인코딩할 수 있습니다. 이를 통해 authorization server는 refresh token이 속한 grant를 효율적으로 파악하고, 나아가 폐기해야 하는 모든 refresh token을 파악할 수 있습니다. 이 경우 authorization server는 예를 들어 서명을 사용하여 refresh token 값의 무결성을 보장해야 합니다(MUST).¶

authorization server는 다음과 같은 보안 이벤트가 발생하면 refresh token을 자동으로 폐기할 수 있습니다(MAY).¶

  • 비밀번호 변경 또는¶
  • authorization server에서 로그아웃.¶

client가 한동안 비활성 상태였던 경우, 즉 refresh token이 한동안 새 access token을 얻는 데 사용되지 않은 경우에는 refresh token을 만료시키는 것이 좋습니다(SHOULD). 만료 시간은 authorization server의 재량에 따릅니다. 전역 값일 수도 있고, client 정책이나 refresh token과 연결된 grant 및 그 민감도를 바탕으로 결정할 수도 있습니다.¶

4.15. resource owner를 사칭하는 client

resource server는 access token이 발급된 대상 resource owner의 신원이나 client credentials grant에서의 client 신원을 바탕으로 접근 제어 결정을 내릴 수 있습니다. 예를 들어 [RFC9068](JSON Web Token (JWT) Profile for OAuth 2.0 Access Tokens)은 다음과 같이 정의된 sub claim을 포함하는 access token의 데이터 구조를 설명합니다.¶

authorization code grant와 같이 resource owner가 관여하는 grant를 통해 얻은 access token의 경우, "sub" 값은 resource owner의 subject identifier에 해당하는 것이 좋습니다(SHOULD). client credentials grant와 같이 resource owner가 관여하지 않는 grant를 통해 얻은 access token의 경우, "sub" 값은 authorization server가 client 애플리케이션을 나타내는 데 사용하는 식별자에 해당하는 것이 좋습니다(SHOULD).¶

두 방식이 모두 가능하면 resource server가 client의 신원을 resource owner의 신원으로 오인할 수 있습니다. 예를 들어 client가 authorization server에 등록할 때 자신의 client_id를 선택할 수 있다면, 악의적인 client는 이를 resource owner를 식별하는 값으로 설정할 수 있습니다(예: OpenID Connect를 사용하는 경우 sub 값). resource server가 resource owner의 관여 하에 얻은 access token과 그렇지 않은 access token을 제대로 구분할 수 없다면, client가 의도치 않게 resource owner의 리소스에 접근할 수 있게 될 수 있습니다.¶

이 공격은 [RFC9068]를 사용하는 구현뿐 아니라 이와 유사한 맞춤형 솔루션에도 영향을 미칠 수 있습니다.¶

4.15.1. 대응책

authorization server는 다음을 허용하지 않는 것이 좋습니다(SHOULD NOT). client ID와 사용자 식별자에 공통 namespace가 존재하는 경우, client가 자신의 client_id 또는 진정한 resource owner와 혼동을 일으킬 수 있는 다른 claim에 영향을 주도록 허용하는 것입니다. 이러한 공통 namespace의 예로는 sub claim이 있으며, 이는 [RFC9068]의 예로 위의 4.15절에 제시되어 있습니다. 이를 피할 수 없다면 authorization server는 resource server가 두 유형의 access token을 구분할 수 있는 다른 수단을 제공해야 합니다(MUST).¶

4.16. Clickjacking

4.4.1.9절([RFC6819])에서 설명하듯이, 인가 요청은 user interface redressing이라고도 하는 clickjacking 공격에 취약합니다. 이러한 공격에서 공격자는 authorization endpoint의 사용자 인터페이스를 무해해 보이는 환경에 삽입합니다. 사용자는 예를 들어 버튼을 클릭하여 그 환경과 상호작용한다고 생각하지만, 실제로는 의도치 않게 authorization endpoint의 사용자 인터페이스와 상호작용합니다. 반대 상황도 가능합니다. authorization endpoint와 상호작용한다고 생각하는 사용자가 원래 사용자 인터페이스 위에 겹쳐 놓은 공격자 제공 입력 필드에 의도치 않게 비밀번호를 입력할 수 있습니다. clickjacking 공격은 사용자가 거의 알아차리지 못하도록 설계할 수 있습니다. 예를 들어 다른 요소 위에 거의 보이지 않는 iframe을 겹쳐 놓을 수 있습니다.¶

공격자는 이 공격 경로를 이용하여 사용자의 인증 자격 증명을 얻고, client에 부여된 접근 scope를 변경하며, 나아가 사용자의 리소스에 접근할 수 있습니다.¶

authorization server는 clickjacking 공격을 방지해야 합니다(MUST). [RFC6819]에는 X-Frame-Options HTTP 응답 헤더 필드와 frame-busting JavaScript 사용을 비롯한 여러 대응책이 설명되어 있습니다. 이에 더하여 authorization server에는 다음 사용도 권장됩니다(SHOULD). 바로 Content Security Policy (CSP) level 2 [W3C.CSP-2] 이상입니다.¶

CSP가 효과를 발휘하려면 authorization endpoint와, 해당되는 경우 사용자 인증 및 client 인가에 사용되는 다른 endpoint(예: device authorization endpoint, 로그인 페이지, 오류 페이지 등)에 CSP를 사용해야 합니다. 이는 CSP를 지원하는 user agent에서 허가되지 않은 origin에 의한 framing을 방지합니다. client는 자신의 redirection endpoint에서 사용하는 origin 이외의 다른 origin에 의한 framing을 허용할 수 있습니다(MAY). 그러므로 authorization server는 관리자가 특정 client에 허용되는 origin을 구성하거나 client가 이를 동적으로 등록할 수 있도록, 또는 둘 다 가능하도록 허용하는 것이 좋습니다(SHOULD).¶

CSP를 사용하면 authorization server는 단일 응답 헤더 필드에 여러 origin을 지정하고 유연한 패턴을 사용하여 이를 제한할 수 있습니다(자세한 내용은 [W3C.CSP-2] 참조). CSP level 2는 frame의 origin을 제한하는 정책(frame-ancestors 사용)과 HTML 페이지에서 실행이 허용되는 스크립트의 출처를 제한하는 정책(script-src 사용)을 함께 사용하여 clickjacking을 방어하는 강력한 메커니즘을 제공합니다. 다음 목록은 그러한 정책의 비규범적 예입니다.¶

HTTP/1.1 200 OK
Content-Security-Policy: frame-ancestors https://ext.example.org:8000
Content-Security-Policy: script-src 'self'
X-Frame-Options: ALLOW-FROM https://ext.example.org:8000
...
¶

일부 user agent는 [W3C.CSP-2]를 지원하지 않으므로, authorization server가 그러한 레거시 user agent를 지원하지 않는다고 명시한 경우가 아니라면 이 기법을 다른 기법과 함께 사용하는 것이 좋습니다(SHOULD). 여기에는 [RFC6819]에 설명된 기법도 포함됩니다. 명시적으로 지원하지 않는 경우에도 추가 대응책을 적용하는 것이 좋습니다(SHOULD).¶

4.17. 브라우저 내 통신 흐름에 대한 공격

인가 응답을 HTTP 리디렉션 대신 postMessage [WHATWG.postmessage_api]와 같은 브라우저 내 통신 기법으로 전송하면, 메시지가 의도치 않게 악의적인 origin으로 전송되거나 악의적인 origin으로부터 주입될 수 있습니다.¶

4.17.1. 예

브라우저 내 통신을 이용하는 공격에 관한 다음 비규범적 의사 코드 예는 [research.rub]에 설명되어 있습니다.¶

4.17.1.1. receiver origin에 대한 불충분한 제한

postMessage로 인가 응답이나 token 응답을 전송할 때 authorization server는 client의 origin 대신 와일드카드 origin "*"로 응답을 전송합니다. 응답이 전송되는 창을 공격자가 제어하는 경우, 공격자는 응답을 읽을 수 있습니다.¶

window.opener.postMessage(
  {
    code: "ABC",
    state: "123"
  },
  "*" // any website in the opener window can receive the message
)
¶
4.17.1.2. 불충분한 URI 검증

postMessage로 인가 응답이나 token 응답을 전송할 때 authorization server가 receiver origin을 redirection URI와 대조하여 확인하지 않고, 대신 예를 들어 공격자가 제공한 origin으로 응답을 전송할 수 있습니다. 이는 4.1절에 설명된 공격과 유사합니다.¶

window.opener.postMessage(
  {
    code: "ABC",
    state: "123"
  },
  "https://attacker.example" // attacker-provided value
)
¶
4.17.1.3. sender origin의 불충분한 검증에 따른 주입

postMessage를 통해 인가 응답이나 token 응답을 받도록 되어 있는 client가 메시지의 sender origin을 검증하지 않을 수 있습니다. 이로 인해 공격자가 client에 인가 응답이나 token 응답을 주입할 수 있게 될 수 있습니다.¶

인가 응답이 악의적으로 주입된 경우, 이 공격은 4.7절에 설명된 CSRF 공격의 변형입니다. 4.7절에 설명된 대응책은 이 공격에도 적용됩니다.¶

token 응답이 악의적으로 주입된 경우, 4.10.1절에 설명된 sender-constrained access token이 일부 상황에서는 공격을 방지할 수 있지만, 일반적으로 4.17.2절에 설명된 추가 대응책이 필요합니다.¶

4.17.2. 권고 사항

client receiver origin을 사전 등록된 origin과 비교할 때 authorization server는 정확한 문자열 일치를 사용해야 하며(MUST), 이는 4.1.3절에 설명되어 있습니다. authorization server는 다음 비규범적 예에 나타난 것처럼 신뢰하는 client receiver origin으로 postMessage를 보내야 합니다(MUST).¶

window.opener.postMessage(
  {
    code: "ABC",
    state: "123"
  },
  "https://client.example" // use explicit client origin
)
¶

공격자가 postMessage의 "*" 같은 wildcard origin을 이용해 피해자의 브라우저 내 메시지를 악성 origin으로 유출할 수 있으므로, 이러한 wildcard origin을 사용해서는 안 됩니다(MUST NOT). 두 조치 모두 authorization code와 access token의 유출을 방지하는 데 기여합니다(4.1절 참조).¶

client는 client 수신 endpoint에서 브라우저 내 메시지의 주입을 방지해야 합니다(MUST). client는 다음 비규범적 예에 나타난 것처럼 정확한 문자열 일치를 사용하여 브라우저 내 메시지의 initiator origin(발신 오리진)과 authorization server origin을 비교해야 합니다(MUST).¶

window.addEventListener("message", (e) => {
  // validate exact authorization server origin
  if (e.origin === "https://honest.as.example") {
    // process e.data.code and e.data.state
  }
})
¶

브라우저 내 통신 흐름은 통신 기법만 다르게 적용하므로(즉, HTTP redirect 대신 postMessage 사용), 2.1절에 나열된 authorization response 보호 조치를 모두 동일하게 적용해야 합니다(MUST).¶
